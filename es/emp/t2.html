Multitarea: procesos y threads

Control de ejecución concurrente: desde fork y pthreads hasta cerrojos y variables de condición

10 Objetivos clave Lectura aprox. 25 min

En el mundo físico los sucesos ocurren de forma simultánea: llegan datos por la interfaz de red, el usuario pulsa un botón y los temporizadores avanzan. Un programa con un único hilo de ejecución difícilmente puede atender todas estas demandas con garantías temporales. Linux ofrece dos mecanismos fundamentales: crear múltiples procesos (processes) aislados o lanzar múltiples hilos (threads) compartiendo el mismo espacio de memoria. Este tema aborda cómo crearlos, sincronizarlos y gestionarlos, cómo planifica la CPU el sistema operativo y cómo resolver los tres grandes desafíos del acceso compartido: condiciones de carrera, sincronización y bloqueos mutuos.

§1¿Por qué necesitamos multitarea? T2.1

¿Puede un bucle while(1) atender la red, leer sensores y actualizar la pantalla sin retrasos?El mundo físico es concurrente.

El esquema habitual en microcontroladores simples es un super-bucle (super-loop) que consulta secuencialmente el estado de cada periférico (sondeo / polling). Este diseño presenta un grave inconveniente: si una tarea se bloquea esperando una respuesta de red o realizando un cálculo largo, todas las demás tareas quedan congeladas. La programación secuencial se vuelve frágil y difícil de mantener.

Linux proporciona soporte nativo para multitarea (multitasking): cada tarea se programa como una secuencia de código lineal independiente que puede bloquearse cuando no hay trabajo, dejando que el planificador del sistema operativo asigne la CPU a las tareas preparadas para ejecutarse.

grano grueso · coarse-grained

Multiproceso

Múltiples procesos independientes con espacios de memoria completamente aislados por la MMU. Máxima robustez: si un proceso cae, el resto continúa intacto. La comunicación interproceso (IPC) requiere mecanismos explícitos (tuberías, memoria compartida, sockets).

grano fino · fine-grained

Multihilo (Multithreading)

Múltiples hilos ejecutándose dentro del mismo proceso. Comparten la misma memoria global, variables y descriptores de fichero. Creación y conmutación mucho más ligeras y comunicación instantánea, requiriendo mecanismos de exclusión mutua para evitar corrupción de datos.

Concurrencia frente a paralelismo

Concurrencia hace referencia a la estructura lógica del software: múltiples tareas progresan de forma solapada en el tiempo mediante multiplexación rápida en un único núcleo de CPU. Paralelismo se refiere a la ejecución física simultánea en el mismo instante, posible únicamente si el hardware dispone de múltiples núcleos (multicore).

§2Gestión de procesos T2.2 · T2.3 · T2.4

¿Cómo se controla un proceso desde la terminal y qué ocurre cuando un programa bifurca a otro?Cada proceso posee un identificador numérico único: PID (Process ID).

Desde la consola de Linux, un proceso en primer plano mantiene ocupada la terminal hasta su terminación. Añadir el operador & al final del comando lo ejecuta en segundo plano (background). Para evitar que un proceso finalice al cerrar la sesión de terminal (señal SIGHUP), se antepone la utilidad nohup.

Ejecutar nuevos programas: exec frente a posix_spawn

Para que un proceso ejecute un binario distinto existen dos vías fundamentales:

  • Familia exec (ejecución destructiva): execv, execlp, etc. Reemplazan completamente el espacio de memoria, código y datos del proceso llamante con la nueva imagen de ejecutable. El PID se conserva, pero el código original desaparece por completo. Por esta razón, una llamada exitosa a exec nunca retorna. Solo retorna (con -1) si el fichero no existe o no se tienen permisos.
  • posix_spawn (ejecución no destructiva): Función estandarizada por POSIX que crea un nuevo proceso y ejecuta el binario especificado en una sola operación atómica, sin destruir el proceso original y optimizando el consumo de memoria en sistemas empotrados.

§3Hilos de ejecución (Threads) T2.5 · T2.6

¿Por qué usar hilos en lugar de múltiples procesos para controlar sensores y actuadores?Los hilos comparten el mismo mapa de memoria: no hay barrera de MMU entre ellos.

Un hilo (thread) es la unidad más pequeña de procesamiento que puede ser planificada por el sistema operativo. Mientras que dos procesos diferentes tienen espacios de memoria virtuales aislados, todos los hilos creados dentro de un mismo proceso comparten el mismo espacio de direcciones.

Recursos compartidos entre hilos

  • Memoria global, variables estáticas y memoria dinámica (heap).
  • Tabla de descriptores de fichero abiertos (ficheros, sockets).
  • Identificador de proceso (PID) y credenciales de usuario.
  • Manejadores de señales y directorio de trabajo actual.

Elementos privados de cada hilo

  • Identificador único de hilo: pthread_t.
  • Pila propia (stack) para variables locales y llamadas a función.
  • Copia de los registros del procesador (incluido SP y PC).
  • Máscara de señales bloqueadas y prioridad de planificación.
  • Variable de error local: errno (reentrante en entornos multihilo).

Creación, paso de argumentos y recolección (pthreads)

El estándar POSIX define la biblioteca pthread (enlace mediante -lpthread):

#include <pthread.h> void *tarea(void *arg) {    int id = *(int *)arg;    printf(\"Hilo %d en ejecución\\n\", id);    return NULL;                               // o pthread_exit(NULL)} int main(void) {    pthread_t h;    int param = 1;    pthread_create(&h, NULL, tarea, &param);   // Lanza el hilo    pthread_join(h, NULL);                     // Espera su finalización    return 0;}

Precaución al pasar argumentos por puntero: no se debe pasar la dirección de una variable local que pueda cambiar o salir de ámbito antes de que el hilo comience su ejecución. Si el hilo no necesita ser esperado mediante pthread_join, se debe marcar con pthread_detach(h) para que sus recursos internos se liberen automáticamente al finalizar.

§4Planificación de la CPU (Scheduling) T2.7

Si hay 10 hilos listos y un solo núcleo de procesador, ¿a quién le toca y durante cuánto tiempo?SCHED_OTHER (tiempo compartido) vs SCHED_FIFO / SCHED_RR (tiempo real).

El planificador (scheduler) del kernel decide qué hilo ocupa la CPU en cada momento. Un hilo transita entre tres estados básicos: Listo (Ready) esperando CPU, En ejecución (Running) ocupando el procesador, o Bloqueado (Blocked) a la espera de un evento externo, temporizador o cerrojo.

PolíticaTipoComportamiento
SCHED_OTHEREstándar (Tiempo compartido)Política predeterminada. Asigna rodajas de tiempo dinámicas según el factor 'nice'. No ofrece garantías de tiempo real.
SCHED_FIFOTiempo real estrictoEl hilo con mayor prioridad toma la CPU y no la cede hasta que termina, se bloquea voluntariamente o es desalojado por un hilo de mayor prioridad. No hay rodajas de tiempo.
SCHED_RRTiempo real Round-RobinSimilar a FIFO, pero entre hilos de la misma prioridad se asigna una rodaja de tiempo fija. Si se agota, el hilo pasa a la cola de su nivel de prioridad.

Las políticas de tiempo real (FIFO y RR) disponen de niveles de prioridad de 1 (mínima) a 99 (máxima), y requieren permisos de superusuario (root). Si un hilo voluntariamente desea ceder su rodaja a otros hilos listos de su misma prioridad, puede invocar sched_yield().

§5Condiciones de carrera y cerrojos (Mutex) T2.8

Dos hilos incrementan un contador 1000 veces cada uno. ¿Por qué el resultado final es 1650 en lugar de 2000?Una condición de carrera ocurre cuando el resultado depende del orden de entrelazado de instrucciones.

La instrucción en C contador++ no es atómica: el procesador debe leer la variable de memoria a un registro, incrementarla en el registro y volver a escribirla en memoria. Si un cambio de contexto ocurre a mitad de esta secuencia, un hilo sobreescribe los cambios del otro, produciendo una condición de carrera (race condition).

El fragmento de código que accede a datos compartidos se denomina sección crítica. Para garantizar que solo un hilo acceda a la sección crítica en un instante determinado se utiliza un cerrojo de exclusión mutua (mutex):

pthread_mutex_t cerrojo = PTHREAD_MUTEX_INITIALIZER; pthread_mutex_lock(&cerrojo);     // Adquiere el cerrojo; si está ocupado, se bloqueacontador++;                       // Sección crítica protegidapthread_mutex_unlock(&cerrojo);   // Libera el cerrojo y despierta a los que esperan

La variante pthread_mutex_trylock() intenta adquirir el cerrojo de inmediato: si está libre lo adquiere y retorna 0; si está ocupado retorna EBUSY de forma no bloqueante, permitiendo al hilo realizar otra tarea alternativa.

Normal

PTHREAD_MUTEX_NORMAL

Sin comprobación de reentradas. Si el mismo hilo intenta adquirirlo dos veces seguidas, se produce un auto-bloqueo permanente (deadlock).

Recursive

PTHREAD_MUTEX_RECURSIVE

Permite al hilo poseedor bloquearlo múltiples veces consecutivas. Requiere el mismo número exacto de llamadas a unlock para quedar liberado.

Errorcheck

PTHREAD_MUTEX_ERRORCHECK

Detecta y devuelve error si un hilo intenta bloquear un cerrojo que ya posee o desbloquear un cerrojo poseído por otro hilo.

§6Sincronización avanzada T2.9

¿Cómo espera un hilo a que ocurra un evento sin consumir el 100% de la CPU en un bucle vacío?Variables condicionales y semáforos permiten la espera pasiva.

Una espera activa con un bucle while(!listo); desperdicia ciclos de CPU e impide la ejecución de otros hilos. Para evitarlo, POSIX proporciona mecanismos de sincronización basados en suspensión pasiva:

Variables de condición (pthread_cond_t)

Permiten suspender un hilo de forma atómica hasta que otro hilo notifique que se cumple una determinada condición de negocio. Siempre van asociadas a un mutex:

pthread_mutex_lock(&mtx);while (cola_vacia()) {                 // Debe usarse while por despertares espurios    pthread_cond_wait(&cond, &mtx);    // Libera mtx y se bloquea atómicamente}elemento = desencolar();pthread_mutex_unlock(&mtx);

El hilo que produce el dato y cambia la condición ejecuta:

pthread_mutex_lock(&mtx);encolar(elemento);pthread_cond_signal(&cond);           // Despierta a un hilo en espera (broadcast despierta a todos)pthread_mutex_unlock(&mtx);

Semáforos POSIX (<semaphore.h>)

Un semáforo (semaphore) mantiene un contador entero no negativo que representa unidades disponibles de un recurso:

  • sem_wait(&s): Si el contador es > 0, lo decrementa en 1 y continúa. Si es 0, bloquea al hilo hasta que otro lo incremente.
  • sem_post(&s): Incrementa el contador en 1 y despierta a un hilo bloqueado. A diferencia de los cerrojos mutex, sem_post puede ser invocado con seguridad desde manejadores de señal o por un hilo distinto al que hizo la espera.

§7Bloqueo mutuo y errores habituales T2.10

El hilo A tiene el recurso 1 y espera el 2; el hilo B tiene el 2 y espera el 1. ¿Qué ocurre?Bloqueo mutuo (Deadlock): el sistema queda congelado para siempre.

El problema del bloqueo mutuo (deadlock) se produce cuando dos o más hilos quedan detenidos indefinidamente esperando recursos que están retenidos por los demás. Ilustrado célebremente por el problema de los filósofos comensales (donde cada filósofo necesita dos tenedores adyacentes para comer y todos toman primero el izquierdo, bloqueándose mutuamente).

Para que se produzca un interbloqueo deben cumplirse simultáneamente las cuatro condiciones de Coffman:

  1. Exclusión mutua: Los recursos no son compartibles al mismo tiempo.
  2. Retención y espera (Hold and wait): Un hilo retiene un recurso mientras solicita otro adicional.
  3. No apropiación (No preemption): Los recursos solo pueden ser liberados voluntariamente por el hilo que los posee.
  4. Espera circular: Existe una cadena cerrada de procesos donde cada uno espera un recurso en poder del siguiente.
Prevención de interbloqueos: orden jerárquico

La técnica más eficaz para prevenir bloqueos mutuos consiste en romper la espera circular: establecer un orden global estricto en la adquisición de los cerrojos. Si todos los hilos del sistema adquieren siempre el cerrojo A antes que el cerrojo B, la condición de espera circular resulta físicamente imposible.

Inversión de prioridades

Ocurre cuando un hilo de baja prioridad adquiere un recurso compartido, un hilo de alta prioridad lo solicita y queda bloqueado, pero un hilo de prioridad media (que no usa el recurso) desaloja al de baja prioridad por tener más prioridad de CPU. En la práctica, el hilo de alta prioridad queda indebidamente retenido por el hilo de media prioridad. Se soluciona mediante el protocolo de herencia de prioridades (el hilo de baja prioridad hereda temporalmente la prioridad del hilo de alta prioridad que espera su recurso).

Preguntas de repaso 12 preguntas

Cuestiones de repaso sobre los contenidos de este tema. Un único intento por pregunta; la justificación aparece al responder.

01¿Cuál es una ventaja principal de utilizar hilos (threads) frente a procesos independientes?

C. Al compartir el mismo mapa de memoria, el cambio de contexto entre hilos no requiere invalidar la tabla de páginas de la MMU ni duplicar estructuras pesadas del sistema (§1 y §3).

02¿Qué sucede cuando un proceso ejecuta con éxito una llamada de la familia exec (como execv)?

B. Las funciones exec son de ejecución destructiva: sustituyen la memoria de código y datos del proceso por el nuevo binario conservando el PID (§2).

03Tras invocar pid_t p = fork();, ¿cómo identifica el código si se encuentra en el proceso padre o en el proceso hijo?

A. fork retorna 0 al hijo recién creado y el PID del hijo al proceso padre, permitiendo ramificar la lógica de control mediante una sentencia if (§2).

04¿Qué es exactamente un proceso en estado zombi (defunct) en Linux?

D. El kernel mantiene la entrada del proceso zombi en su tabla de procesos para preservar el código de salida hasta que el padre invoque wait() o waitpid() (§2).

05¿Cuál de los siguientes elementos no se comparte entre los hilos de un mismo proceso?

C. Cada hilo dispone obligatoriamente de su propia pila para albergar variables locales y registros de llamada, manteniendo su propio flujo de control (§3).

06En una aplicación con hilos POSIX, ¿qué función se utiliza para esperar la finalización de un hilo y obtener su resultado?

B. pthread_join bloquea al hilo llamante hasta que el hilo indicado finaliza y recupera el puntero de retorno devuelto en pthread_exit o return (§3).

07¿En qué se diferencian las políticas de planificación de tiempo real SCHED_FIFO y SCHED_RR?

A. En SCHED_FIFO un hilo retiene la CPU hasta bloquearse o ser desalojado por mayor prioridad; en SCHED_RR los hilos de igual prioridad rotan periódicamente (§4).

08¿Por qué es indispensable evaluar la condición asociada a pthread_cond_wait() dentro de un bucle while y no de un simple if?

C. Los estándares POSIX advierten que un hilo puede despertar sin señal explícita (despertar espurio) o que otro hilo haya modificado el estado antes de que este reanude el mutex (§6).

09¿Qué sucede si un hilo invoca pthread_mutex_lock() sobre un mutex de tipo PTHREAD_MUTEX_NORMAL que ya tenía previamente bloqueado?

D. Los cerrojos normales no verifican la reentrada del propio hilo poseedor, resultando en un auto-bloqueo. Para reentradas seguras debe emplearse PTHREAD_MUTEX_RECURSIVE (§5).

10¿Cuál de las siguientes acciones permite romper la condición de espera circular y prevenir interbloqueos (deadlocks)?

B. Si todos los hilos adquieren los cerrojos en el mismo orden predeterminado (por ejemplo, cerrojo A antes de cerrojo B), no puede formarse un ciclo cerrado de dependencia (§7).

11En el problema de la inversión de prioridades, ¿cuál es la técnica estándar para evitar que un hilo de prioridad media bloquee indirectamente a uno de alta prioridad?

A. La herencia de prioridades eleva temporalmente la prioridad del hilo de baja prioridad mientras retenga un recurso solicitado por el hilo de alta prioridad (§7).

12¿Cuál es una diferencia esencial entre un semáforo POSIX (sem_t) y un cerrojo mutex (pthread_mutex_t)?

C. El cerrojo mutex modela la posesión de una sección crítica exclusiva, mientras que el semáforo modela la disponibilidad y señalización de recursos y eventos (§5 y §6).
