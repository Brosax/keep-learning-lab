Sistemas empotrados, ARM y Linux embebido

From "powering on a board" to "writing code on a PC and debugging on the board"

In MICRO, microcontroller programs run directly on bare metal: no operating system, main() is everything. This course enters a different world: an ARM microprocessor (EN) / microprocesador (ES) surrounded by DRAM and an SD card, running full Linux. §1What is an Embedded System? T1.1 · T1.2

Routers, automotive controllers, and GPS navigators are all "computers." How do they differ from a desktop PC?Un sistema empotrado es un sistema informático de uso específico.

An embedded system (EN) / sistema empotrado (ES) is a dedicated computer system. Compared to a general-purpose PC, it has three key differences:

  • Dedicated purpose: Designed for a specific application rather than general-purpose computing.
  • On-board integration: Components that are expansion cards in a PC (graphics, sound, modem...) are mostly integrated directly onto the motherboard.
  • Programmed on another machine: Software is not developed on the device itself, but written and compiled on a host PC before being transferred to the target. This is the origin of cross-development (§4).

This definition is broad, covering diverse products: consumer electronics (DVD players, digital cameras, gaming consoles), communications equipment (mobile phones, routers, satellites), industrial systems (process control, avionics, automotive electronics).

Why Use Linux?

Advantages

  • Component reuse: Kernel, compilers, and libraries are readily available; teams only develop product-specific code.
  • High quality: Linux kernel, GCC, and C libraries have been extensively field-tested.
  • Complete control: Full source code available, enabling modification of any component.
  • Community support.
  • Low cost: No royalties (per-unit licensing fees).

Who Uses It?

  • GPS navigators (TomTom, Garmin)
  • Home routers (Linksys, Netgear)
  • TVs, cameras, DVD players (Sony, Philips)
  • Tablets and smartphones: Android is built on top of the Linux kernel

Microcontroller vs. Microprocessor

Embedded hardware differs substantially from PCs: varied CPU architectures (ARM, MIPS, PowerPC, x86), limited Flash storage and RAM, buses rarely seen on PCs (I2C, SPI, SSP, CAN). Linux imposes minimum hardware requirements:

ItemMinimum Requirements for Linux
CPU32-bit, supported by GCC and Linux kernel
MMURequired by standard Linux; non-MMU CPUs use uClinux
RAMAt least 8 MB to perform useful tasks
StorageAt least 4 MB

A Memory Management Unit (MMU) / unidad de gestión de memoria translates the virtual addresses seen by programs into physical addresses and enforces access permissions. Linux relies on it to provide an isolated address space for each process: if one process corrupts memory, it cannot overwrite other processes or the kernel. Microcontrollers like the MSP430 lack an MMU; all code shares a single physical address space.

Few KB RAM · Microcontroller

bare metal

No OS: code directly manipulates registers, a single main() plus interrupts. Like MSP430 in MICRO. Linux is not meant for MCUs with only a few KB of RAM.

Microcontroller · Needs Multitasking

FreeRTOS and Microkernels

Tiny real-time kernel offering tasks, scheduling, and synchronization, without full process isolation or filesystems.

32-bit MPU + MMU + MB-scale RAM

Linux

Full OS: processes, filesystems, network stack, drivers. The Raspberry Pi in this course belongs to this category. 32-bit non-MMU chips can also run it via uClinux.

Embedded system = dedicated + developed on a host machine. Putting Linux on a device depends on hardware adequacy: 32-bit CPU, MMU (otherwise uClinux), at least 8 MB RAM, and at least 4 MB storage. Smaller chips use bare metal or FreeRTOS.

§2ARM: Architecture, Registers, and Two Instruction Sets T1.3 · T1.4 · T1.5

Why is ARM inside almost every smartphone?ARM (Advanced RISC Machines): arquitectura RISC de 32/64 bits.

ARM (Advanced RISC Machines) is a 32/64-bit RISC architecture designed by ARM Holdings. Its streamlined architecture provides high energy efficiency: by 2005, 98% of mobile phones utilized at least one ARM processor. Note its business model: ARM does not manufacture chips itself; it designs processor cores and licenses the IP to semiconductor vendors (such as the Broadcom SoC used on the Raspberry Pi).

Architecture Characteristics

  1. load/store: Only load and store instructions access memory; all other instructions operate exclusively on internal registers.
  2. Memory alignment: Data must reside at naturally aligned addresses.
  3. 32-bit mode: 16 uniform 32-bit registers; 64-bit mode: 31 64-bit registers.
  4. RISC instruction set with fixed 32-bit instruction width.
  5. 32/64-bit address space.
  6. Most instructions execute in a single clock cycle.
  7. Instructions support conditional execution.
  8. 32-bit barrel shifter.
  9. Dedicated return address register (link register).

16 Registers in 32-bit Mode

  • R0–R12: General-purpose registers.
  • R13 = SP: Stack Pointer.
  • R14 = LR: link register (LR) / registro de enlace. When calling a subroutine with BL, the return address is stored here without pushing to the stack.
  • R15 = PC: Program Counter (32-bit).
  • CPSR: Current Program Status Register, holding condition flags, processor mode, and the execution state ("ARM or Thumb").

The processor operates in several modes: user applications run in User mode; Supervisor (SVC) mode is reserved for the OS kernel. Upon entering SVC mode, CPSR is backed up to SPSR to facilitate restoration upon return. The system call mechanism (§3) relies on this transition.

Two Instruction Sets: ARM and Thumb

ARM processors feature two instruction sets: standard 32-bit ARM instructions, and 16-bit compressed Thumb instructions. Thumb is not executed by a separate core; the processor hardware decompresses 16-bit Thumb instructions into standard ARM instructions on the fly during decode.

Thumb Limitations

  • Only r0–r7 are fully accessible; r8–r15 have limited instruction support.
  • No conditional execution on individual instructions (conditional branches only).
  • Reduced immediate value widths.

Memory Savings

  • Higher code density: Thumb code takes roughly 65% of the memory required by ARM code (saving ~35% Flash/ROM).
  • On narrow 16-bit or 8-bit memory buses, Thumb achieves up to 160% of ARM performance because fewer bus cycles are needed to fetch instructions. On 32-bit wide memory buses, Thumb executes at ~85% of ARM speed due to needing slightly more instructions for complex operations.

Mixing ARM and Thumb: Interworking

In the same system, time-critical routines can be compiled in ARM (32-bit), while memory-sensitive logic uses Thumb (16-bit). Switching between the two is called interworking. The branch instructions BX (branch and exchange) and BLX (branch with link and exchange) perform the switch based on bit 0 of the target address:

  • bit 0 = 1: Switches to Thumb state (instructions executed as 16-bit).
  • bit 0 = 0: Switches to ARM state (instructions executed as 32-bit).

Because ARM instructions are 4-byte aligned (addresses end in 00) and Thumb instructions are 2-byte aligned (addresses end in 0), bit 0 of a valid instruction address is always 0. The hardware strips bit 0 before loading into the PC, using bit 0 purely as the execution state selector.

Using Thumb in Your System

  • Kernel and user space can differ: ARM kernel + Thumb user space works seamlessly; the kernel-user ABI is identical.
  • User space can be entirely Thumb (including libc), or user applications can be Thumb while glibc remains ARM.

Compiler Options

  • Generate Thumb code: -mthumb (in Makefile: CFLAGS += -mthumb).
  • Toolchain interworking support: binutils and gcc configured with --enable-interwork.
  • Generate interworking-safe code: -mthumb-interwork. In uClibc, enable USE_BX in its configuration.

Floating-Point and EABI

Many ARM processors lack a hardware floating-point unit (FPU). When building the kernel and toolchain, a choice must be made on how to handle real arithmetic:

Kernel Emulation · Common in Linux

hard float

User programs issue standard floating-point instructions. Since the chip does not recognize them, an "illegal instruction" exception is raised, caught by an in-kernel emulator (NWFPE, or the faster FastFPE). Slow: every FP instruction incurs exception handling and context-switch overhead. The benefit is that binaries run unchanged when moving to hardware FPU.

User-Space Emulation · Selected at Compile Time

soft float

Add -msoft-float at compile time. The compiler emits calls to software FP runtime library routines (libgcc) rather than FPU instructions.

ARM10, ARM11, and Cortex cores include the VFP vector floating-point coprocessor, providing true hardware floating-point. Under the legacy ABI, hard float and soft float code could not be mixed; an entire executable and all its linked libraries had to choose the same convention.

An Application Binary Interface (ABI) / interfaz binaria de aplicación is the binary-level contract between a program and the OS (or another library). ARM's newer Embedded ABI (EABI) defines file formats, data types, register usage, stack alignment, and calling conventions. Key advantages: permits mixing hard/soft float code, interoperability with third-party compilers, and full Thumb support. Additional changes:

  • Structures no longer have minimum alignment; stack frames are 8-byte aligned (formerly 4); 64-bit integers are 8-byte aligned.
  • System call number is passed in register r7. The old ABI embedded the call number inside the SWI instruction itself, requiring the kernel to read back and decode instruction memory, polluting the data cache.
  • 64-bit function arguments are aligned to even-numbered register pairs.

Support: GCC 4.1.0+ supports EABI; Linux kernel 2.6.16+ introduced CONFIG_AEABI; CONFIG_OABI_COMPAT allows EABI kernels to execute legacy OABI binaries (non-Thumb only). Conversely, an EABI binary cannot run on a legacy OABI kernel. The toolchain prefix arm-linux-gnueabihf- on Raspberry Pi stands for GNU + EABI + hard float (leveraging hardware VFP).

ARM is a licensed RISC architecture: load/store, 16 32-bit registers, conditional execution. Thumb is a 16-bit compressed encoding expanded into ARM by hardware; ARM and Thumb switch via bit 0 of the target address in bx. EABI standardizes calling conventions and places the system call number in r7.

§3Booting Layer by Layer: Anatomy of Embedded Linux T1.6 · T1.7

From power-on to running applications, what sequence of software stages hands off execution?Bootloader → kernel → root filesystem → aplicaciones.

Deploying Linux on an embedded system requires several core software building blocks:

  • bootloader (EN) / cargador de arranque (ES): Performs minimal hardware initialization, loads the kernel into memory, and executes it.
  • Linux kernel / núcleo: Manages memory and processes, containing device drivers, network stacks, and core services.
  • C library (EN) / librería C (ES): The interface between the kernel and user-space applications, providing standard POSIX APIs. Multiple implementations exist: glibc, uClibc, eglibc, dietlibc, newlib, etc.
  • Other user libraries and applications.
  • Additionally, a cross-compilation toolchain (§4) is required—residing on the development PC rather than the target board.

Linux organizes all files into a unified directory tree. A dedicated filesystem, the root filesystem (EN) / sistema de ficheros raíz (ES), is mounted at /. In embedded systems, it holds system libraries, applications, configuration files, and data. Constructing the root filesystem is one of the fundamental tasks in embedded Linux development; the kernel binary is typically stored separately.

What the Bootloader Does

Basic Tasks

  • Basic hardware initialization.
  • Loading a binary program (here, the kernel) into RAM from Flash, network, or non-volatile media.
  • Jumping to and executing it.

Most bootloaders also provide a simple interactive shell for inspecting memory, downloading files, and diagnosing hardware.

Differences: PC vs. Embedded

x86 PC: The motherboard features BIOS/UEFI, executing automatically on reset to initialize basic hardware and load a primary loader from the disk's first sector, which subsequently starts GRUB or systemd-boot.

Embedded: Highly tied to the specific SoC and board architecture. Some boards have NOR Flash where the CPU fetches its very first instruction directly upon reset, hosting the bootloader at that fixed address. Other SoCs have an on-chip ROM bootloader that loads a small secondary loader into internal SRAM from NAND Flash or SD card—this is two-stage booting. Because the bootloader runs immediately after reset, it is even responsible for configuring the DRAM controller.

The most common open-source bootloader is U-Boot (Universal Bootloader, widely used across ARM, PPC, MIPS, x86), alongside RedBoot and uMon. Taking an OMAP development board booting from an SD card as an example, here is the complete staged boot process:

U-Boot Command Line

Once U-Boot starts, its interactive prompt is accessible over the serial console. Common commands: printenv / setenv / saveenv to inspect, modify, and persist environment variables (e.g. ipaddr, serverip, bootargs); tftpboot to download kernel images from a TFTP server on the PC over the network; bootm <address> to boot the kernel from memory. Kernels loaded by U-Boot must first be processed with mkimage to prepend a U-Boot header (Buildroot automates this step). Flashing a new U-Boot requires care: errors can brick the board, requiring JTAG to recover.

User Space and Kernel Space: System Calls

Once booted, the system is strictly divided into two domains. User applications execute in user space (EN) / espacio de usuario (ES), barred from directly manipulating hardware; the kernel executes in kernel space (EN) / espacio del kernel (ES), governing processes, memory, filesystems, devices, and networking. The sole official bridge between them is the system call (EN) / llamada al sistema (ES) interface—the operating system's fundamental API:

The C library and compiled applications interact constantly with the kernel: system calls, constant definitions, and kernel data structures. Consequently, the compiler requires kernel headers (the linux/ and asm/ directories). When an application calls write(), here is what actually takes place under the hood:

Kernel Headers and ABI Compatibility

The ABI between kernel and user space is backward compatible: binaries compiled with older kernel headers run reliably on newer kernels (without accessing newer features); binaries compiled with newer headers can often run on older kernels provided they don't invoke newly introduced features. Headers are exported from kernel source via make headers_install.

Boot sequence: bootloader (possibly two-stage) → kernel → mount rootfs → /sbin/init → applications. User-space applications access kernel services exclusively through system calls: the C library loads the call number into r7 and arguments into r0..., invokes SWI to enter Supervisor mode, and the kernel dispatches via the call table, returning results in r0.

§4Cross-Development: Programming for ARM on a PC T1.8

Why won't a binary compiled by gcc on a PC run when copied to an ARM board?Toolchain nativa vs. toolchain cruzada.

Development tools built into a Linux workstation constitute a native toolchain: they emit binaries targeted to the very machine running them. Embedded devices generally cannot—and should not—run native toolchains: target memory and storage are tightly constrained, and execution speed is far slower than a workstation. Running tools on one platform (the host) to generate binaries for another platform (the target) is called cross-development (EN) / desarrollo cruzado (ES).

What Is Inside a Cross-Toolchain?

These components originate from GNU (a Unix-compatible free software system initiated in 1984):

ComponentRole
binutilsGenerates and processes target-architecture binaries: assembler (as), linker (ld), static archiver (ar/ ranlib), binary inspection (objdump / readelf / size / nm / strings), and strip to remove debug symbols and reduce size.
Kernel headersAlso called system headers: definitions for system calls, constants, and kernel structures (§3).
GCCThe compiler collection (C, C++, Ada, Fortran, etc.), capable of emitting code for ARM, AVR, MIPS, PowerPC, x86, and many other architectures.
C/C++ standard libraryglibc, uClibc, etc. Must be configured alongside the toolchain so GCC generates conforming runtime code.
GDB (optional)Debugger (gdb / gdbserver).

Toolchain executables use a target prefix indicating the target architecture: arm-linux-gcc, arm-linux-objdump, or arm-linux-gnueabihf-gcc for 32-bit Raspberry Pi. The host's native gcc remains completely separate; both toolchains coexist harmoniously.

Build, Host, Target: Four Combinations

Three machines must be distinguished when discussing toolchains: build (where the toolchain is built); host (where the toolchain executes); and target (where the resulting compiled program runs). Their combinations yield four configurations:

Typebuild · host · targetDescription
nativa (Native)A · A · AStandard PC and workstation setup: all stages on the same machine.
cruzada (Cross)A · A · BBuilt and executed on one machine to produce code for a different architecture. Standard for embedded microprocessors.
cruzada-nativa (Cross-Native)A · B · BBuilt on machine A to run natively on machine B, compiling code for B.
cruzada-cruzada (Canadian Cross)A · B · CBuilt on A to run on B, emitting code targeted for C.

How Host and Target Connect

standalone

Standalone

Target has everything on board: bootloader, kernel, filesystem, and native compiler. No host required.

linked

Wired Connection

Host is the development workstation, connected to target via serial cable or Ethernet RJ45. Fast file transfers and interactive debugging.

almacenamiento removible

Removable Storage

Target only runs a bootloader; the host writes the secondary bootloader, kernel, and rootfs onto an SD card or USB drive, which is then inserted into the target.

A Development Cycle: "Edit — Build — Transfer — Debug"

Connecting these tools establishes the daily development workflow. In this course, the host is a PC equipped with the cross-toolchain and Eclipse CDT, while the target is a Raspberry Pi running Linux, interconnected via Ethernet:

Configuring CMake for Cross-Compilation

During cross-compilation, CMake must be informed of the target toolchain, ensuring it searches for headers and libraries solely inside the sysroot rather than using the PC's host libraries:

SET(CMAKE_SYSTEM_NAME Linux)SET(CMAKE_C_COMPILER   arm-linux-gnueabihf-gcc)SET(CMAKE_FIND_ROOT_PATH $ENV{HOME}/raspberry/rootfs)SET(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER) # Programs: use host toolsSET(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)  # Libraries: search exclusively in sysrootSET(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)  # Headers: search exclusively in sysroot

The sysroot is synchronized from the target via: rsync -rl --delete-after --safe-links pi@<board-IP>:/{lib,usr} /path/to/sysroot. Symbolic links are adjusted to point relatively inside the sysroot.

Shared Folders: NFS and sshfs

  • NFS (Network File System): On a Linux host, export a directory (e.g. /exportado) in /etc/exports, start the NFS service, and run exportfs -ra; on the board, add an entry to /etc/fstab: host_IP:/exportado /exportado nfs ..., then mount -a.
  • sshfs: Mounts a remote directory over SSH. On Windows, sshfs-win (leveraging WinFsp) maps the board's directory to a local drive letter.
  • On Windows, the cross-toolchain uses SysGCC for Raspberry Pi; Eclipse is unpacked into the same root directory.

Cross-toolchain = binutils + kernel headers + GCC + C library (+ GDB), running on host PC to generate code for target ARM. Sysroot provides target headers and libraries on the PC. Remote debugging uses gdbserver over Ethernet.

§5Buildroot: Building an Entire System with a Single Command T1.9

Toolchain, kernel, root filesystem, hundreds of software packages—how long would it take to cross-compile them all by hand?Buildroot: un conjunto de makefiles que automatizan la construcción.

Knowing what components are needed, how do you actually build an embedded Linux system? There are three paths:

distribución

Pre-built Distribution

Distributions like Debian offer pre-compiled binary packages for ARM, MIPS, and PowerPC, getting you up and running quickly. However, configuration options (soft/hard float, EABI/OABI...) are fixed by maintainers and may not match your needs; you lack control over system integration (boot, dependencies); and applying patches requires rebuilding packages without automation.

a mano

Entirely by Hand

Manually compile, configure, and install every component. Maximum flexibility, but you must resolve dependencies yourself, cross-compilation is tedious, and there is no automated mechanism to rebuild the entire system after making changes or fixes.

sistema de construcción

Build System

Automatically downloads, configures, compiles, and installs everything; provides reproducible rebuilds; simplifies applying patches and adding custom packages. It understands open-source software packages and has already resolved cross-compilation pitfalls and dependencies.

Buildroot is such a build system: a collection of Makefiles that automates "building a cross-toolchain + building an embedded Linux system." Originally created for uClibc, it was revitalized in January 2009 under Peter Korsgaard, releasing new versions every 3 months. Similar tools include PTXdist (Pengutronix) and LTIB (Freescale); alternative approaches include OpenEmbedded/Yocto (more flexible and complex) and Gentoo Embedded.

Configuration: make menuconfig

Buildroot uses the kernel's Kconfig system, presenting an interactive menuconfig text menu and saving choices in .config:

MenuAvailable Options
TargetArchitecture (arm, mips, powerpc, i386, x86_64...); Variant (ARM7TDMI, ARM920T, Xscale, Cortex-A8...); ABI (EABI or OABI on ARM)
Build optionsTools, directory paths, documentation, debug symbols, optimization levels
ToolchainBuild internally (uClibc) or use an external toolchain; kernel header version, C library version, GCC version and languages (C++, Fortran...), GDB (target gdbserver, target gdb, host cross-gdb), IPv6/largefile/locale
PackagesHundreds of packages with automatic dependency resolution: busybox, bash, openssh, dropbear, lighttpd, tcpdump, iptables, sqlite, i2c-tools, Qt Embedded, python...
Filesystem · bootloader · kernelRootfs formats (ext2, jffs2, ubifs, squashfs, cramfs, tar, cpio, initramfs...); U-Boot; kernel version, configuration, patches, and image formats (uImage, zImage, bzImage)

From Scratch to a Bootable SD Card

Taking a Cortex-A8 IGEP development board as an example, the complete workflow is:

  1. Configure Buildroot: Extract source, run make menuconfig: select ARM architecture, Cortex-A8 variant, EABI; enable IPv6, wide characters, large files, RPC; build target gdbserver and host GDB; enable g++; select tar rootfs (gzip-compressed); select packages.
  2. make. Produces two primary outputs: root filesystem (applications, shared libraries, configuration files) in output/images; and cross-toolchain (compiler, libraries, headers) with binaries in output/staging/usr/bin.
  3. Build the kernel with the new toolchain: Add toolchain directory to PATH, verify with arm-linux-gcc -v; set ARCH=arm and CROSS_COMPILE=arm-linux-, load vendor default config make igep0020_defconfig (optionally customize via make menuconfig), then run make uImage, make modules, and make modules_install. Use -j4 for multi-core parallel builds.
  4. Build bootloader: X-loader and U-Boot, similarly compiled using CROSS_COMPILE=arm-linux-.
  5. Prepare SD card: Identify device name with dmesg (e.g. /dev/sdb), use fdisk to create two partitions: small first partition formatted as FAT32 and marked bootable for bootloader and kernel; second partition using remaining space formatted as ext3 for root filesystem. Format via mkfs.vfat and mkfs.ext3, then mount.
  6. Copy files: In boot partition, place MLO first (order matters: must reside in initial sectors), then u-boot.bin, uImage, and the boot script generated from boot.cmd via mkimage; in root partition, extract rootfs.tar.gz, copy kernel modules, and edit etc/inittab to ensure a serial login terminal (getty).
  7. Power on: Observe X-loader, U-Boot, kernel, and applications booting in succession (§3 Scene 2). Initial boot may be slower as programs run first-time initialization.

If the pre-installed U-Boot in the board's NAND Flash is usable, simplify: omit X-loader and U-Boot on the SD card, placing only the kernel image and boot configuration for the on-board U-Boot to load.

Buildroot = a collection of Makefiles: make menuconfig selects architecture, ABI, toolchain, packages, filesystem, and kernel, saved to .config; running make outputs the cross-toolchain and root filesystem image.

§6Raspberry Pi: The Course Development Environment T1.10

Board connected via Ethernet: PuTTY connects fine, but Eclipse reports a timeout—what is the issue?Configuración de la Raspberry Pi para desarrollo cruzado.

The Raspberry Pi is a small computer built on an ARM microprocessor: featuring programmable digital GPIOs and instrumentation buses for sensors, it reads physical data, processes it, and responds; connects to IP networks; and runs Linux. In C/C++, this course utilizes the wiringPi library, which mimics Arduino syntax for straightforward code migration.

Required Components

Hardware

  • Raspberry Pi 3 or 4
  • MicroSD card (at least 8 GB) and SD adapter
  • RJ45 Ethernet cable
  • PC with an available Ethernet port, or a router with a spare port

Software (Windows Host)

  • Cross-development system: SysGCC Raspberry Pi toolchain
  • Raspberry Pi Imager (OS image flashing)
  • PuTTY (SSH terminal), Notepad++
  • Eclipse IDE for C/C++ Developers (CDT), unpacked into the SysGCC directory

Setup Steps

  1. Use Raspberry Pi Imager to flash Raspberry Pi OS onto the SD card. Enable SSH in advanced options, setting hostname and user credentials (course convention uses hostname raspberrypi.local). Without SSH enabled, remote login is impossible.
  2. Connect the board directly to the PC with an Ethernet cable; insert the SD card and power on.
  3. On Windows, configure Internet Connection Sharing (ICS) on the Wi-Fi adapter: Network Settings → Change Adapter Options → Wi-Fi Properties → "Sharing" tab, check "Allow other network users to connect through this computer's Internet connection". Note: share the Wi-Fi interface providing Internet access, not the Ethernet port connected to the board. Once shared, Windows assigns 192.168.137.1 to the Ethernet port and leases 192.168.137.x to the board via DHCP.
  4. Connect via PuTTY to raspberrypi.local using configured credentials. Follow course instructions to enable the root account and permit SSH root login (editing /etc/ssh/sshd_config).
  5. Run ifconfig to check the board's IPv4 address; run sudo raspi-config to enable SPI and I2C buses; install wiringPi library headers and binaries.
  6. Configure the cross-toolchain and remote connection in Eclipse (§4 workflow).

Connection Troubleshooting: IPv6 Only, No IPv4

Why GPIO Toggling is Slower on Linux

When programs call sleep() or usleep(), the process yields the CPU to the operating system; its resumption depends on the scheduler's time slice. Pin toggling frequency via sleep is therefore constrained by the kernel scheduler. This fundamental difference between Linux and bare metal on microcontrollers drives the topics covered in upcoming chapters (multithreading, POSIX timers, real-time signals).

Two Solutions

  1. Connect the board to a home router, allowing the router to assign an IPv4 address.
  2. Configure a fallback static IPv4 address on the board: use 192.168.137.2/24 with gateway 192.168.137.1 (the shared Windows Ethernet port) if DHCP fails.
    • Prior to Bookworm: add a static profile with fallback at the end of /etc/dhcpcd.conf, then reboot.
    • From Bookworm onward: create two connections using nmcli (DHCP priority 1, static IP priority 0), testing DHCP first and falling back to static IP. Toggle Windows connection sharing off and on once.

With a static IP, raspberrypi.local mDNS may become unreachable; connect directly to 192.168.137.2. If the board cannot access the Internet through Windows, add nameserver 8.8.8.8 to /etc/resolv.conf.

Determining the Board's IP: arp -a

In Windows Command Prompt, run arp -a and inspect entries beneath the 192.168.137.1 interface:

Interfaz: 192.168.137.1 --- 0x11  192.168.137.128   b8-27-eb-2d-bf-a5  192.168.137.205   b8-27-eb-2d-bf-a5  192.168.137.255   ff-ff-ff-ff-ff-ff  # Broadcast

Two IP addresses mapped to the same MAC indicates the board was power-cycled, receiving two consecutive leases from Windows. Run ping to determine which is currently active.

Three Pin Numbering Schemes

The Raspberry Pi 40-pin header features three distinct numbering systems for the same physical pin:

  • Header pin (Physical Numbering): Board position, 1–40, odd on one row, even on the other.
  • BCM GPIO: Broadcom SoC internal GPIO numbering (e.g. GPIO17).
  • wiringPi Numbering: wiringPi library's custom scheme (0, 1, 2...).

Click any pin on the header below to view its three numbering designations and corresponding pinMode() syntax across initialization modes:

#include <wiringPi.h> wiringPiSetup();          // wiringPi numberingpinMode(4, OUTPUT);        // wiringPi 4 = BCM GPIO23 = header 16 // Or:wiringPiSetupPhys();      // Physical header pin numberingpinMode(16, OUTPUT);       // Same physical pindigitalWrite(16, HIGH);   // Output high; read input using digitalRead()

The initialization function determines how pin numbers are interpreted across all subsequent library calls. Selecting the wrong numbering mode compiles without warnings but drives the wrong physical pin.

Other Peripherals

I2C · SPI

Two Buses

I2C requires only two lines: data SDA (header 3) and clock SCL (header 5). On-board 1.8 kΩ pull-up resistors are already present, making these pins unsuitable as general-purpose GPIOs. Enable via raspi-config, then inspect bus and device addresses with i2cdetect. SPI uses three shared lines (MOSI, MISO, SCLK) plus a chip-enable line per device (CE0、CE1).

entradas analógicas

No Analog Inputs

The Raspberry Pi lacks an integrated ADC. To sample analog signals, connect an external SPI or I2C converter, such as the 8-channel 10-bit MCP3008 (supported natively by wiringPi) or the 16-bit ADS1115.

PWM

"Analog Output"

Outputs a 0–3.3 V square wave; varying the pulse width (duty cycle) modulates the average voltage. pwmWrite(pin, value) maps values 0–1023 to 0–100% duty cycle. Only two pins offer hardware PWM; software PWM on other pins operates at substantially lower frequencies.

f_PWM = 19.2 MHz ÷ divisor · default divisor = 32 → 600 kHz · adjust via pwmSetClock(divisor)
Why GPIO Toggling is Slower on Linux

When programs call sleep() or usleep(), the process yields the CPU to the operating system; its resumption depends on the scheduler's time slice. Pin toggling frequency via sleep is therefore constrained by the kernel scheduler. This fundamental difference between Linux and bare metal on microcontrollers drives the topics covered in upcoming chapters (multithreading, POSIX timers, real-time signals).

Enable SSH in the OS image; Ethernet direct connection shares the Wi-Fi interface, placing the board at 192.168.137.x. If PuTTY connects but Eclipse times out, the board lacks an IPv4 address—resolve via router or static IP fallback. Always verify pin numbering conventions: wiringPiSetup() expects wiringPi numbers, whereas wiringPiSetupPhys() uses physical header pin numbers.

Self-Test 12 Questions

Self-test questions based on this chapter. Only one attempt per question; explanations appear after answering.

01 Which of the following hardware configurations is NOT suitable for running standard Linux?

D. Standard Linux requires at least a 32-bit CPU, 8 MB RAM, and 4 MB storage. Microcontrollers with only tens of KB of RAM run bare metal or FreeRTOS (§1).

02 ARM is a load/store architecture, which means?

B. Arithmetic and logic instructions only touch internal registers; memory access is restricted to dedicated load/store instructions (§2).

03 Regarding the Thumb instruction set, which statement is INCORRECT?

C. Accessing coprocessors and status registers cannot be done directly in Thumb; code must switch back to ARM state when needed (§2).

04 Thumb code executes bx r3, where r3 = 0x00009001. What does the processor do next?

A. Bit 0 = 1 specifies entering/remaining in Thumb state; bit 0 itself is stripped before loading into PC, resuming execution at 0x9000 (§2 Scene 1).

05 On an ARM board without an FPU where the kernel uses hard float emulation, what happens when a floating-point instruction is executed?

D. Option A describes soft float (-msoft-float). Hard float emulation traps into the kernel via an illegal instruction exception, incurring heavy context-switching overhead (§2).

06 Under ARM EABI, where is the system call number passed?

B. Option A was the legacy OABI convention, which required the kernel to read instruction memory back as data. Register r0 holds the first argument and return value (§2, §3).

07 When the SWI instruction executes, which of the following does NOT happen?

C. errno is set in user space by the C library wrapper after the system call returns, and only when an error occurs (§3 Scene 3).

08 What is the correct boot sequence for embedded Linux booting from an SD card?

A. Each stage only knows how to locate and load the subsequent stage. init resides on rootfs, so the rootfs must be mounted first (§3 Scene 2).

09 A toolchain is built on an x86 PC and executes on that same PC to generate ARM binaries. Which toolchain configuration is this?

C. build = host = x86, target = ARM. This is the standard setup for embedded microprocessor development (§4).

10 Why synchronize /lib and /usr from the Raspberry Pi to a directory on the PC?

B. This directory forms the sysroot; linking against the host's /usr/lib would pull in x86 libraries, which are incompatible with ARM (§4).

11 After executing make in Buildroot, what is the primary deliverable produced?

D. .config is created by make menuconfig. Running make builds the cross-toolchain (output/staging) and the rootfs image (output/images) (§5).

12 Directly connected Raspberry Pi: PuTTY connects via SSH, but Eclipse connection times out. What is the most likely cause and solution?

A. If SSH were disabled, PuTTY could not connect either. PuTTY connects over IPv6, whereas Eclipse requires an IPv4 address (§6).
