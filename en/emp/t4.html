Comunicaciones: sockets

Sockets: Enabling communication between embedded boards and remote network endpoints

10 Key Points Approx. 25 min read

Once a Linux-powered Raspberry Pi connects to Ethernet or Wi-Fi, how do user-space programs exchange data over the network? Almost all modern operating systems provide the same answer: socket (EN) / conector (ES). A socket behaves like a file descriptor: you can read, write, and close it; behind the scenes, the kernel handles packetization, addressing, retransmission, and packet ordering. This chapter explores how data is encapsulated through network layers, dissects TCP server, TCP client, and UDP system calls step by step, and finishes with the structure of an HTTP message.

§1Layering & Addressing T4.1 · T4.2

The program writes four bytes "hola", yet a packet of dozens of bytes travels across the wire. What is all the extra data?Cada capa añade su propia cabecera.

Network software is organized into layers. The theoretical OSI reference model defines 7 layers (Físico, Enlace, Red, Transporte, Sesión, Presentación, Aplicación); practical TCP/IP stacks collapse these into 4 layers, merging OSI layers 5–7 into the "Application Layer" and layers 1–2 into the "Link Layer". Each layer communicates strictly with its adjacent layers, prepending its own header (EN) / cabecera (ES) to outbound data—a process known as encapsulation (EN) / encapsulado (ES).

The 5 Elements of Communication

Any communication channel between two network programs is uniquely identified by a 5-tuple:

ProtocolSource IPSource PortDest IPDest Port
tcp192.168.0.11200192.168.0.21500

IP address (EN) / dirección IP (ES): Identifies a network device (specifically, a network interface on a host): IPv4 is 32 bits, formatted in dot-decimal notation such as 10.12.110.57; IPv6 is 128 bits, written like 2001:db8:63b3:1::3490. port (EN) / puerto (ES): A 16-bit number (0–65535) identifying a specific process or service on that host. For example, HTTP servers conventionally listen on port 80.

Two Ways to Acquire a Port

  • Fixed Port: The application selects an explicit port number and binds to it via bind. Servers must do this; otherwise, clients have no known address to target. Take care not to collide with already bound ports.
  • System-Assigned Port: Setting the port to 0 during bind, or omitting bind entirely, prompts the kernel to dynamically allocate a free port from the ephemeral ports (EN) / puertos dinámicos (ES) pool. Clients typically follow this pattern.

Port Number Ranges

  • Ports below 1024 are reserved for well-known services (ftp, ssh, http…); binding them on Linux requires root privileges (superuser).
  • The range for ephemeral ports is determined by the OS; on Linux, inspect /proc/sys/net/ipv4/ip_local_port_range.
  • For custom services, select an unused port above 1024. Examples in this chapter use 5005 (TCP), 6006 (UDP), and 7070 (HTTP).
Client vs. Server

server (EN) / servidor (ES): Starts first and listens/waits on a well-known port; client (EN) / cliente (ES): Actively initiates communication. In TCP, the call sequence differs substantially between the two roles (§4, §5); in UDP, system calls on both sides are nearly identical, with "client" referring simply to the party that sends the initial message (§6).

§2What is a Socket T4.3

Why can a simple integer represent an active network connection?socket() devuelve un descriptor, como un fichero.

In Linux, sockets—like regular files—are referenced via a file descriptor (EN) / descriptor (ES): a small non-negative integer representing an index in the process open file table. Consequently, standard file calls like read, write, and close work directly on sockets. A socket is instantiated using a single system call:

#include <sys/types.h>#include <sys/socket.h> int socket(int domain, int type, int protocol);   // Success: descriptor ≥ 0; Failure: -1 and sets errno
ParameterCommon ValuesMeaning
domainAF_INET · AF_INET6 · AF_UNIX (= AF_LOCAL)Address family: IPv4, IPv6, or local IPC on the same host. Determines which address struct is used.
typeSOCK_STREAM · SOCK_DGRAMCommunication semantics: connection-oriented byte stream (circuito virtual), or connectionless datagram (datagrama).
protocol0Passing 0 selects the default protocol: STREAM → TCP, DGRAM → UDP. Can also be explicit, e.g. IPPROTO_SCTP.

SOCK_STREAM · TCP

connection-oriented (EN) / orientado a conexión (ES): Requires establishing a connection prior to data transfer. Retransmission, sequencing, and deduplication are handled transparently by the OS; the application interacts with a reliable, in-order byte stream. The trade-off is protocol-level control overhead.

SOCK_DGRAM · UDP

connectionless (EN) / no orientado a conexión (ES): Data is dispatched immediately without prior handshake. No retransmission, no sequencing; reliability, if required, must be implemented by the application. Each transmission is an independent datagrama.

int s = socket(AF_INET, SOCK_STREAM, 0);   // IPv4 + TCPif (s == -1) {    perror("socket");                     // Print error cause    exit(EXIT_FAILURE);}

PF_INET (Protocol Family) and AF_INET (Address Family) share identical numeric values on Linux; many codebases pass PF_ to socket() and AF_ to address structs. Either form works reliably.

Do Not Overlook AF_UNIX

AF_UNIX sockets communicate exclusively between processes on the same host, using a filesystem path as the address (sun_path in struct sockaddr_un). Frequently overlooked, modern system services increasingly adopt AF_UNIX over legacy IPC mechanisms: the API is identical to network sockets, differing only in the address family.

§3Addresses & Byte Order T4.4

You assigned port 5005 in code, but the remote client waits on port 36115. Why?¡¡¡Atención!!! formato red y formato máquina.

All address-handling system calls (bind, connect, accept, sendto, recvfrom) accept a generic address pointer struct sockaddr *, inspecting its first field (the address family) to interpret remaining bytes. The concrete structure for IPv4 is sockaddr_in, cast to sockaddr * when passed as an argument:

struct sockaddr {                 // Generic: used purely for pointer casting    sa_family_t sa_family;         // AF_xxx    char        sa_data[14];}; struct sockaddr_in {              // IPv4, defined in <netinet/in.h>    sa_family_t    sin_family;     // AF_INET    in_port_t      sin_port;       // Port, network byte order    struct in_addr sin_addr;       // { uint32_t s_addr; } IP, network byte order    unsigned char  sin_zero[8];    // Zero padding to match sizeof(struct sockaddr)};

IPv6 uses sockaddr_in6 (sin6_family = AF_INET6, 16-byte address in in6_addr, plus flowinfo and scope_id). When generic storage for both address families is needed, use struct sockaddr_storage.

formato red · formato máquina

Multi-byte integers can be stored in memory in two ways: big endian (most significant byte at the lowest address) and little endian (least significant byte at the lowest address). Network standards mandate that port numbers and IP addresses in packet headers must always use big-endian format, designated as network byte order (formato red). Conversely, Intel x86 and Raspberry Pi ARM CPUs operate natively in little-endian format (formato máquina). Examine how port 5005 is organized in memory:

Function (<arpa/inet.h>)DirectionCommon Usage
uint16_t htons(uint16_t)Host → Network, 16-bitPort: sin_port = htons(5005)
uint32_t htonl(uint32_t)Host → Network, 32-bitIPv4 address constant: sin_addr.s_addr = htonl(INADDR_ANY)
uint16_t ntohs(uint16_t)Network → Host, 16-bitPrinting received port: ntohs(cli.sin_port)
uint32_t ntohl(uint32_t)Network → Host, 32-bitComparing or calculating received IP addresses as integers

Text Addresses ↔ Binary Addresses

Humans write addresses like "192.168.1.20", whereas sin_addr expects 4 bytes in network byte order. Conversions are performed with inet_pton (presentation to network) and its reverse inet_ntop. Both support IPv4 and IPv6, returning values via pointers:

struct sockaddr_in dst;memset(&dst, 0, sizeof dst);                  // Clears sin_zero paddingdst.sin_family = AF_INET;dst.sin_port   = htons(5005);if (inet_pton(AF_INET, \"192.168.1.20\", &dst.sin_addr) != 1)    /* 1 = Success; 0 = Invalid IP string; -1 = Unsupported address family */; char txt[INET_ADDRSTRLEN];                     // 16 bytes, enough for \"255.255.255.255\"inet_ntop(AF_INET, &dst.sin_addr, txt, sizeof txt);printf(\"%s:%u\\n\", txt, ntohs(dst.sin_port));   // 192.168.1.20:5005
  • Legacy inet_addr("192.168.1.20") returns a 32-bit network-ordered integer, while inet_ntoa() performs the reverse. They only support IPv4, and inet_addr's failure return code collides with "255.255.255.255"; modern code uses pton/ntop.
  • INADDR_ANY (value 0) represents "any local interface": a server bound to INADDR_ANY accepts incoming traffic on any network interface matching the target port.
  • getaddrinfo("www.example.com", "http", &hints, &res) resolves hostnames and service names into a linked list of socket-ready addresses (IPv4 and IPv6), freed via freeaddrinfo; its inverse is getnameinfo.
Clarification · Common Documentation Confusion

Some literature states that "after inet_addr(\"192.168.0.1\"), s_addr contains 0xC0A80001": this reflects reading the value in network byte order (left-to-right). On a little-endian Raspberry Pi, printing directly via printf(\"%x\", s_addr) displays 0x0100A8C0; only ntohl(s_addr) yields 0xC0A80001.

§4TCP Server T4.5 · T4.6

A server is servicing a client on port 5005. When a second client connects, will it succeed?socket → bind → listen → accept → read / write → close.

A connection-oriented server proceeds through four preparatory stages, each serving a distinct purpose: socket creates the communications endpoint (abrir canal), bind assigns the local address (publicar dirección), listen expresses willingness to accept connections, and accept dequeues an established connection. Below, server and client timelines illustrate when each call unblocks and what the kernel accomplishes behind the scenes:

System Call Parameters

CallPurpose & Key Details
bind(fd, addr, len)Binds the socket to a local IP address and port. Sockets are initially created with an address family but no bound endpoint. Servers must bind to maintain a known port; connection-oriented clients do not require it.
listen(fd, backlog)Used exclusively with TCP. Enables the incoming connection queue; backlog defines the upper limit of established connections awaiting accept, typically 5–10 (or 1 for single-client daemons).
accept(fd, addr, &len)Dequeues the first connection from the backlog, returning a new file descriptor; blocks if the queue is empty. addr retrieves the client's address; len is a value-result parameter: initialized to sizeof(struct), returning the actual address length. Pass NULL if client address inspection is unneeded. Returns -1 on failure.
read / writePerforms I/O on the newly returned descriptor from accept; see §5.
close(fd)Terminates the connection and releases kernel resources; see §7.

These calls assemble into an iterative server: handling one client sequentially before calling accept for the next. This implementation capitalizes text and returns it:

int main(void) {    int lfd = socket(AF_INET, SOCK_STREAM, 0);    if (lfd < 0) { perror("socket"); return 1; }    int on = 1;    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);   // See §7     struct sockaddr_in me;    memset(&me, 0, sizeof me);    me.sin_family      = AF_INET;    me.sin_addr.s_addr = htonl(INADDR_ANY);   // Any local interface    me.sin_port        = htons(5005);    if (bind(lfd, (struct sockaddr *)&me, sizeof me) < 0) { perror("bind"); return 1; }    if (listen(lfd, 5) < 0) { perror("listen"); return 1; }     for (;;) {        struct sockaddr_in peer;        socklen_t plen = sizeof peer;            // In: buffer capacity        int cfd = accept(lfd, (struct sockaddr *)&peer, &plen);   // Blocks        if (cfd < 0) { perror("accept"); continue; }         char buf[128];        ssize_t n;        while ((n = read(cfd, buf, sizeof buf)) > 0) {   // 0 = Client closed, -1 = Error            for (ssize_t i = 0; i < n; i++) buf[i] = toupper((unsigned char)buf[i]);            write_all(cfd, buf, n);                // Helper from §5        }        close(cfd);                                // Closes client; lfd remains listening    }}

Header dependencies: <sys/socket.h>, <netinet/in.h>, <arpa/inet.h>, <unistd.h>, <string.h>, <ctype.h>, <stdio.h>. While servicing a client, subsequent connection handshakes succeed and wait in the backlog queue; concurrent client handling is covered in §7.

Clarification · Port Assignment of the New Socket

Some texts state that accept allocates a new ephemeral port for the returned socket to free the listening port. In reality, the local port of the accepted socket remains 5005: the kernel disambiguates connections using the full 4-tuple (local IP, local port, remote IP, remote port). Thus, a listening socket and multiple connected sockets can coexist on port 5005 simultaneously. The key architectural reality remains: accept returns a distinct new socket, leaving the listening socket available.

§5TCP Client & Byte Stream T4.7

If the client writes twice, will the server definitely read twice?TCP es un flujo de bytes: no conserva los límites de los mensajes.

A TCP client requires only two calls: socket, followed by connect targeting the server's address. connect blocks until connection establishment succeeds (returning 0) or fails (returning -1, e.g. Connection refused when no process is listening). No bind is necessary: the kernel assigns an ephemeral port during connect and maintains it for the connection's lifetime.

int fd = socket(AF_INET, SOCK_STREAM, 0);struct sockaddr_in srv;memset(&srv, 0, sizeof srv);srv.sin_family = AF_INET;srv.sin_port   = htons(5005);inet_pton(AF_INET, "192.168.1.20", &srv.sin_addr);if (connect(fd, (struct sockaddr *)&srv, sizeof srv) < 0) {   // Blocks until handshake completes    perror("connect");                       // e.g. Connection refused    return 1;}write_all(fd, "hola\n", 5);char buf[64];ssize_t n = read(fd, buf, sizeof buf);close(fd);

Three Return Values of read and recv

> 0

Read n Bytes

n may be smaller than requested: represents only bytes currently buffered in the kernel.

= 0

Peer Closed Connection

End of stream (EOF). No further data will arrive; close your local descriptor.

= -1

Error Occurred

Inspect errno; output diagnostics via perror().

recv(fd, buf, len, flags) and send(fd, buf, len, flags) are socket-specific variants. When flags is 0, their behavior matches read/write. Useful flags include: MSG_PEEK (peeks at data without dequeuing), MSG_OOB (out-of-band data), and MSG_NOSIGNAL (see §7). send/write returns the count of bytes accepted by the kernel, which may also be less than requested.

TCP delivers a continuous byte stream (EN) / flujo de bytes (ES): it guarantees reliable, sequenced, deduplicated arrival, but does not preserve individual write boundaries:

Writing requires identical diligence: write may perform a partial write (especially under heavy loads or slow receivers), requiring an explicit loop:

/* Writes all len bytes to fd; returns 0 on success, -1 on error */int write_all(int fd, const void *p, size_t len) {    const char *c = p;    while (len > 0) {        ssize_t n = write(fd, c, len);        if (n < 0) {            if (errno == EINTR) continue;   // Interrupted by signal: retry            return -1;        }        c += n; len -= n;                   // Partial write: advance pointer and continue    }    return 0;}

TCP guarantees reliable, ordered bytes, not messages. Both reads and writes may complete partially; delineating message start and end boundaries is strictly an application-layer responsibility.

§6UDP: One Datagram at a Time T4.8

Without a connection, how does the receiver know who sent the packet and where to reply?sendto() y recvfrom() llevan la dirección en cada llamada.

UDP discards listen, accept, and connect: both peers create endpoints via socket(AF_INET, SOCK_DGRAM, 0). The receiving peer binds to a known port with bind and immediately exchanges data. Lacking a persistent connection, every outbound call must specify the target address, and every inbound call returns the sender's address:

ssize_t sendto(int fd, const void *buf, size_t len, int flags,               const struct sockaddr *to, socklen_t tolen);      // Send to destination 'to'ssize_t recvfrom(int fd, void *buf, size_t len, int flags,                 struct sockaddr *from, socklen_t *fromlen);      // 'from' captures sender address

fromlen is a value-result parameter, identical to accept's length argument. Passing from directly back into sendto allows immediate replies. Both functions return bytes transferred, or -1 on error. Because UDP is connectionless, a return value of 0 does not denote disconnection—it merely indicates reception of a 0-byte datagram.

A typical UDP receiver: listening on port 6006, printing message content and sender address:

int fd = socket(AF_INET, SOCK_DGRAM, 0);struct sockaddr_in me;memset(&me, 0, sizeof me);me.sin_family = AF_INET;me.sin_addr.s_addr = htonl(INADDR_ANY);me.sin_port = htons(6006);bind(fd, (struct sockaddr *)&me, sizeof me);         // Receiving requires a known port for (;;) {    char buf[1500];                                   // Buffer ≥ maximum datagram size    struct sockaddr_in from;    socklen_t flen = sizeof from;    ssize_t n = recvfrom(fd, buf, sizeof buf, 0, (struct sockaddr *)&from, &flen);    if (n < 0) { perror("recvfrom"); continue; }    char ip[INET_ADDRSTRLEN];    inet_ntop(AF_INET, &from.sin_addr, ip, sizeof ip);    printf("%zd bytes de %s:%u: %.*s\n", n, ip, ntohs(from.sin_port), (int)n, buf);}

Send-only UDP clients do not require bind: when calling sendto(fd, msg, len, 0, (struct sockaddr *)&dst, sizeof dst), the kernel assigns an ephemeral port on the first transmit, visible in the receiver's from struct. UDP sockets can optionally invoke connect: this performs no network handshake, simply recording a default destination address so subsequent calls can use standard send/recv.

TCP vs. UDP: Architectural Comparison

FeatureTCP · SOCK_STREAMUDP · SOCK_DGRAM
Connection SetupThree-way handshake requiredConnectionless; transmits immediately
ReliabilityRetransmits lost data; in-order, deduplicatedPackets may be dropped, duplicated, or reordered
FramingContinuous byte stream; no message boundariesDiscrete datagrams; overflow discarded
I/O Callsread/write, recv/send (peer known via connection)sendto/recvfrom (or connect to record peer)
Control LevelManaged by kernel protocol engineApplication retains control over delivery & drops
SuitabilityLoss-intolerant: files, web pages, commandsReal-time control & streaming: late data is useless

TCP is standard for general networking, but unsuitable for strict real-time telemetry: when a packet drops, subsequent packets stall until retransmission completes (head-of-line blocking), causing unpredictable latency spikes outside application control. UDP returns control to the developer: the application observes exactly when packets arrive, identifying drops immediately and deciding whether to wait, retransmit, or discard stale data. When lower-level raw frame manipulation is required, Linux provides raw sockets to construct IP packets directly.

§7Blocking, Multiplexing & Closing T4.9

The server is blocked in accept waiting for clients, but must simultaneously handle other tasks. What can you do?¿Necesitamos multitarea? select como alternativa.

Socket calls are blocking (EN) / bloqueante (ES) by default: when prerequisites are unmet, execution suspends, halting the calling thread until an event occurs.

System CallBlocking Condition
acceptWaits until an established connection enters the backlog queue
connect (TCP)Waits until the three-way handshake completes or fails
read / recv / recvfromWaits until at least 1 byte (or 1 datagram) arrives, or peer terminates connection
write / send (TCP)Waits for space in the kernel send buffer (blocks when peer reads too slowly)

When an application must service multiple concurrent clients or balance communication with peripheral sensing and user input, single-threaded blocking is unacceptable. Three design patterns resolve this:

multitarea

One Thread per Client

The main thread exclusively executes accept; upon accepting a connection, it spawns a worker thread (or forks a child process) dedicated to that descriptor. Worker code uses straightforward blocking I/O. Maximizes responsiveness; requires thread synchronization for shared state (Tema 2).

multiplexación

select / poll

A single thread monitors multiple descriptors simultaneously: requests the kernel notify it when any descriptor becomes ready for I/O, then calls accept or read exclusively on ready descriptors without blocking.

no bloqueante

Non-Blocking Mode

Configuring descriptors via fcntl(fd, F_SETFL, O_NONBLOCK) causes unmet calls to return -1 immediately with errno = EAGAIN or EWOULDBLOCK. Typically paired with select/poll event loops.

Older documentation sometimes refers to non-blocking flags as O_NODELAY; Linux POSIX headers standardize on O_NONBLOCK.

Multi-Threaded Server Example

static void *atiende(void *arg) {    int cfd = (int)(intptr_t)arg;    /* ...servicing client using blocking read/write on cfd... */    close(cfd);    return NULL;} for (;;) {                                       // Main thread: accepts clients    int cfd = accept(lfd, NULL, NULL);    if (cfd < 0) continue;    pthread_t th;    pthread_create(&th, NULL, atiende, (void *)(intptr_t)cfd);    pthread_detach(th);                          // Automatically reclaim on termination}

I/O Multiplexing: select

int select(int nfds, fd_set *readfds, fd_set *writefds,           fd_set *exceptfds, struct timeval *timeout);
  • readfds, writefds, and exceptfds represent descriptor sets monitored for readability, writability, and exceptional conditions (pass NULL to ignore). Manipulated via FD_ZERO (clear), FD_SET (add), FD_CLR (remove), and FD_ISSET (test membership).
  • nfds must equal the highest descriptor value in any set plus 1.
  • timeout specifies maximum wait time (seconds + microseconds); passing NULL waits indefinitely; expiring with no events returns 0.
  • Upon return, the kernel modifies the sets in place, retaining only ready descriptors. Hence, loops must refresh the sets from a master copy on each cycle. A listening socket ready for read indicates an incoming connection for accept; a connected socket ready for read indicates available data or EOF (read returning 0).
fd_set all, rd;FD_ZERO(&all);FD_SET(lfd, &all);int maxfd = lfd;for (;;) {    rd = all;                                     // Refresh copy: select modifies sets    struct timeval tv = { 1, 500000 };         // 1.5 s    int r = select(maxfd + 1, &rd, NULL, NULL, &tv);    if (r < 0) { perror("select"); break; }    if (r == 0) { puts("sin actividad"); continue; }   // Timeout    for (int fd = 0; fd <= maxfd; fd++) {        if (!FD_ISSET(fd, &rd)) continue;        if (fd == lfd) {                          // New connection: accept will not block            int c = accept(lfd, NULL, NULL);            if (c >= 0) { FD_SET(c, &all); if (c > maxfd) maxfd = c; }        } else {                                  // Client data available or disconnected            char buf[256];            ssize_t n = read(fd, buf, sizeof buf);            if (n <= 0) { close(fd); FD_CLR(fd, &all); }            else write_all(fd, buf, n);            // Echo payload        }    }}
Architectural Guidance

While select allows single-threaded concurrency, dedicated worker threads paired with timers provide substantially greater modularity and responsiveness. Rule of thumb: when handling periodic tasks or complex client workflows, use multithreading; when forwarding modest traffic between a handful of sockets, select suffices. poll operates similarly, substituting an array of struct pollfd for bitsets and eliminating the descriptor count ceiling (where select is bounded by FD_SETSIZE, commonly 1024).

Connection Teardown: close vs. shutdown

close(fd)

Terminates both communication directions simultaneously and releases the file descriptor and underlying kernel resources. Sockets must always be closed upon completion.

shutdown(fd, how)

Selectively shuts down communication directions: SHUT_RD (0, ceases receiving), SHUT_WR (1, ceases transmitting; informs peer via EOF/read returning 0), SHUT_RDWR (2, both directions). It does not release descriptor resources; close must still be invoked.

To ensure clean termination without protocol ambiguity: invoke shutdown(fd, SHUT_RDWR) to explicitly signal communication termination, followed by close(fd) to free descriptor table entries.

bind: Address already in use

Following process termination, the kernel retains recently closed TCP endpoints in TIME_WAIT state for approximately 1–2 minutes. Rebinding to the same port during this interval fails. To bypass this delay, set SO_REUSEADDR on the socket prior to calling bind:

int on = 1;setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);

Failing to close sockets during process execution holds ports open continuously, preventing other applications from binding.

SIGPIPE Handling

Writing to a TCP socket after the remote peer has closed the connection triggers the kernel to deliver a SIGPIPE signal to your process. Its default action terminates the process abruptly. Prevent termination by passing MSG_NOSIGNAL during write, which returns -1 with errno = EPIPE for graceful handling:

send(fd, buf, len, MSG_NOSIGNAL);sendto(fd, buf, len, MSG_NOSIGNAL, (struct sockaddr *)&to, sizeof to);

Alternatively, ignore the signal globally during program startup: signal(SIGPIPE, SIG_IGN); standard writes will then fail with EPIPE rather than killing the process (Tema 3).

Useful network diagnostic utilities include: getpeername(fd, …) to retrieve the connected remote endpoint address (TCP only); gethostname(buf, size) to query local host name; and getifaddrs/freeifaddrs to enumerate local network interfaces (e.g. eth0, wlan0) along with their assigned IP addresses.

§8HTTP Messages T4.10

A web browser is simply a TCP client. What does it actually write onto the connection?HTTP: texto sobre TCP, líneas terminadas en CRLF.

HTTP (HyperText Transfer Protocol) is an application-level text protocol layered directly over TCP. A web client initiates a TCP connection (default port 80; port 7070 in http://192.168.1.20:7070/), transmits an HTTP request, and the server returns an HTTP response. Both message types share a standardized structure:

  1. First line: Request line or Status line;
  2. Arbitrary number of headers formatted as Header-Name: value;
  3. An empty line;
  4. Optional message body.

Every header line terminates with CRLF (\r\n, Carriage Return + Line Feed). This exemplifies the delimiter framing described in §5: servers must loop reading from the socket until detecting the sequence \r\n\r\n (the empty line) signaling header completion.

Request · Petición

GET /saludo HTTP/1.1\r\nHost: 192.168.1.20:7070\r\nUser-Agent: Mozilla/5.0 …\r\nAccept: text/html\r\n\r\n

Request Line = Method + URI Path + HTTP Version. Dominant methods include GET (resource retrieval) and POST (data submission, included in body). GET requests rarely contain a body.

Response · Respuesta

HTTP/1.1 200 OK\r\nContent-Type: text/plain; charset=utf-8\r\nContent-Length: 4\r\nConnection: close\r\n\r\nHola

Status Line = HTTP Version + Status Code + Reason Phrase. Standard codes: 200 OK, 301 Moved Permanently, 400 Bad Request, 404 Not Found, 500 Internal Server Error.

HeaderSignificance
HostSpecifies target host domain and port (mandatory in HTTP/1.1)
Content-TypeMIME type of payload: text/plain, text/html, application/json…
Content-LengthExact payload size measured in bytes
Connection: closeInstructs peer that server will close connection following response

Detecting Message Body Boundaries

Headers terminate cleanly via the blank line delimiter, but payload bodies can contain arbitrary binary bytes. HTTP resolves body length through three mechanisms:

  • Content-Length: Header declares exact byte count; receiver reads until reaching this count.
  • Connection Closure: Server transmits payload and immediately closes socket; receiver detects termination when read returns 0 (communicated via Connection: close).
  • Chunked Transfer (Transfer-Encoding: chunked): Data arrives in sequential chunks with preceding hexadecimal lengths; a 0-length chunk signals end of payload.

From the server's perspective, responding involves writing formatted bytes to the client socket descriptor cfd after reading the request headers:

static const char resp[] =    "HTTP/1.1 200 OK\r\n"    "Content-Type: text/plain; charset=utf-8\r\n"    "Content-Length: 4\r\n"                  // "Hola" = 4 bytes    "Connection: close\r\n"    "\r\n"                                    // Blank line: terminates headers    "Hola";write_all(cfd, resp, sizeof resp - 1);     // Exclude trailing string null terminator '\0'close(cfd);

Content-Length measures bytes, not characters: UTF-8 characters such as "ñ" or "á" each consume 2 bytes in memory.

Self-Test 12 Questions

Self-test questions based on this chapter. Only one attempt per question; explanations appear after answering.

01Which layer of the network stack does the socket API expose to user applications?

B. Sockets interface between the application layer and transport layer; address family and connection semantics must still be declared by the application (§1).

02On a little-endian Raspberry Pi, what is the value of htons(5005) (where 5005 = 0x138D) when read in host byte order?

C. htons swaps the two bytes (not individual hex nibbles) so that 0x13 sits first in memory matching network byte order (§3).

03Which of the following correctly initializes sockaddr_in for a server listening on port 5005 across all local interfaces?

A. sin_family takes the address family, not socket type; the port must be converted to network byte order using 16-bit htons (§3).

04Which system call is specific to TCP servers and directs the kernel to begin queueing incoming connection requests for a socket?

D. listen configures the socket to passive listening mode, setting the backlog queue limit; accept dequeues established connections (§4).

05Regarding the TCP three-way handshake and accept, which statement is accurate?

B. The listening socket remains open and listening; subsequent data exchange with the client proceeds via the newly created descriptor from accept (§4).

06On an established TCP socket, what does read(fd, buf, 100) returning 0 signify?

C. > 0 indicates bytes read, 0 indicates peer closure (EOF), and -1 indicates an error. Under blocking mode, lack of data causes read to wait rather than return (§5, §7).

07A client executes write(fd, "ABC", 3) followed immediately by write(fd, "DEFG", 4). When the server invokes read(fd, buf, 100) once, what may it receive?

D. TCP provides an ordered byte stream without message boundaries; receivers must loop and parse messages using delimiters or length prefixes (§5).

08A UDP sender transmits a 1000-byte datagram. The receiver calls recvfrom(fd, buf, 500, 0, …) with a 500-byte buffer. What happens?

A. Datagrams are discrete units and must be read in a single call; buffer length must accommodate the maximum anticipated datagram size (§6).

09Which of the following entities typically does not invoke bind?

C. During connect, the kernel automatically binds an ephemeral port; servers and listening UDP endpoints require predetermined fixed ports (§4, §5, §6).

10When using select to monitor multiple sockets, why must descriptor sets be reinitialized on every iteration of the event loop?

B. A master descriptor set is typically maintained, copied into a working set before each select call (§7).

11A server writes data to a TCP client that unexpectedly disconnected, causing the server process to terminate abruptly. What is the cause and resolution?

A. SO_REUSEADDR resolves "Address already in use" on bind; SIGPIPE handles writing to severed connections (§7).

12In an HTTP response message, what separates the headers from the body payload?

D. Body boundaries are then parsed via Content-Length, connection termination, or chunked transfer encoding (§8).
