§1像人一样：感知、思考、行动

智能环境的架构可以类比 modelo de proceso humano (ES)——人的信息处理模型。系统与 mundo físico——物理世界（环境和人）互动：通过 entradas——输入采集信息，percepción——感知模块提取最相关的特征并分类，存进 conocimiento——知识模块的记忆；conocimiento 再做决策，要么改变系统自身的状态，要么通过 salidas——输出对物理世界采取行动。它还会从经验中学习，不仅能适应变化，还能预测变化。

Mundo físico · 物理世界

由 entorno medioambiental（物理环境）和 personas（人）组成。图里是一个椭圆，里面列着天气（云、闪电）、温度（温度计）、物体（1 kg 砝码）和人。系统的输入都来自这里，系统的动作也都作用在这里。

Entradas · 输入 = sensores

可以是简单的 transductor——换能器，也可以是集成了处理或通信能力的 dispositivo inteligente——智能设备。

Percepción · 感知

从采集到的原始数据中提取最相关的 características（特征），并对它们分类，存进 conocimiento 的记忆。

Aprendizaje · 学习

系统 aprende de la experiencia——从经验中学习，所以不仅能适应变化，还能预测变化。图里它是一个独立模块，夹在 Percepción 和 Generación de acciones 之间、紧挨着 Conocimiento。

Generación de acciones · 生成动作

Conocimiento 的决策有两种结果：改变系统自身的状态，或者生成动作，再通过 salidas 体现在物理世界里。

Conocimiento · 知识

把分类后的信息存进记忆，据此做决策：改变系统状态，或者交给 Generación de acciones 产生对外的动作。图里它是最大的一块，纵跨 Aprendizaje 和 Generación de acciones 两行。

Salidas · 输出 = actuadores

把决策变成对物理世界的动作：开灯、调温、锁门……和输入一样，可以是简单换能器，也可以是智能设备。

关键词

感知并作用于物理世界、计算与物理过程闭环耦合，所以智能环境可以看作一个 sistema ciberfísico (ES) / cyber-physical system, CPS (EN)——信息物理系统。

§2为什么需要 middleware 2.1.1

智能环境的特点，直接决定了它对软件架构的要求：

特点
  • 技术多、差异大
  • 资源分散在环境各处
  • 设备和服务动态接入、断开，互相通信，组合成新服务
  • 有 inteligencia、consciencia del contexto（情境感知）和 autonomía
→
所以系统是

grandes · complejos · dinámicos · heterogéneos · distribuidos

大、复杂、动态、异构、分布式

→
需要

escalables · interoperables · adaptativas 的方案，加上一个强大的 middleware：屏蔽各元素的异构和变化，让大家共用一个模型。

选一选：下面哪种 middleware 适合智能环境？点开每一种看结论。

不太适合

分布式计算的传统 middleware，例如 RPC (Remote Procedure Calls)、CORBA (Common Object Request Broker Architecture)、Java RMI (Remote Method Invocation)、Microsoft DCOM (Distributed Component Object Model)。问题在于对环境变化的适应能力有限。

可选方案

middleware reflectivo——反射式中间件：一般指能在运行时检查并调整自身行为的中间件。

可选方案

AOP (Aspect Oriented Programming)——面向切面编程：一般指把日志、安全这类横切关注点从业务代码里分离出来。

可选方案

SOA (Services Oriented Architecture)——面向服务的架构。功能以“服务”的形式提供，可以发布、发现、组合。后面讲的 servicios web 和 OSGi 都属于这条路线。

首选 · 目标 2.1.1 的答案

SSOA (Semantic Services Oriented Architecture)——语义化面向服务架构。在 SOA 的基础上加入语义（web semántica + ontología），机器能自己理解服务，从而自动发现、组合服务。上面几种方案里，本章特别强调 SSOA（sobre todo）。

§3服务发现与协调 2.1.2

middleware 要处理好两件事：服务的发现，以及服务之间的通信与协调。

定义 · 2.1.2

descubrimiento de servicios (ES) / service discovery (EN)——服务发现：向“cliente”（客户端）提供环境中所有可用服务的信息。

看一个 Bluetooth 的例子：一台 PDA 想知道周围的设备能做什么，于是发出一条服务查询；只有被问到的那台设备回答。

配对：发现协议有很多种。先点左边的协议，再点右边它所属的技术。

发现服务之后，靠什么通信和协调？举三种机制：

Servicios web

为网络上的 M2M 通信设计的软件组件，接口用标准语言定义。§4 详细讲。

Agentes

agente——智能体：自主的软件实体，具备通信、协商、协调能力。例：JADE (JAVA Agent DEvelopment Framework)。

Tuple Spaces

Tuple Space——元组空间：各组件共享的一块空间，用几个简单原语读写其中的信息。例：Sun 的 JavaSpaces。

§4Servicios web：七步走 2.1.3

servicio web (ES) / web service (EN)——Web 服务。下面是它的典型工作流程。三个角色：proveedor（service provider，服务提供者）、registro de servicios（service registry，服务注册表，一个存放服务描述的数据库）、cliente（service requestor，服务请求者）。

概览

三个协议各回答一个问题。把它们放进同一个场景：客户端想找一个能做 X 的服务。点击图中的箭头，看每个协议负责哪一段：

UDDI · 找到服务（第 1、2 步）

① Client 问 UDDI Registry：哪里有能做 X 的 Web 服务？② Registry 回答：Server A 能做 X。两步都标着 UDDI，也就是 descubrir los servicios。

WSDL · 知道怎么调用（第 3、4 步）

③ Client 直接问 Server A：具体该怎么调用你？④ Server A 回一份 WSDL：“看这个”。WSDL 是服务器自己提供的服务描述，也就是 saber cómo invocarlos。图中第 ③ 步没有标协议，只有第 ④ 步标着 WSDL。

SOAP · 发出请求（第 5、6 步）

⑤ Client 用 SOAP 请求执行操作 X；⑥ Server A 也用 SOAP 返回操作 X 的结果。所以 SOAP 不只是“发请求”，结果也走 SOAP。也就是 cómo solicitarlos。

先自己想，再点击右列揭晓：

要回答的问题比喻协议（点击揭晓）
有哪些服务？在哪里？（descubrir）· 上图第 1–2 步黄页UDDI · Universal Description, Discovery and Integration：向注册表查询
怎么调用它？（saber cómo invocarlos）· 第 3–4 步说明书WSDL · Web Services Description Language：服务器提供的服务描述
怎么发出请求？（cómo solicitarlos）· 第 5–6 步信封SOAP · Simple Object Access Protocol：请求和结果都用它传

比喻只是帮助记忆。

§5OSGi 与 bundle 2.1.6

OSGi (Open Service Gateway Initiative) 是一种更针对智能环境的面向服务架构，用来为复杂、异构的系统构建模块化的 Java 应用。它的模块叫 bundle。

定义 · 2.1.6

bundle (OSGi)——OSGi 模块：

  • componente autocontenido——自包含组件：不需要外部引用就能存在和运行；
  • 本质是一个 JAR 文件 + 一组 metadatos（元数据），元数据说明这个 bundle 的特性；
  • 可以单独开发、测试、部署、管理、更新、删除，对其他 bundle 的影响最小。

动手试试：下面是一个模拟的 OSGi 框架。更新、停止或删除任意一个 bundle，看看其他 bundle 会不会受影响。

ACTIVE、RESOLVED 是 OSGi 规范里 bundle 的状态名。Gator smart house（§8）里，每个 sensor platform 通电后会把自己的 OSGi bundle 定义发给服务层完成注册。

§6语义网与本体 2.1.42.1.5

servicios web 在 descubrimiento 阶段还不够聪明。一个很适合智能环境的改进，是基于 SSOA 的 web semántica (ES) / Semantic Web (EN)——语义网。

定义 · 2.1.4

语义网里的信息是明确定义的，机器可以直接解读。于是有些事情以前只能在 tiempo de compilación（编译时）完成，现在可以自动完成：

  • 服务的 composición y ejecución（组合与执行）
  • descubrimiento dinámico（动态发现）

把两种 web 并排对比一下。切换看看：先看两张网络图，再看一个灯的小例子。

链接是有的，但链接不带含义：机器只知道 A 链到 B，不知道 B 是什么、为什么链过去。

小例子：<p>客厅的灯开着，功率 9 W。</p> 人一看就懂；对机器来说只是一串字符，它不知道“灯”是一种 actuador，也不知道“客厅”是一个房间。

同样是一张网，但每个节点知道自己是什么（Software、Document、Person……），每条边说明是什么关系（requires、hasAuthor、livesAt……）。机器可以顺着关系推理，例如“这份 Document 的作者住在哪里”。

小例子：同一句“客厅的灯开着，功率 9 W”写成三元组——

sujetopredicadoobjeto
Lámpara_01esUnActuador
Lámpara_01estáEnSalón
Lámpara_01estadoencendida
Lámpara_01potencia9 W

每个词都指向 ontología 里定义好的概念。机器现在能自己回答：“Salón 里有哪些 Actuador？”答案是 Lámpara_01。

要做到这一点，语义网需要一个 ontología。

定义 · 2.1.5

ontología (ES) / ontology (EN)——本体：对环境中所有概念及其相互关系的形式化表示，目的是让应用“理解”信息。

更严格的定义和词源

更严格地说，ontología 是一种形式化的、经过共识的概念规范表示，提供关于某个领域的共享知识；这些知识是机器可处理的语义信息，并且能在 agentes（组织、个人、软件）之间互操作。

这个词来自哲学：希腊语 onto（存在）+ logos（知识），指研究现实的本质和组织的理论。在计算机领域，它指描述环境中有哪些类型的实体、它们之间如何关联。

§7Plataformas IoT 了解即可

plataforma IoT (ES) / IoT platform (EN)——IoT 平台：一种 middleware，以安全、容错的方式把“cosas”（物）和它们采集的数据，连接到 web 应用并加以管理。它可扩展、灵活，通常基于标准、API 和 SDK，方便接入新的设备、应用和异构服务。

为什么要用平台？很多看起来完全不同的 IoT 应用，需求其实大同小异：传感器及其管理、安全与隐私、数据分析和处理、存储、用户界面。平台提供抽象层和可定制的通用工具，能缩短 time-to-market（上市时间），往往也能降低成本。

Watson IoT AWS IoT Microsoft Azure IoT Suite Kaa Firebase

想多了解，可以读 IBM 的 IoT 101 指南（为什么要用 IoT 平台）；这份指南属于拓展内容。

§8Gator smart house 的分层

University of Florida 的 Gator Tech Smart House（Bloque 1 见过）为任意普适计算空间设计了一套通用的参考架构，分成几个抽象层级：Físico、Plataforma del sensor、Servicio（与 Conocimiento、Gestión del contexto 同级）、Aplicación。点击每一层：

Aplicación · 应用层

一个 application manager（应用管理器），负责激活、停用服务；再加上一套开发工具，用来创建新的应用和智能空间。图中这套工具是一个 Integrated development environment，包括 service composer、context builder、debugger 和 simulator。应用层和下面三个同级的层都有双向箭头。

Servicio · 服务层

应用层和平台层之间的中介，提供发布、定义语义、发现、组合服务的机制。这一层运行 OSGi framework：sensor platform 的 bundle 在这里成为 basic services，basic services 再组合成 composite services（图中 basic 和 composite 之间的虚线）。组合出来的服务，就是这个空间里可用的应用。

Conocimiento · 知识层

包含所提供服务和所连接设备的 ontología（图中：Knowledge and service semantics），以及一个 motor de razonamiento（Reasoning engine，推理引擎），它借助本体做决策，判断某些 servicios compuestos（组合服务）是否可用。

注意：图中把 Service registration 和 Service discovery 也画在知识层里；有些资料正文则把发布、发现服务归给服务层。

例子：系统要知道摄氏温度传感器的输出必须先转成华氏度，才能交给另一个服务。

Gestión del contexto · 情境管理层

可以定义不同的 contexto（情境）。每个情境是一张图（图中：Context graphs），规定或限制多个应用中服务的激活和状态。motor de contexto（图中：Context detection and maintenance engine）负责检测“没有考虑到的状态”，并从中恢复。

Plataforma del sensor · 传感器平台层

通常是嵌入式系统，汇集并控制环境中某一区域的传感器和执行器，向上提供统一的接口和协议。它的作用是把硬件变成软件服务，可以编程，也可以和其他服务组合。这些服务就是 OSGi bundle：每个平台由 sensor/actuator firmware 和一份 OSGi service bundle definition 组成（图中简写为 OSGi bundle + firmware）。

例子：烤面包机应该接入（忘了关可能起火），搅拌机就不必。

Físico · 物理层

各种电器和设备的传感器、执行器：灯、电视、机顶盒、收音机、闹钟、门铃、门锁、烟雾和温度探测、空调、报警和安防系统……上层通过 plataforma del sensor 来“发现”并控制它们。图中把这一层再分成两个子层：Sensor/actuator layer（传感器、执行器）和 Physical world layer（appliances/devices/objects，电器、设备、物体）。

自测 10 题

根据本章内容编写的练习题。每题只能点一次，答完会显示解析。

01按本章的说法，智能环境可以看作一种什么系统？

C。它感知物理世界、做决策、再作用回物理世界，是计算和物理过程闭环耦合的 sistema ciberfísico（§1）。

02为什么传统的分布式计算 middleware（RPC、CORBA、RMI、DCOM）不太适合智能环境？

B。传统 middleware 在 adaptabilidad a un cambio en el entorno 方面有局限（§2）。

03本章认为最适合智能环境的 middleware 是？

D。§2 列出 reflectivo、AOP、SOA，并特别强调 SSOA，这就是目标 2.1.1 的答案。Tuple Space 是一种协调机制，不是这里说的 middleware 方案。

04“向 cliente 提供环境中所有可用服务的信息”，这个机制叫什么？

A。这是 descubrimiento de servicios 的定义（目标 2.1.2）。publicación 是 proveedor 把描述登记到 registro。

05在 servicios web 的流程里，proveedor 把服务描述登记到 registro de servicios，这一步叫什么？

C。第 ① 步就是 publicación。búsqueda 是第 ⑤ 步：registro 把某个服务的信息发给 cliente。

06哪个协议告诉你“如何调用”一个 web service？

B。UDDI 用来发现服务，WSDL 描述如何调用，SOAP 用来发出请求。SSDP 是 UPnP 的发现协议。

07关于 OSGi 的 bundle，哪一项正确？

C。bundle = JAR + metadatos，自包含，可以单独更新或删除，对其他 bundle 影响最小（目标 2.1.6）。

08语义网要让应用“理解”信息，需要什么？

A。La web semántica necesita una ontología：对所有概念及其关系的形式化表示（目标 2.1.4、2.1.5）。

09在 Gator smart house 中，把硬件变成可编程、可组合的软件服务的是哪一层？

D。sensor platform 把传感器和执行器变成软件服务（OSGi bundle），向上提供统一接口。

10Gator 中，谁来判断某个 servicio compuesto 是否可用？

B。知识层借助 ontología 推理，判断组合服务是否可用。motor de contexto 负责检测并恢复“没有考虑到的状态”。
