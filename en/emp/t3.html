Señales y temporización POSIX

Signals and timers: enabling processes to act at the right moment

10 Key Points Approx. 30 min read

On microcontrollers, timer overflows directly interrupt the CPU. On boards running Linux, hardware interrupts are owned strictly by the kernel and inaccessible to user space. The kernel transforms events such as "time expired", "another process wants your attention", or "invalid memory access" into signals (EN) / señales (ES) sent to processes. This chapter examines how signals are generated, delivered, handled, and masked; how POSIX reads system clocks, sleeps, and creates timers; and why periodic tasks suffer from drift and how absolute timing eliminates it.

§1What Signals Are T3.1 · T3.2

Hardware interrupts belong to the kernel. How does a user process know when "time is up"?Una señal es una interrupción software que el kernel envía a un proceso.

A signal is an asynchronous software notification delivered to a process: while the process executes normal instructions, arrival of a signal causes control flow to jump to a predefined function, returning to the interrupted location upon completion. While conceptually similar to hardware interrupts, the fundamental distinction lies in who generates the event and who receives it:

hardware

Interrupt · interrupción

Generated by physical hardware and delivered to the CPU. On Linux, only kernel device drivers can handle physical interrupts directly.

software

Signal · señal

Generated by the kernel or another process and delivered to a specific process. When a hardware timer expires, the kernel handles the interrupt and generates a signal on behalf of the clock.

Why this layer of indirection? The physical board has only a single hardware timer generating one type of interrupt. The kernel intercepts this interrupt and distributes appropriate signals to multiple processes as requested. If a user process directly seized control of the physical timer interrupt, no other process could utilize timing services.

Upon receiving a signal, a process executes one of three dispositions, configured per signal:

SIG_DFL

Default Action

Executed by the kernel. The default action for most signals is terminating the process, sometimes writing a core dump file, or pausing, continuing, or ignoring (see table below).

SIG_IGN

Ignore

The signal is discarded upon arrival. Note: Ignoring is fundamentally distinct from blocking. A blocked signal waits as pending; an ignored signal is permanently discarded (§3).

handler

Catch

Executes a programmer-defined signal handler (EN) / manejador (ES). The program will not terminate unless the handler explicitly calls exit.

Signals are asynchronous software notifications delivered by the kernel to processes. Each signal possesses a disposition: default action, ignore, or custom handler. SIGKILL and SIGSTOP are critical exceptions: the kernel guarantees it can always terminate or pause any process, so they can never be caught, blocked, or ignored.

§2Catching Signals: signal and sigaction T3.3 · T3.4

Installing a signal handler takes just one line. The tricky question: what are you actually allowed to do inside it?Armado de la función de tratamiento de señal.

The Simple signal() API

#include <signal.h>void (*signal(int signum, void (*handler)(int)))(int);

While the C declaration appears complex, it simply means: signal takes a signal number and a pointer to a function returning void that accepts an int, returning the previous handler function pointer (or SIG_ERR on failure). The second argument can also be the constant SIG_DFL (restore default) or SIG_IGN (ignore). The integer received by the handler is the signal number, enabling a single handler to process multiple signal types.

Example: The first two Ctrl+C presses print warnings; the third restores default disposition, so the fourth Ctrl+C terminates the program:

#include <signal.h>#include <stdio.h>#include <unistd.h> static volatile sig_atomic_t veces = 0; static void on_int(int sig) {    veces++;    if (veces == 3)        signal(SIGINT, SIG_DFL);           // Next Ctrl+C invokes default action: terminate} int main(void) {    if (signal(SIGINT, on_int) == SIG_ERR) { perror("signal"); return 1; }    for (;;) {        pause();                              // Sleep until any caught signal arrives        printf("Ctrl+C count: %d\n", (int)veces);  // printf is in main, never inside signal handler    }}
  • pause() puts the calling process to sleep until a signal is handled, then returns −1 with errno = EINTR. Here −1 does not signify an error condition; it is the normal return contract.
  • Sending signals: kill(pid, sig) sends to another process (pid > 0 targets that process; pid = −1 broadcasts to all authorized processes except init; pid < −1 targets process group −pid); raise(sig) sends to the caller itself, equivalent to kill(getpid(), sig). From the command line, use kill -USR1 <pid>.
  • Handlers can be swapped dynamically at any time: a subsequent call to signal overwrites the disposition with the newest registration.

The Complete sigaction() API

The behavior of signal() historically differed across Unix flavors (such as whether handlers auto-reset to default or whether interrupted system calls restart automatically) and cannot provide metadata regarding sender identity. POSIX strongly standardizes on sigaction:

int sigaction(int signum, const struct sigaction *act, struct sigaction *oldact); struct sigaction {    void     (*sa_handler)(int);                       // Basic handler: identical to signal    void     (*sa_sigaction)(int, siginfo_t *, void *);  // Extended handler: receives extra metadata    sigset_t   sa_mask;                                  // Additional signals masked while handler executes    int        sa_flags;                                 // Behavior flags, bitwise OR-ed};

sa_handler and sa_sigaction are mutually exclusive—only one can be used. To use the extended signature, set SA_SIGINFO in sa_flags; the handler then receives three parameters: the signal number, a siginfo_t * pointer (identifying sender PID, generation cause, and accompanying payload), and an execution context pointer. When oldact is non-NULL, it receives the previous configuration for subsequent restoration.

sa_flagsPurpose
SA_SIGINFOEnables sa_sigaction extended handler, passing full siginfo_t metadata
SA_RESTARTSystem calls interrupted by this signal (read, write, wait...) restart automatically rather than failing with −1 / EINTR
SA_RESETHANDResets disposition to SIG_DFL upon entering the handler ("one-shot catch")
SA_NODEFERDoes not automatically mask the signal during its own handler execution, allowing nested recursion
SA_NOCLDSTOP(Used with SIGCHLD) Do not generate SIGCHLD when child processes stop or resume
SA_NOCLDWAIT(Used with SIGCHLD) Prevent child processes from transforming into zombies upon exit
SA_ONSTACKExecutes handler on an alternate signal stack configured via sigaltstack

By default, the signal currently being handled is automatically blocked for the duration of its execution (unless SA_NODEFER is specified), in addition to any signals specified in sa_mask. Upon handler return, the previous mask is automatically restored.

Common fields in siginfo_t: si_signo (signal number), si_code (origin: SI_USER for kill, SI_QUEUE for sigqueue, SI_TIMER for POSIX timers), si_pid / si_uid (sender PID/UID), and si_value (accompanying payload value, §4).

Example: Using the extended form to record who sent SIGUSR1, while blocking SIGUSR2 during handler execution:

static volatile sig_atomic_t quien = 0; static void on_usr1(int sig, siginfo_t *si, void *ctx) {    (void)sig; (void)ctx;    quien = si->si_pid;                          // Record sender PID safely    write(STDOUT_FILENO, "USR1\n", 5);           // write is async-signal-safe} int main(void) {    struct sigaction sa;    memset(&sa, 0, sizeof sa);    sa.sa_sigaction = on_usr1;                   // Extended form handler    sa.sa_flags = SA_SIGINFO | SA_RESTART;       // Requires SA_SIGINFO    sigemptyset(&sa.sa_mask);    sigaddset(&sa.sa_mask, SIGUSR2);             // Mask SIGUSR2 during execution    if (sigaction(SIGUSR1, &sa, NULL) == -1) { perror("sigaction"); return 1; }    for (;;) {        pause();        printf("SIGUSR1 received from PID %d\n", (int)quien);    }}

What Can Run Safely Inside a Signal Handler

A signal handler can interrupt the main program after any single machine instruction, including in the middle of a printf or malloc call. If the handler itself invokes printf, both contexts simultaneously mutate internal stdio buffers, leading to memory corruption or deadlock (main holds the lock, handler blocks waiting for it, while main waits for handler completion to release it).

Consequently, signal handlers must only call async-signal-safe functions: functions guaranteed to be reentrant or to mask signals internally during execution.

Allowed

write, read, _exit, kill, raise, sigaction, sigprocmask, clock_gettime, timer_getoverrun, sem_post, and reading/writing volatile sig_atomic_t variables.

Disallowed

printf family, malloc / free, exit (flushes stdio buffers), pthread_mutex_lock, and the vast majority of standard library functions.

Best Practice

This follows the embedded microcontroller principle that "interrupt service routines must be minimal": the handler merely sets a volatile sig_atomic_t flag (or calls sem_post), deferring substantive processing to the main program. volatile forces the compiler to re-read the variable from memory; sig_atomic_t guarantees atomic read/write operations that cannot be torn by a signal. An even cleaner architecture avoids signal handlers entirely, using §3's synchronous sigwait. (Many classroom examples use printf inside handlers for quick demonstration, but production code must never do so).

Jumping Out of Handlers: sigsetjmp / siglongjmp

Signal handlers normally return to the interrupted instruction. When returning is inappropriate (e.g. after a fatal error or when main is blocked in an unwanted call), non-local jumps can unwind directly to a preset restore point:

#include <setjmp.h>int  sigsetjmp(sigjmp_buf env, int savesigs);   // Sets jump point: returns 0 on initial executionvoid siglongjmp(sigjmp_buf env, int val);      // Jumps back: sigsetjmp then returns val (cannot be 0)

The return value of sigsetjmp distinguishes initial registration (0) from jump resumption (val). When savesigs is non-zero, jumping back restores the saved signal mask, which is why signal unwinding must use the sig-variant rather than standard setjmp / longjmp. Always guard jumps with a volatile sig_atomic_t flag to confirm the jump environment is fully initialized.

§3Signal Mask and Blocking T3.5 · T3.6

A critical code block must never be interrupted. How do you make incoming signals wait?Enmascarado de señales: bloquear no es ignorar.

Each thread possesses a signal mask (EN) / máscara de señales (ES): a set of signals that are currently blocked. A blocked signal is still generated normally, but its delivery is deferred—it is held in the pending set until unblocked. This is fundamentally distinct from SIG_IGN:

bloquear · sigprocmask

Blocking: Hold Pending

The signal is retained in the pending set and delivered immediately once unblocked. It is not discarded (though duplicate standard signals merge into one).

ignorar · SIG_IGN

Ignoring: Discard Immediately

The signal is discarded upon arrival without trace. Restoring a handler later cannot retrieve discarded signals.

Signal Sets: sigset_t

int sigemptyset(sigset_t *set);              // Clear all signalsint sigfillset(sigset_t *set);               // Include all signalsint sigaddset(sigset_t *set, int signo);     // Add one signalint sigdelset(sigset_t *set, int signo);     // Remove one signalint sigismember(const sigset_t *set, int signo);  // Query membership: 1 / 0

sigset_t is an opaque type; always initialize it with sigemptyset or sigfillset before manipulation. Early Unix used an integer bitmask (sigblock, sigsetmask), limited to 32 signals; POSIX sigset_t accommodates all system signals, including real-time extensions.

sigprocmask

int sigprocmask(int how, const sigset_t *set, sigset_t *oldset);
howResulting Mask
SIG_BLOCKCurrent mask ∪ set (adds specified signals to mask)
SIG_UNBLOCKCurrent mask − set (unblocks specified signals)
SIG_SETMASKExact copy of set (replaces entire mask)

When oldset is non-NULL, it receives the previous mask; passing NULL for set queries the mask without modification. Standard pattern for critical sections: invoke SIG_BLOCK while saving oldset, then restore the original mask with SIG_SETMASK (rather than SIG_UNBLOCK, preserving signals that were already blocked prior to entry):

sigset_t set, old;sigemptyset(&set);sigaddset(&set, SIGINT);sigaddset(&set, SIGUSR1);sigprocmask(SIG_BLOCK, &set, &old);     // Enter critical section: mask both signalsactualizar_tabla();                     // Signal handlers also access this tablesigprocmask(SIG_SETMASK, &old, NULL);   // Restore: signals pending from critical section deliver here
  • sigpending(&set): Populates set with currently pending signals (generated but blocked from delivery).
  • sigsuspend(&mask): Atomically swaps the active mask with mask and suspends the thread until an unblocked signal is handled, restoring the previous mask upon return. Splitting "unblock then pause" into two steps introduces a race window: if a signal arrives between unblock and pause, it is handled immediately, causing pause to hang indefinitely. sigsuspend fuses both steps atomically.

Signals in Threads: pthread_sigmask + sigwait

In multithreaded applications, signal masks are per-thread (new threads inherit the creator's mask), whereas signal dispositions (handlers) are shared process-wide. A signal sent to the process (via kill or timer) is delivered to any arbitrary thread that has not blocked it.

To modify masks in threads, call pthread_sigmask (sigprocmask is undefined in multithreaded code). A widely adopted design pattern completely avoids asynchronous signal handlers:

  1. In main, before spawning any threads, block all target signals using pthread_sigmask. All subsequent threads inherit this blocked mask, preventing any thread from being asynchronously interrupted.
  2. Spawn a dedicated signal-handling thread running a loop around sigwait(&set, &sig): it sleeps until one of the specified signals becomes pending, consumes it synchronously without invoking a handler, and returns the signal number in sig.
static void *hilo_senales(void *arg) {    sigset_t *set = arg;    int sig;    for (;;) {        sigwait(set, &sig);                 // Wait synchronously: regular context, any function can be called        printf("Received signal %d\n", sig);        if (sig == SIGTERM) exit(0);    }} int main(void) {    static sigset_t set;    sigemptyset(&set);    sigaddset(&set, SIGUSR1);    sigaddset(&set, SIGTERM);    pthread_sigmask(SIG_BLOCK, &set, NULL);       // 1. Block first: all child threads inherit this mask    pthread_t th;    pthread_create(&th, NULL, hilo_senales, &set);  // 2. Dedicated signal listener thread    /* 3. Worker threads proceed unhindered by these signals */    pthread_join(th, NULL);}
  • sigwaitinfo(&set, &info): Similar to sigwait, but returns the complete siginfo_t structure (sender PID, si_value), returning the signal number directly.
  • sigtimedwait(&set, &info, &timeout): Same with timeout; returns −1 with errno = EAGAIN on timeout.
  • Signals monitored via sigwait must be blocked beforehand: if unblocked, the signal may be dispatched to a default handler (terminating the process) before sigwait can retrieve it.

Asynchronous signal handlers face strict async-signal-safe limitations. Blocking signals and consuming them synchronously via sigwait in a dedicated thread converts signals into standard sequential events where arbitrary code and library functions can run safely.

§4Real-Time Signals T3.7

Standard signals have only one pending bit; three signals merge into one. What if every single notification is critical?Señales de tiempo real: SIGRTMIN…SIGRTMAX.

POSIX.1b introduced a range of signal numbers known as real-time signals (EN) / señales de tiempo real (ES) (SIGRTMIN … SIGRTMAX). They carry no pre-allocated operating system semantics, leaving them entirely to application software. Their default action is process termination. Compared to standard signals, they introduce three critical enhancements:

Standard SignalsReal-Time Signals
SemanticsPredefined by OS (SIGINT, SIGALRM…), only SIGUSR1/2 user-definedEntirely allocated for application use
Arrival While PendingMerged into a single bitQueued individually in FIFO order
Delivery PriorityUnspecified orderLower signal numbers deliver first; identical signals deliver FIFO
Payload DataNonesi_value (sival_int or sival_ptr)

Numbering

On Linux, SIGRTMIN and SIGRTMAX are not compile-time constants, but runtime values determined dynamically: the kernel reserves signals 32 through 64, while the glibc threading implementation internally reserves the first two, resulting in typical user values of SIGRTMIN = 34 and SIGRTMAX = 64. Therefore:

SIGRTMIN + n = 34 + n　　SIGRTMAX − n = 64 − n

Always reference signals in code as SIGRTMIN + n rather than hardcoded integers, verifying SIGRTMIN + n <= SIGRTMAX. The system-wide queued real-time signal capacity can be queried via sysconf(_SC_RTSIG_MAX).

Passing Data: sigqueue and si_value

union sigval { int sival_int; void *sival_ptr; };int sigqueue(pid_t pid, int sig, const union sigval value);

sigqueue functions similarly to kill, with the addition of a union sigval payload. The receiver extracts this value from si->si_value in an SA_SIGINFO handler or via sigwaitinfo, where si_code equals SI_QUEUE. Across process boundaries, only sival_int is meaningful (pointers in another process address space are invalid); within the same process (such as POSIX timers in §6), passing pointers is standard practice.

/* Sender */union sigval v = { .sival_int = 42 };sigqueue(pid_receptor, SIGRTMIN + 3, v); /* Receiver: block and retrieve synchronously via sigwaitinfo */sigset_t set;  siginfo_t si;sigemptyset(&set);sigaddset(&set, SIGRTMIN + 3);sigprocmask(SIG_BLOCK, &set, NULL);for (;;) {    sigwaitinfo(&set, &si);    printf("Value %d from PID %d\n", si.si_value.sival_int, (int)si.si_pid);}

§5POSIX Clocks and Sleeping T3.8

"What time is it now?" and "How much time has elapsed?" are two entirely different questions.Relojes: CLOCK_REALTIME y CLOCK_MONOTONIC.

A real-time embedded system requires three core timing mechanisms: a clock (EN) / reloj (ES) to measure elapsed intervals, an execution suspension mechanism to awaken tasks at planned times, and a timeout mechanism to detect timing violations.

Clocks are Counters

A clock consists of a hardware oscillator generating periodic ticks coupled with a counter tracking tick counts; software converts counts to engineering units. Two fundamental metrics: resolution (granularidad, the time span of a single tick) and range (the duration before the counter overflows). They trade off against each other: for a 32-bit counter, finer resolution causes faster overflow.

Range = 2³² × Resolution ≈ 4.29 × 10⁹ × Resolution
Resolution32-bit Counter Range
100 nsApprox. 429 s (7.2 min)
1 µsApprox. 4295 s (72 min)
100 µsApprox. 119 h
1 msApprox. 50 days
1 sApprox. 136 years

Note: Some literature erroneously lists 4.3 s for 100 ns resolution; 2³² × 100 ns equals ~429 s (4.29 s corresponds to 1 ns resolution).

Time Representation in POSIX

Unix represents absolute wall-clock time as seconds elapsed since the Epoch (1970-01-01 00:00:00 UTC) using time_t (64-bit on 64-bit Linux). Sub-second resolution uses structured types:

struct timeval  { time_t tv_sec; suseconds_t tv_usec; };  // Microseconds: 0 … 999 999struct timespec { time_t tv_sec; long        tv_nsec; };  // Nanoseconds: 0 … 999 999 999 (standard in POSIX)

Legacy interfaces: time() (seconds), gettimeofday() / settimeofday() (timeval, microseconds), difftime() (difference between two time_t values), struct tm (broken-down time: tm_year starts from 1900, tm_mon is 0–11), and mktime (tm → time_t). Adjusting system time requires administrative privileges.

POSIX Clock Types

int clock_gettime(clockid_t clk, struct timespec *tp);        // Read timeint clock_getres(clockid_t clk, struct timespec *res);       // Query resolutionint clock_settime(clockid_t clk, const struct timespec *tp);  // Set time (CLOCK_REALTIME only, requires root)
CLOCK_REALTIME

Wall-Clock Time

"What time is it now": Seconds elapsed since the Epoch. Subject to discontinuous jumps: manual adjustments by administrators or NTP stepping can cause time to shift forward or backward. Suitable for wall-clock timestamps and calendar-based actions.

CLOCK_MONOTONIC

Monotonic Clock

"How much time has elapsed": Monotonically increasing from an arbitrary baseline (typically system boot), never jumping backwards or forwards regardless of NTP adjustments. Always use for measuring intervals and scheduling periodic tasks.

Benchmarking execution duration:

struct timespec t0, t1;clock_gettime(CLOCK_MONOTONIC, &t0);trabajo();clock_gettime(CLOCK_MONOTONIC, &t1);long long ns = (t1.tv_sec - t0.tv_sec) * 1000000000LL + (t1.tv_nsec - t0.tv_nsec);

When performing addition on timespec, tv_nsec must strictly remain between 0 and 999 999 999; values exceeding this boundary must carry over into tv_sec. Kernel functions (nanosleep, timer_settime) immediately fail with EINVAL if tv_nsec ≥ 10⁹. Standard normalization helper:

#define NS_POR_S 1000000000Lstatic void ts_add_ns(struct timespec *t, long ns) {    t->tv_nsec += ns;    while (t->tv_nsec >= NS_POR_S) {          // Carry over when >= 10^9        t->tv_nsec -= NS_POR_S;        t->tv_sec++;    }}

Suspending Execution: Sleep Functions

FunctionResolutionCharacteristics
sleep(s)SecondsReturns unslept seconds if interrupted by a signal
usleep(us)MicrosecondsObsolete; removed in modern POSIX, use nanosleep instead

nanosleep returns under three conditions: requested duration elapsed; a signal handler was invoked; or the process was killed. Standard pattern to resume remaining sleep after an interruption:

struct timespec req = { .tv_sec = 0, .tv_nsec = 200 * 1000000L }, rem;   // 200 mswhile (nanosleep(&req, &rem) == -1 && errno == EINTR)    req = rem;                                // Resume remaining duration
Actual Sleep Duration

Actual sleep duration will only ever be longer than requested, never shorter: requests are rounded up to system clock granularity, and upon expiration the task must wait for the OS scheduler to reschedule it. Query clock resolution with clock_getres. Crucially, the retry loop above accumulates additional latency each time it is interrupted; eliminating this error requires absolute time (§7).

§6POSIX Timers T3.9

Sleeping halts task execution completely. Can the kernel notify the process upon expiration while it continues working?timer_create, timer_settime, struct sigevent, struct itimerspec.

Legacy Approaches: alarm and setitimer

  • unsigned alarm(unsigned s): Sends a SIGALRM signal to the process after s seconds. Calling again resets the timer (returning remaining seconds); alarm(0) cancels it. Coarse second-level resolution only.
  • setitimer(ITIMER_REAL, &it, &old): Uses struct itimerval (two timeval fields: it_value initial delay, it_interval periodic reload) for microsecond periodic timers, also delivering SIGALRM.
  • Default action for SIGALRM is process termination: always register the handler before arming the timer, or the program will terminate on first expiration.

Their drawbacks: strictly one timer per process; all tied to SIGALRM; relative durations only. POSIX timers resolve all three limitations:

#include <signal.h>#include <time.h>int timer_create(clockid_t clk, struct sigevent *evp, timer_t *timerid);int timer_settime(timer_t timerid, int flags, const struct itimerspec *nuevo, struct itimerspec *viejo);int timer_gettime(timer_t timerid, struct itimerspec *actual);   // Query remaining durationint timer_getoverrun(timer_t timerid);int timer_delete(timer_t timerid);

Older glibc versions require linking with -lrt; modern Linux glibc includes these directly in libc.

Expiration Action: struct sigevent

struct sigevent {  int          sigev_notify;   // Notification method  int          sigev_signo;    // Signal to deliver  union sigval sigev_value;    // Payload passed to recipient  void (*sigev_notify_function)(union sigval);  pthread_attr_t *sigev_notify_attributes;};
  • SIGEV_SIGNAL: Delivers the signal designated by sigev_signo, with si_value = sigev_value and si_code = SI_TIMER.
  • SIGEV_THREAD: Spawns a new thread executing sigev_notify_function(sigev_value). Because it runs in a standard thread context, async-signal-safe rules do not apply.
  • SIGEV_NONE: No asynchronous notification; caller polls status manually via timer_gettime.
  • evp = NULL: Defaults to SIGEV_SIGNAL delivering SIGALRM, with sigev_value set to the timer's ID.

Expiration Timing: struct itimerspec

struct itimerspec {  struct timespec it_interval; // Subsequent periodic interval  struct timespec it_value;    // First expiration delay or timestamp};
  • it_value ≠ 0: Arms the timer. When flags = 0, represents relative delay from now; when flags = TIMER_ABSTIME, represents an absolute timestamp (timestamps already in the past expire immediately).
  • it_value = 0: Disarms (stops) the timer, regardless of it_interval.
  • it_interval ≠ 0: Periodic timer; automatically reloaded upon every expiration.
  • it_interval = 0: One-shot timer; expires exactly once.

Emits SIGRTMIN every 250 ms until the main loop counts 20 ticks. Initialization sequence: register handler first, create timer, then arm:

#include <signal.h>#include <stdio.h>#include <time.h>#include <unistd.h> static volatile sig_atomic_t ticks = 0; static void on_tick(int sig, siginfo_t *si, void *uc) {    (void)sig; (void)si; (void)uc;    ticks++;                                     // Minimal action; si->si_value.sival_ptr points to tid} int main(void) {    struct sigaction sa = {0};    sa.sa_sigaction = on_tick;    sa.sa_flags = SA_SIGINFO;    sigemptyset(&sa.sa_mask);    sigaction(SIGRTMIN, &sa, NULL);             // 1. Register handler first     timer_t tid;    struct sigevent sev = {0};    sev.sigev_notify = SIGEV_SIGNAL;             // 2. Signal notification    sev.sigev_signo  = SIGRTMIN;    sev.sigev_value.sival_ptr = &tid;    if (timer_create(CLOCK_MONOTONIC, &sev, &tid) == -1) { perror("timer_create"); return 1; } struct itimerspec its = {0};    its.it_value.tv_nsec    = 250 * 1000000L;   // 3. Initial delay: 250 ms    its.it_interval.tv_nsec = 250 * 1000000L;   //    Reload: every 250 ms    timer_settime(tid, 0, &its, NULL);           //    flags = 0: relative duration while (ticks < 20) {        pause();        printf("tick %d\n", (int)ticks);    }    timer_delete(tid);    return 0;}

static void timeout(union sigval v) {             // Runs in a newly spawned thread    printf("Timed out: %s\n", (char *)v.sival_ptr);    // Standard thread: printf is legal} struct sigevent sev = {0};sev.sigev_notify = SIGEV_THREAD;sev.sigev_notify_function = timeout;sev.sigev_value.sival_ptr = "waiting for response";timer_t tid;timer_create(CLOCK_MONOTONIC, &sev, &tid); struct itimerspec once = {0};once.it_value.tv_sec = 3;                         // 3 seconds from now; it_interval = 0 -> fires oncetimer_settime(tid, 0, &once, NULL);
Alternative Timeout Mechanisms

Timeouts: To bound blocking waits on events, developers can use a one-shot timer or pass a timeout parameter to select(), which monitors descriptor readiness up to a timeout threshold (returning 0 on expiration). timerfd (Linux-specific): timerfd_create + timerfd_settime yields a file descriptor where standard read() blocks until timer expiration, reading an 8-byte integer tracking expirations—operating completely free of signals. Asynchronous I/O completions (aio_read) utilize the exact same struct sigevent mechanism.

§7Drift: Relative vs. Absolute Time T3.10

Sleeping 50 ms each loop for 100 iterations: why does total execution exceed 5 seconds?Deriva local y deriva acumulativa.

The most intuitive structure for a periodic task is "execute once, then sleep for one period":

for (;;) {    tarea_periodica();    nanosleep(&periodo, NULL);     // Relative sleep: sleeps one period starting from "now"}

This formulation suffers from two major flaws: it fails to deduct the execution time of the task itself, and wakeup is delayed by scheduling latency and timer granularity. The delay experienced in any individual cycle is local drift (EN) / deriva local (ES); because each subsequent cycle recalculates relative sleep from the delayed current moment, these errors compound into cumulative drift (EN) / deriva acumulativa (ES).

Relative Sleep Cumulative Drift ≈ n × (Execution Time + Wakeup Latency)　　Absolute Timing: ~Wakeup Latency per cycle (non-cumulative)

Constructing Periodic Loops with Absolute Time

The core concept is variable sleep: sleep only as long as needed to reach the next scheduled target. The cleanest implementation calculates deadlines against CLOCK_MONOTONIC using clock_nanosleep(…, TIMER_ABSTIME, …):

struct timespec next;clock_gettime(CLOCK_MONOTONIC, &next);              // Baseline reference pointfor (;;) {    ts_add_ns(&next, 50 * 1000000L);                // Next target = previous target + period (helper from §5)    while (clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL) == EINTR)        ;                                             // Interrupted by signal: target remains identical, resume sleeping    tarea_periodica();}
  • Crucially, next is incremented by adding the period to the previous target timestamp, not to "current time". The clock is sampled only once at initialization.
  • Upon signal interruption, the loop simply retries against the unchanged target timestamp without accumulating extra error.
  • If task workload occasionally exceeds a period, the target timestamp is already in the past, causing clock_nanosleep to return immediately: the task executes catch-up cycles without delay (analogous to timer overrun).

The identical principle applies to POSIX timers: pass TIMER_ABSTIME in timer_settime flags, specifying it_value as an absolute timestamp, advancing it by one period on each iteration (period 500 ms):

struct itimerspec its = {0};                        // it_interval = 0: manually schedule each targetclock_gettime(CLOCK_MONOTONIC, &its.it_value);for (;;) {    ts_add_ns(&its.it_value, 500 * 1000000L);       // Next absolute targettimer_settime(tid, TIMER_ABSTIME, &its, NULL);    pause();                                         // Wait for expiration signal    /* …execute cycle workload… */}
Does it_interval Drift?

For periodic timers (it_interval ≠ 0), the kernel schedules subsequent expirations by adding it_interval to the previous scheduled expiration timestamp, completely decoupled from when the user handler actually runs. Hence, POSIX periodic timers inherently avoid cumulative drift from task runtime. The genuine culprit behind cumulative drift is relative sleeping ("work then sleep").

Cumulative drift occurs when delays are computed relatively from "now". Defining future deadlines as "previous target + period" and waiting via absolute time (TIMER_ABSTIME) bounds timing errors to unavoidable local latency without compounding over time.

01What is the fundamental difference between signals and hardware interrupts?

B. Both are asynchronous events that return to the interrupted execution stream; they differ in source and destination entities (§1).

02Which pair of signals cannot be caught, blocked, or ignored?

D. The operating system must always retain the authority to terminate or stop any running process (§1).

03To register a 3-argument handler void h(int, siginfo_t *, void *) using sigaction, how must it be configured?

A. sa_handler and sa_sigaction are mutually exclusive; the extended signature requires SA_SIGINFO (§2).

04Which of the following functions is safe to call inside a signal handler?

C. write is async-signal-safe; printf, malloc, and mutex locking contend with the interrupted program state and risk deadlock (§2).

05SIGUSR1 has a registered handler and is currently blocked. Another process sends SIGUSR1 4 times via kill. When unblocked, how many times does the handler execute?

B. Blocking holds signals pending, but standard signals do not queue: multiple arrivals merge into a single pending bit (§3, §4).

06In the same scenario, if SIGRTMIN+3 is sent 4 times via sigqueue with distinct payload values, what happens upon unblocking?

C. Real-time signals queue in FIFO order for identical signal numbers, with each instance carrying its si_value (§4).

07What is the distinction between "signal X is ignored (SIG_IGN)" and "signal X is blocked"?

A. Masking (bloquear) defers delivery; ignoring (SIG_IGN) permanently drops the signal (§3).

08In a multithreaded program handling SIGTERM via sigwait in a dedicated thread, what is the correct setup?

D. Process-directed signals can target any thread that does not block them; all threads must block the signal for sigwait to reliably consume it (§3).

09Calling timer_settime(tid, 0, &its, NULL) with its.it_value = {0, 0} and its.it_interval = {0, 200000000} results in:

B. Setting it_value to zero disarms the timer regardless of it_interval (§6).

10A periodic timer's signal was blocked; upon unblocking, timer_getoverrun() returns 2. What does this indicate?

C. A timer maintains only one pending signal; additional expirations while pending increment the overrun counter (§6).
