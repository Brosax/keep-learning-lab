§0五种架构，一条阶梯 M28.1

同一块 MSP430F5529，程序的"骨架"可以完全不同。由什么决定？¿Qué arquitectura de programa elegir?

先把视野拉远一点：编程只是开发周期中的一步，其余任务同样必不可少，也会消耗大量开发资源。设计一个微控制器系统分成四个阶段，程序架构属于第二个（图里加粗的那一框）：

  1. ANÁLISIS（Especificación）——分析：写规格
  2. DISEÑO（Arquitectura）——设计：选程序架构，就是本章
  3. IMPLEMENTACIÓN（Programación, Validación e Integración）——实现：编程、验证、集成
  4. PRUEBAS（Depuración）——测试：调试

图里的说明框点出了本章的出发点：微控制器系统比较简单，所以只要定义一小组程序架构，就能开发大多数应用。至于能选哪几种，首先受微控制器本身的能力限制。

5 种架构按复杂度递增：bucle infinito → + interrupciones → + bajo consumo → planificador → RTOS。不是越复杂越好：够用、并且资源（内存、功耗、成本）负担得起的那一种，才是对的。

§1Bucle infinito · 无限循环 M28.2

没有中断，CPU 怎么知道哪个外设需要它？La CPU sondea cada periférico.

写成代码就是 Bloque 1 里的轮询，只是把多个外设串在同一个循环里（示意）：

int main(void) {    inicializar_perifericos();    while (1) {                                      // 永远不退出        if (p1_necesita_atencion()) atender_p1();   // CPU 主动去问        if (p2_necesita_atencion()) atender_p2();        if (p3_necesita_atencion()) atender_p3();    }}

Bucle infinito：CPU 周期性地 sondea 每个外设，外设从不打断 CPU。优点是简单；缺点是一个外设要等其他外设都处理完，才能再次被处理。

§2Bucle infinito con interrupciones M28.3

有的外设很紧急，等不起一整圈。怎么办？Las interrupciones permiten a los periféricos hacer peticiones a la CPU.

让外设自己"举手"：中断。可 M21 §8 已经说过，RTI 要短。于是分工：RTI 只改一个 flag 就返回，主循环周期性地检查这些 flag，flag 说需要时，再做完整的处理。这正是 M21 §8 的 tareas-interrupción 模型。

这里要分清三个概念：

interrupciones

中断与 RTI

对应必须尽快处理的重要事件，所以每个中断的专用代码（RTI）要尽量短、尽量快。默认情况下执行 RTI 时不允许中断嵌套（anidamiento (ES) / nesting (EN)——嵌套），这也是 RTI 必须短的原因。

tareas

任务

tarea (ES) / task (EN)——任务：处理过程太长、太慢，不适合放进 RTI 的代码段，通常与某些中断关联。

interacción

两者怎样配合

靠 flag：每个 tarea 有一个 flag，由需要执行它的那个中断置位。

哪些中断需要 tarea？

  • 处理短而快的：在 RTI 里直接做完，不需要额外的 tarea。
  • 处理长而慢的：需要一个 tarea 来做，RTI 只负责激活这个 tarea（置它的 flag）。
volatile unsigned char flag_1 = 0, flag_2 = 0;   // 每个 tarea 一个 flag inicializar_perifericos();while (1) {    if (flag_1) { tarea_1(); flag_1 = 0; }      // 先 atender，再 borrar flag    if (flag_2) { tarea_2(); flag_2 = 0; }      // 长处理放在主循环} /* RTI A：只置 flag 就返回      RTI C：短处理，直接在 RTI 里做完 */
补充

清 flag 的时机：Escena 2 的流程是先处理、后清 flag。如果 tarea 执行期间同一个外设又来了中断，RTI 重新置的 flag 会被随后的"borrar"清掉，这次事件就丢了。所以实际代码里常常先清 flag，再执行 tarea。

中断负责"尽快知道"，主循环负责"慢慢做完"。RTI 置 flag、主循环查 flag 执行 tarea 再清 flag；短处理可以直接留在 RTI 里。

§3Bucle infinito con bajo consumo e interrupciones M28.4

火灾探测器每 4–5 秒看一眼传感器就够了。其余时间，CPU 在干什么？La mayor parte del tiempo, dando vueltas sin hacer nada.

看一个例子：火灾探测。CPU 不必一直盯着传感器，每 4 到 5 秒查一次就绰绰有余；每次查只要毫秒级的时间。火灾是罕见事件，绝大多数时候结果都是"没事"，CPU 又要等 4–5 秒才需要再查。

代码骨架（示意）。主循环和 RTI 分开看：

inicializar_perifericos();                 // 包括那个周期性产生中断的外设while (1) {    __bis_SR_register(LPM3_bits + GIE);    // 睡：CPU 停，外设继续（见 M26）    if (flag_sensor) {                      // 被叫醒后从这里继续        leer_sensor();                       // ≈ ms        flag_sensor = 0;                       // 先 atender，再 borrar flag    }}
#pragma vector=TIMER0_A0_VECTOR              // 示意：用定时器做周期唤醒__interrupt void RTI_periodica(void) {    flag_sensor = 1;                           // 只置 flag    __bic_SR_register_on_exit(LPM3_bits);   // 改栈上保存的 SR：返回后 CPU 醒着}
怎样醒着返回

如果中断的处理需要通过一个 tarea 完成，就在 RTI 里让 CPU 退出低功耗状态，办法是修改保存在栈（pila）上的 SR。原因：进入 RTI 时 SR 被压栈，RETI 再把它恢复（见 M21 §3）；不改的话，恢复的就是睡前的 SR，CPU 返回后接着睡。反过来推：处理在 RTI 里就能做完的中断不必改 SR，返回后 CPU 继续睡。

补充

上面的 LPM3_bits、__bis_SR_register、__bic_SR_register_on_exit 和定时器向量是 MSP430 C 编译器的常见写法：__bic_SR_register_on_exit 改的正是栈上保存的那份 SR。进入 RTI 时 SR 被清零（SCG0 除外），所以 RTI 本身总是醒着执行的。各个 LPM 模式关掉什么、怎样唤醒，见 M26 Modos de bajo consumo。

没事做的时候，与其空转，不如睡觉。CPU 睡在低功耗状态里，外设在需要时用中断叫醒它；需要 tarea 的 RTI 修改栈上的 SR，让 CPU 醒着返回。其余和 §2 一样。

§4Arquitectura de planificador M28.5

外设 2 的任务正在执行，更重要的外设 1 来了中断。它要等多久？El problema de prioridades entre tareas.

§3 的架构优化了 CPU 的时间，却没有解决任务之间的优先级：正在执行外设 2 的任务时，优先级更高的外设 1 中断了，可在其他外设都处理完之前，外设 1 不会被处理。最直接的办法是把外设 1 的任务搬进它的 RTI——看看会怎样：

当应用需要给各个外设的处理任务不同的优先级时，更合适的是 planificador (ES) / scheduler (EN)——调度器架构。原理很简单：无限循环依次执行一个函数队列（cola de funciones）里的函数，而中断负责往队列里添加函数。关键在于：中断不一定把函数加到队尾，可以按优先级或紧急程度插到前面。

int main(void) {    inicializar_cola(&cola);          // 先准备好函数队列……    inicializar_perifericos();        // ……再初始化外设（之后随时可能来中断）    while (1) {        if (!cola_vacia(&cola)) {            funcion_t f = sacar_primera(&cola);   // 取队首            f();                                  // 执行完才会取下一个        }    }}
__interrupt void RTI_P1(void) {    // Añadir función 1 a la cola → Retorno de interrupción    // 不一定放队尾：按优先级插入    insertar_por_prioridad(&cola, atender_p1, PRIO_ALTA);}
补充

函数名都是示意。实际实现时，队列同时被 RTI 和主循环修改，主循环取函数的那几条指令一般要短暂关中断，避免两边同时改队列。

Planificador：无限循环执行函数队列，中断往队列里按优先级或紧急程度插入函数。任务有了优先级，RTI 也保持短；但正在执行的函数不能被打断。

§5Sistema operativo en tiempo real M28.6

如果连"等当前任务做完"都等不起呢？Una tarea en ejecución puede ser interrumpida por otra que debe ejecutarse inmediatamente.

有些应用要求：正在执行的任务能被另一个必须立即执行的任务打断。调度器做不到，这时通常用 RTOS, Real Time Operating System (EN) / sistema operativo en tiempo real (ES)——实时操作系统。RTOS 一般不自己写，而是作为商业产品购买。

int main(void) {                   // 主程序只做初始化    inicializar_perifericos();    inicializar_tareas();    inicializar_RTOS();           // 之后 CPU 由 RTOS 调度，main 没有自己的循环} void tarea_p1(void) {               // 每个任务都是一个无限循环    for (;;) {        esperar_senal(S_P1);        // 伪 API：等中断发来的信号        atender_p1();    }} __interrupt void RTI_P1(void) {    enviar_senal(S_P1);             // Enviar Señal 1 → 告诉 RTOS：tarea_p1 需要执行}
补充

esperar_senal、enviar_senal 是为了说明而编的名字。真实 RTOS 的 inicializar_RTOS() 一般就是启动调度器，调用后不再返回。实际的 RTOS 用信号量（semáforo / semaphore）、任务通知等机制，而高优先级任务打断低优先级任务的做法一般叫 expropiación (ES) / preemption (EN)——抢占。

往后看

硕士的 MicroKernels（MICROK）这门课专门讲用这种架构设计应用。

RTOS：主程序只做初始化（periféricos → tareas → RTOS）；中断向 RTOS 发信号；RTOS 根据该任务的优先级，立即执行它，或者等当前任务做完。每个任务都是一个无限循环。功能最强，但要消耗 CPU 和内存。

§6同一组事件，五种架构 M28.2–M28.6

把同样的事件交给五种架构，谁先响应？谁让紧急任务等得最久？谁能睡觉？Misma carga, cinco arquitecturas.

三个外设：P1 最紧急（优先级最高，任务 3 u），P2（6 u），P3（4 u）。RTI 都很短（1 u）。选一种架构，看 CPU 时间线；在时间轴上放几个事件，再换一种架构比较。下面的表格同时给出五种架构的结果。

  • P1 任务等待：P1 的事件发生到它的任务开始执行的时间。

试试看

只放一个 P2 事件和紧跟其后的一个 P1 事件（例如 t = 10 和 t = 12），依次切换 1 → 5：架构 2、3 把"首次响应"降到 0，但 P1 的任务照样排队；架构 3 多出了睡眠；架构 4 让 P1 插队，但仍要等 P2 做完；只有架构 5 让 P1 立刻执行。

自测 13 题

根据本章内容编写的练习题。每题只能点一次，答完会显示解析。

01按复杂度从低到高，本章的 5 种架构顺序是？

B。按 §1–§5 的顺序，复杂度逐级升高（§0）。

02选择哪种程序架构，主要取决于什么？

D。前提是微控制器具备相应能力（中断、低功耗、内存和速度）；在此之上看功能和资源约束（§0）。

03在 bucle infinito 架构中，外设需要处理时是怎样被发现的？

A。不是外设打断 CPU，而是 CPU 去轮询每个可能需要处理的外设（§1）。

04某个外设需要非常紧急地被处理。bucle infinito 为什么不合适？

C。循环必须先转完一整圈（§1）。简单恰恰是它的优点。

05在 bucle infinito con interrupciones 中，处理过程又长又慢的中断，它的 RTI 应该做什么？

B。RTI 只负责激活 tarea（置 flag）；长处理由主循环里的 tarea 完成（§2）。

06哪一类中断不需要关联 tarea？

D。是否需要 tarea 取决于处理量：短而快的留在 RTI，长而慢的交给 tarea（§2）。

07为什么强调 RTI 必须尽量短？

A。默认没有 anidamiento，所以 RTI 越长，其他中断被挡得越久（§2、§4）。

08火灾探测器为什么不适合用 bucle infinito？

C。这正是加入低功耗的理由（§3）。

09bucle infinito con bajo consumo e interrupciones 和 bucle infinito con interrupciones 的区别是？

B。这种架构和上一种类似，只是无限循环换成了 CPU 睡眠的低功耗状态。相应地，需要 tarea 的 RTI 要让 CPU 醒着返回（见下一题；§3）。

10在 bucle infinito con bajo consumo e interrupciones 中，某个中断的处理要交给 tarea 完成。按 §3 的流程，RTI 怎样让 CPU 退出低功耗？

C。进入 RTI 时 SR 被压栈，RETI 会把它恢复；不改的话恢复的是睡前的 SR，CPU 返回后接着睡（所以 A 错）。处理在 RTI 里就能做完的中断不需要这样做（§3）。

11为了让 P1 的任务优先，把它直接搬进 P1 的 RTI。问题是？

C。这可能是一个更大的问题，所以需要 planificador（§4）。

12planificador 架构的关键是什么？

A。B 和 C 是 RTOS 的特点，D 是 bucle infinito（§4）。

13RTOS 架构中，中断发生后会怎样？

D。此外，RTOS 要消耗 CPU 和内存；MSP430 中只有资源较多的器件（如 F5529）能用（§5）。
