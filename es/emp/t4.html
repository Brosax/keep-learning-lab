Comunicaciones: sockets

Sockets: comunicación entre aplicaciones locales y la red

10 Objetivos clave Lectura aprox. 25 min

Una vez que una Raspberry Pi con Linux se conecta mediante cable de red o Wi-Fi, ¿cómo intercambian datos las aplicaciones con la red? Casi todos los sistemas operativos modernos ofrecen la misma respuesta: socket (conector de red). Funciona como un descriptor de fichero ordinario: admite read, write y close; pero entre bastidores, el kernel gestiona el empaquetado, direccionamiento, retransmisión y ordenación de los datos. Este tema examina primero el empaquetado progresivo en capas, desglosa paso a paso las llamadas al sistema en servidores y clientes TCP y UDP, y analiza la estructura de los mensajes HTTP.

§1Capas y direcciones T4.1 · T4.2

Un programa solo escribe cuatro bytes "hola", pero por el cable viaja un paquete de decenas de bytes. ¿Qué se ha añadido?Cada capa añade su propia cabecera.

El software de red se organiza en capas. El modelo de referencia OSI define 7 capas (Física, Enlace, Red, Transporte, Sesión, Presentación, Aplicación); en la práctica, TCP/IP define 4 capas, integrando las tres superiores de OSI en el "nivel de aplicación" y las dos inferiores en el "nivel de enlace". Cada nivel interactúa únicamente con sus niveles adyacentes y antepone a los datos su propia cabecera (header), en un proceso denominado encapsulado (encapsulation).

Los cinco parámetros de una comunicación

Una comunicación entre dos procesos queda definida unívocamente por cinco datos:

ProtocoloIP origenPuerto origenIP destinoPuerto destino
tcp192.168.0.11200192.168.0.21500

Una dirección IP (IP address) identifica un host (más exactamente, una interfaz de red): IPv4 utiliza 32 bits representados en notación punto-decimal como 10.12.110.57; IPv6 utiliza 128 bits como 2001:db8:63b3:1::3490. Un puerto (port) es un entero de 16 bits (0–65535) que identifica un proceso o servicio concreto dentro de la máquina. Por ejemplo, un servidor web HTTP escucha por convención en el puerto 80.

Dos formas de obtener un puerto

  • Puerto fijo: la aplicación selecciona un número y lo vincula con bind. Imprescindible en servidores para que los clientes sepan a qué puerto dirigirse. Debe evitarse colisionar con puertos ya ocupados.
  • Asignado por el kernel: se especifica puerto 0 en bind o se omite esta llamada; el kernel selecciona un puerto libre del rango de puertos dinámicos (ephemeral ports). Es el mecanismo habitual en clientes.

Rangos de puertos

  • Por debajo de 1024: reservados para servicios conocidos del sistema (ftp, ssh, http...), requiriendo permisos de superusuario para vincularlos en Linux.
  • El rango de puertos efímeros depende del sistema operativo; en Linux puede consultarse en /proc/sys/net/ipv4/ip_local_port_range.
  • Para servicios propios, elija un puerto superior a 1024 que no esté ocupado. Los ejemplos de este tema emplean 5005 (TCP), 6006 (UDP) y 7070 (HTTP).
Cliente y servidor

servidor (server): se inicia primero y permanece a la espera en un puerto conocido; cliente (client): inicia la comunicación de forma activa. En TCP el orden de llamadas de ambos roles es completamente distinto (§4, §5); en UDP las llamadas son prácticamente idénticas, denominando cliente al extremo que transmite primero (§6).

§2¿Qué es un socket? T4.3

¿Cómo puede un simple número entero representar una conexión de red activa?socket() devuelve un descriptor, como un fichero.

En Linux, un socket se gestiona igual que un fichero mediante un descriptor de fichero (file descriptor): un entero no negativo que indexa la tabla de ficheros abiertos del proceso. Gracias a ello, llamadas como read, write o close funcionan de manera idéntica sobre sockets. Su creación se realiza mediante una única llamada al sistema:

#include <sys/types.h>#include <sys/socket.h> int socket(int domain, int type, int protocol);   // Éxito: descriptor ≥ 0; error: -1 con errno
ParámetroValores habitualesSignificado
domainAF_INET · AF_INET6 · AF_UNIX (= AF_LOCAL)Familia de direcciones: determina si se usa IPv4, IPv6 o comunicación local entre procesos en la misma máquina. Define qué estructura de dirección usar.
typeSOCK_STREAM · SOCK_DGRAMSemántica: flujo de bytes orientado a conexión (circuito virtual) o datagramas sin conexión (datagrama).
protocol0Indicar 0 selecciona el protocolo por defecto: STREAM → TCP, DGRAM → UDP. Puede fijarse explícitamente, p. ej. IPPROTO_SCTP.

SOCK_STREAM · TCP

orientado a conexión (connection-oriented): requiere establecer una sesión antes de transmitir. El kernel gestiona retransmisión por pérdidas, ordenación y eliminación de duplicados; la aplicación observa un flujo de bytes fiable y secuencial. El control del protocolo reside enteramente en el kernel.

SOCK_DGRAM · UDP

no orientado a conexión (connectionless): envía mensajes directamente sin negociación previa. No ofrece retransmisiones automáticas ni garantías de orden; si se precisa fiabilidad, debe programarse en la capa de aplicación. Cada envío constituye un datagrama independiente.

int s = socket(AF_INET, SOCK_STREAM, 0);   // IPv4 + TCPif (s == -1) {    perror("socket");                     // Muestra la causa del error    exit(EXIT_FAILURE);}

PF_INET (Protocol Family) y AF_INET (Address Family) tienen el mismo valor en Linux; muchos proyectos usan PF_ en socket() y AF_ en estructuras de dirección; ambos funcionan indistintamente.

No olvide AF_UNIX

Los sockets AF_UNIX comunican procesos dentro de la misma máquina mediante una ruta del sistema de ficheros (campo sun_path en struct sockaddr_un). Cada vez más servicios del sistema los utilizan por su alto rendimiento y por emplear la misma API estándar que los sockets de red.

§3Direcciones y orden de bytes T4.4

Configuró el puerto 5005, pero el servidor espera conexiones en el 36115. ¿Por qué ocurre esto?¡¡¡Atención!!! formato red y formato máquina.

Todas las llamadas con direcciones (bind, connect, accept, sendto, recvfrom) aceptan un puntero genérico struct sockaddr *, deduciendo el formato real mediante el primer campo (la familia). Para IPv4 la estructura concreta es sockaddr_in, convirtiendo el puntero con un cast a sockaddr *:

struct sockaddr {                 // Genérico: para paso de parámetros    sa_family_t sa_family;         // AF_xxx    char        sa_data[14];}; struct sockaddr_in {              // IPv4, <netinet/in.h>    sa_family_t    sin_family;     // AF_INET    in_port_t      sin_port;       // Puerto, formato red    struct in_addr sin_addr;       // { uint32_t s_addr; } IP, formato red    unsigned char  sin_zero[8];    // Relleno a ceros, iguala tamaño a sockaddr};

IPv6 emplea sockaddr_in6 (sin6_family = AF_INET6, dirección de 16 bytes in6_addr, con flowinfo y scope_id); para alojar cualquiera de las dos familias se utiliza struct sockaddr_storage.

formato red · formato máquina

Los enteros multibyte pueden almacenarse en memoria bajo dos ordenaciones: big endian (byte más significativo en la dirección más baja) y little endian (byte menos significativo en la dirección más baja). Los protocolos de red establecen que puertos y direcciones viajan siempre en orden big endian, denominado formato red (network byte order). Sin embargo, arquitecturas como Intel y ARM de Raspberry Pi operan en little endian (formato máquina). Observe cómo reside el puerto 5005 en memoria:

Función (<arpa/inet.h>)SentidoUso típico
uint16_t htons(uint16_t)Host → Red, 16 bitsPuertos: sin_port = htons(5005)
uint32_t htonl(uint32_t)Host → Red, 32 bitsConstantes IPv4: sin_addr.s_addr = htonl(INADDR_ANY)
uint16_t ntohs(uint16_t)Red → Host, 16 bitsImprimir puerto recibido: ntohs(cli.sin_port)
uint32_t ntohl(uint32_t)Red → Host, 32 bitsComparar o calcular direcciones IP numéricas

Direcciones en texto ↔ Binario

En el código se manejan cadenas como "192.168.1.20", mientras que sin_addr requiere 4 bytes en formato red. Las conversiones se realizan con inet_pton (presentation → network) y inet_ntop, compatibles con IPv4 e IPv6 mediante punteros:

struct sockaddr_in dst;memset(&dst, 0, sizeof dst);                  // Pone sin_zero a cerodst.sin_family = AF_INET;dst.sin_port   = htons(5005);if (inet_pton(AF_INET, "192.168.1.20", &dst.sin_addr) != 1)    /* 1 = éxito; 0 = cadena inválida; -1 = familia no soportada */; char txt[INET_ADDRSTRLEN];                     // 16 bytes para "255.255.255.255"inet_ntop(AF_INET, &dst.sin_addr, txt, sizeof txt);printf("%s:%u\n", txt, ntohs(dst.sin_port));   // 192.168.1.20:5005
  • Las funciones antiguas inet_addr e inet_ntoa solo admiten IPv4 y presentan ambigüedad con "255.255.255.255"; en código moderno se usan siempre pton y ntop.
  • INADDR_ANY (valor 0) representa "cualquier interfaz de este equipo": al vincularlo (bind), el servidor atenderá peticiones dirigidas a cualquiera de sus tarjetas de red en el puerto indicado.
  • getaddrinfo("www.example.com", "http", &hints, &res) resuelve nombres de host y servicios devolviendo una lista enlazada de direcciones lista para usar en socket/connect; se libera con freeaddrinfo. La operación inversa es getnameinfo.
Aviso · Notación en la literatura

Algunos manuales señalan que tras inet_addr("192.168.0.1") el campo s_addr vale 0xC0A80001: dicho valor corresponde a la lectura directa en formato red (de izquierda a derecha). En una CPU little-endian como Raspberry Pi, printf("%x", s_addr) muestra 0x0100A8C0; únicamente tras aplicar ntohl(s_addr) se obtiene 0xC0A80001.

§4Servidor TCP T4.5 · T4.6

Un servidor atiende a un cliente en el puerto 5005. Cuando llega un segundo cliente, ¿puede conectarse?socket → bind → listen → accept → read / write → close.

Un servidor orientado a conexión ejecuta cuatro fases iniciales indispensables: socket abre el canal de comunicación, bind publica la dirección local, listen declara la disposición a admitir conexiones y accept extrae una conexión confirmada. La siguiente cronología sincroniza las operaciones de servidor y cliente:

Parámetros de las llamadas

LlamadaComportamiento y detalles
bind(fd, addr, len)Asigna una dirección local y puerto al socket. Obligatorio en servidores para que los clientes dispongan de un punto de contacto conocido. Innecesario en clientes orientados a conexión.
listen(fd, backlog)Exclusivo de TCP. Habilita la cola de peticiones; backlog especifica el límite de conexiones completadas pendientes de accept (habitualmente 5–10).
accept(fd, addr, &len)Extrae la primera conexión de la cola y retorna un nuevo descriptor; bloquea si está vacía. addr almacena la dirección del cliente remoto; len es parámetro de entrada/salida (tamaño inicial de la estructura, longitud real al volver). Si no interesa la dirección remota pueden pasarse como NULL. Devuelve -1 ante error.
read / writeTransfieren datos a través del descriptor devuelto por accept (§5).
close(fd)Finaliza la conexión y libera los recursos del sistema (§7).

Implementación de un servidor iterativo mínimo: procesa un cliente cada vez, atendiendo al siguiente una vez finalizada la sesión previa. Convierte a mayúsculas el texto recibido:

int main(void) {    int lfd = socket(AF_INET, SOCK_STREAM, 0);    if (lfd < 0) { perror("socket"); return 1; }    int on = 1;    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);   // Véase §7     struct sockaddr_in me;    memset(&me, 0, sizeof me);    me.sin_family      = AF_INET;    me.sin_addr.s_addr = htonl(INADDR_ANY);   // Cualquier interfaz    me.sin_port        = htons(5005);    if (bind(lfd, (struct sockaddr *)&me, sizeof me) < 0) { perror("bind"); return 1; }    if (listen(lfd, 5) < 0) { perror("listen"); return 1; }     for (;;) {        struct sockaddr_in peer;        socklen_t plen = sizeof peer;            // Tamaño de estructura como entrada        int cfd = accept(lfd, (struct sockaddr *)&peer, &plen);   // Bloqueante        if (cfd < 0) { perror("accept"); continue; }         char buf[128];        ssize_t n;        while ((n = read(cfd, buf, sizeof buf)) > 0) {   // 0 = cliente cerró, -1 = error            for (ssize_t i = 0; i < n; i++) buf[i] = toupper((unsigned char)buf[i]);            write_all(cfd, buf, n);                // Función auxiliar descrita en §5        }        close(cfd);                                // Cierra este cliente; lfd sigue escuchando    }}

Cabeceras requeridas: <sys/socket.h>, <netinet/in.h>, <arpa/inet.h>, <unistd.h>, <string.h>, <ctype.h>, <stdio.h>. Mientras este servidor procesa un cliente, otro puede completar el handshake y esperar en cola; para concurrencia simultánea véase §7.

Aviso · Puerto del nuevo socket

Algunas fuentes señalan que accept genera un descriptor con un puerto reasignado dinámicamente para dejar libre el puerto de escucha. Con rigor, el puerto local del nuevo socket sigue siendo 5005: el kernel diferencia conexiones mediante la 4-tupla (IP local, puerto local, IP remota, puerto remoto). La conclusión práctica no cambia: accept retorna un descriptor nuevo independiente mientras el socket de escucha original permanece disponible.

§5Cliente TCP y flujo de bytes T4.7

El cliente ejecuta write dos veces. ¿El servidor realizará necesariamente dos lecturas?TCP es un flujo de bytes: no conserva los límites de los mensajes.

Un cliente TCP requiere únicamente dos pasos: socket y a continuación connect hacia el servidor. La llamada connect suspende la ejecución hasta consolidar la sesión (devuelve 0) o fracasar (retorna -1, p. ej. sin proceso en escucha). No precisa bind: el kernel selecciona automáticamente un puerto dinámico al conectar y lo conserva durante toda la sesión.

int fd = socket(AF_INET, SOCK_STREAM, 0);struct sockaddr_in srv;memset(&srv, 0, sizeof srv);srv.sin_family = AF_INET;srv.sin_port   = htons(5005);inet_pton(AF_INET, "192.168.1.20", &srv.sin_addr);if (connect(fd, (struct sockaddr *)&srv, sizeof srv) < 0) {   // Bloquea hasta completar handshake    perror("connect");                       // P. ej. Connection refused    return 1;}write_all(fd, "hola\n", 5);char buf[64];ssize_t n = read(fd, buf, sizeof buf);close(fd);

Los tres valores devueltos por read y recv

> 0

Lectura de n bytes

n puede ser menor que el tamaño solicitado: proporciona exclusivamente los datos ya recibidos en el búfer.

= 0

Extremo remoto desconectado

Fin de flujo (EOF). No llegarán más datos; procede invocar close en el extremo local.

= -1

Condición de error

Consultar errno y registrar el motivo con perror().

recv(fd, buf, len, flags) y send(fd, buf, len, flags) proporcionan opciones específicas para sockets; con flags en 0 equivalen a read/write. Flags destacados: MSG_PEEK (inspecciona datos manteniéndolos en cola), MSG_OOB (datos urgentes fuera de banda), MSG_NOSIGNAL (§7). Asimismo, send/write pueden aceptar un número de bytes menor al solicitado.

TCP proporciona a la aplicación un flujo de bytes (byte stream): asegura recepción ordenada, sin pérdidas ni duplicados, pero no preserva la frontera de cada operación write:

Al emitir datos rige el mismo principio: write puede transmitir solo una porción del búfer, requiriendo un bucle de escritura completa:

/* Transmite len bytes íntegramente; éxito: 0, error: -1 */int write_all(int fd, const void *p, size_t len) {    const char *c = p;    while (len > 0) {        ssize_t n = write(fd, c, len);        if (n < 0) {            if (errno == EINTR) continue;   // Interrumpido por señal: reintentar            return -1;        }        c += n; len -= n;                   // Escritura parcial: avanzar puntero    }    return 0;}

TCP garantiza la transmisión íntegra y ordenada de bytes, no de mensajes completos. Lecturas y escrituras pueden resultar parciales; delimitar el inicio y conclusión de cada mensaje corresponde a la aplicación.

§6UDP: un datagrama por operación T4.8

Sin conexión previa, ¿cómo sabe el receptor quién ha enviado el mensaje y cómo responderle?sendto() y recvfrom() llevan la dirección en cada llamada.

UDP prescinde de listen, accept y connect: ambos extremos configuran socket(AF_INET, SOCK_DGRAM, 0), vinculando con bind únicamente quien desea recibir en un puerto prefijado. Al carecer de conexión persistente, cada emisión requiere especificar la dirección de destino y cada recepción captura la dirección del remitente:

ssize_t sendto(int fd, const void *buf, size_t len, int flags,               const struct sockaddr *to, socklen_t tolen);      // Envío a destino 'to'ssize_t recvfrom(int fd, void *buf, size_t len, int flags,                 struct sockaddr *from, socklen_t *fromlen);      // 'from' captura remitente

fromlen actúa como parámetro de entrada/salida. El receptor puede remitir una respuesta reutilizando directamente from en sendto. Ambas funciones retornan la cantidad de bytes transferidos o -1 ante fallo; en UDP un retorno de 0 denota un datagrama vacío, no un fin de conexión.

Receptor de ejemplo: escucha datagramas en el puerto 6006 y muestra contenido y remitente:

int fd = socket(AF_INET, SOCK_DGRAM, 0);struct sockaddr_in me;memset(&me, 0, sizeof me);me.sin_family = AF_INET;me.sin_addr.s_addr = htonl(INADDR_ANY);me.sin_port = htons(6006);bind(fd, (struct sockaddr *)&me, sizeof me);         // Recepción en puerto conocido for (;;) {    char buf[1500];                                   // ≥ Tamaño máximo de datagrama    struct sockaddr_in from;    socklen_t flen = sizeof from;    ssize_t n = recvfrom(fd, buf, sizeof buf, 0, (struct sockaddr *)&from, &flen);    if (n < 0) { perror("recvfrom"); continue; }    char ip[INET_ADDRSTRLEN];    inet_ntop(AF_INET, &from.sin_addr, ip, sizeof ip);    printf("%zd bytes de %s:%u: %.*s\n", n, ip, ntohs(from.sin_port), (int)n, buf);}

El emisor prescinde de bind si solo emite; al invocar sendto con la dirección destino, el kernel le asigna un puerto efímero. Es posible invocar connect en sockets UDP para registrar una dirección remota por defecto y simplificar llamadas con send/recv.

¿Cuándo usar TCP o UDP?

CaracterísticaTCP · SOCK_STREAMUDP · SOCK_DGRAM
ConexiónEstablecimiento previo con 3-way handshakeSin conexión, emisión directa
FiabilidadRetransmisión, orden secuencial, sin duplicadosPosible pérdida, desorden o duplicación
FronterasFlujo de bytes continuo, sin límites de mensajeDatagramas delimitados; truncamiento descarta sobrante
Operacionesread/write o recv/sendsendto/recvfrom (o send/recv tras connect)
ControlMonopolizado por el protocolo en el kernelBajo control directo de la aplicación
Ámbito óptimoIntegridad estricta: ficheros, web, comandosTiempo real y control: latencia predecible y baja sobrecarga

TCP constituye la opción estándar general, pero resulta inadecuado en tiempo real estricto: la pérdida de un paquete detiene la llegada de los subsiguientes hasta culminar la retransmisión, introduciendo fluctuaciones inaceptables. UDP traslada el control a la aplicación, permitiendo decidir si un dato retrasado debe descartarse en favor de la muestra más reciente. En caso de requerir control sobre cabeceras IP se recurre a raw sockets.

§7Bloqueo, multiplexación y cierre T4.9

El servidor permanece bloqueado en accept, pero necesita atender otras tareas concurrentes. ¿Qué opciones existen?¿Necesitamos multitarea? select como alternativa.

Por defecto las operaciones sobre sockets son bloqueantes (blocking): si las condiciones no se satisfacen, la llamada suspende el hilo de ejecución indefinidamente.

LlamadaCondición de espera
acceptLlegada de una conexión completada a la cola
connect (TCP)Finalización exitosa o fallo del handshake
read / recv / recvfromRecepción de al menos 1 byte (o datagrama), o desconexión remota
write / send (TCP)Espacio libre disponible en el búfer de emisión del kernel

Cuando la aplicación debe atender otras tareas simultáneamente (sensores, interfaz de usuario) o concurrencia de clientes, no puede quedar inmovilizada en una llamada. Existen tres estrategias:

multitarea

Un hilo por cliente

El hilo principal se reserva para accept; al recibir una conexión, lanza un hilo (o proceso con fork) dedicado al descriptor devuelto. Cada hilo opera con llamadas bloqueantes sencillas. Máxima flexibilidad a cambio de sincronizar memoria compartida (Tema 2).

multiplexación

select / poll

Un único hilo supervisa múltiples descriptores: solicita al kernel notificación cuando alguno presente datos disponibles, invocando accept o read únicamente sobre los descriptores listos sin riesgo de bloqueo.

no bloqueante

Modo no bloqueante

Con fcntl(fd, F_SETFL, O_NONBLOCK) el descriptor responde inmediatamente con -1 y errno = EAGAIN/EWOULDBLOCK si la operación no puede completarse de inmediato. Suele combinarse con select.

Algunas fuentes nombran O_NODELAY a este modo; en las cabeceras estándar de Linux se define como O_NONBLOCK.

Un hilo por cliente

static void *atiende(void *arg) {    int cfd = (int)(intptr_t)arg;    /* Atiende peticiones en cfd con read/write bloqueantes... */    close(cfd);    return NULL;} for (;;) {                                       // Hilo principal: recepción de conexiones    int cfd = accept(lfd, NULL, NULL);    if (cfd < 0) continue;    pthread_t th;    pthread_create(&th, NULL, atiende, (void *)(intptr_t)cfd);    pthread_detach(th);                          // Libera recursos al terminar}

select

int select(int nfds, fd_set *readfds, fd_set *writefds,           fd_set *exceptfds, struct timeval *timeout);
  • readfds, writefds y exceptfds representan conjuntos de descriptores a monitorizar (lectura, escritura, excepción), pasando NULL si no aplican. Se manipulan con FD_ZERO, FD_SET, FD_CLR y FD_ISSET.
  • nfds corresponde al descriptor de mayor valor numérico + 1.
  • timeout limita el tiempo de espera; retorna 0 al vencer el plazo; pasando NULL espera indefinidamente.
  • Al retornar, el kernel sobrescribe los conjuntos conservando únicamente los descriptores activos. Por ello debe mantenerse un conjunto maestro y copiarlo en cada ciclo. Un socket de escucha activo indica conexiones pendientes en accept; un socket conectado activo indica datos entrantes o cierre remoto (read retorna 0).
fd_set all, rd;FD_ZERO(&all);FD_SET(lfd, &all);int maxfd = lfd;for (;;) {    rd = all;                                     // select modifica la máscara: copiar en cada ciclo    struct timeval tv = { 1, 500000 };         // 1,5 s de timeout    int r = select(maxfd + 1, &rd, NULL, NULL, &tv);    if (r < 0) { perror("select"); break; }    if (r == 0) { puts("sin actividad"); continue; }   // Temporizador agotado    for (int fd = 0; fd <= maxfd; fd++) {        if (!FD_ISSET(fd, &rd)) continue;        if (fd == lfd) {                          // Nueva conexión: accept no se bloqueará            int c = accept(lfd, NULL, NULL);            if (c >= 0) { FD_SET(c, &all); if (c > maxfd) maxfd = c; }        } else {                                  // Datos listos o desconexión            char buf[256];            ssize_t n = read(fd, buf, sizeof buf);            if (n <= 0) { close(fd); FD_CLR(fd, &all); }            else write_all(fd, buf, n);            // Respuesta directa de eco        }    }}
Criterio de elección

select evita la sobrecarga de múltiples hilos, pero hilos con temporizadores ofrecen mayor modularidad para tareas complejas. Como norma: si el servicio realiza cálculos intensivos o tareas periódicas paralelas, emplee hilos; si reenvía tráfico ligero entre descriptores, select resulta óptimo. poll ofrece funcionalidad semejante empleando un array de estructuras pollfd sin el límite FD_SETSIZE de select.

Cierre del canal: close y shutdown

close(fd)

Interrumpe ambos sentidos de comunicación y libera el descriptor y sus recursos en el kernel. Imprescindible tras concluir la sesión.

shutdown(fd, how)

Cierra selectivamente un sentido: SHUT_RD (0, no más recepciones), SHUT_WR (1, no más emisiones; el par leerá EOF), SHUT_RDWR (2, ambos). No libera el descriptor: requiere invocar close posteriormente.

Buenas prácticas ante desconexión ordenada: ejecutar shutdown(fd, SHUT_RDWR) para notificar el cese y posteriormente close(fd) para reciclar el descriptor.

bind: Address already in use

Al concluir una aplicación, el kernel retiene la conexión en estado TIME_WAIT durante 1 a 2 minutos. Intentar reiniciar el servidor de inmediato genera este error en bind. Solución: activar SO_REUSEADDR antes de invocar bind:

int on = 1;setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);

Omitir close mantiene el puerto bloqueado impidiendo su reutilización.

SIGPIPE

Escribir en un socket TCP cuyo par ya ha cerrado la conexión provoca que el kernel emita la señal SIGPIPE, cuya acción por defecto aborta el proceso. Para evitar la interrupción brusca se añade la opción MSG_NOSIGNAL en el envío, provocando retorno de -1 con errno = EPIPE:

send(fd, buf, len, MSG_NOSIGNAL);sendto(fd, buf, len, MSG_NOSIGNAL, (struct sockaddr *)&to, sizeof to);

Alternativamente puede ignorarse la señal al iniciar el proceso con signal(SIGPIPE, SIG_IGN) (Tema 3).

Otras utilidades de red: getpeername(fd, …) consulta la dirección del extremo remoto en TCP; gethostname(buf, size) obtiene el nombre del equipo; getifaddrs/freeifaddrs enumera todas las interfaces locales (como eth0 o wlan0) con sus correspondientes IPs.

§8Mensajes HTTP T4.10

Un navegador web es simplemente un cliente TCP. ¿Qué contenido envía exactamente por la conexión?HTTP: texto sobre TCP, líneas terminadas en CRLF.

HTTP (HyperText Transfer Protocol) es un protocolo textual sobre TCP: el cliente se conecta al servidor (puerto 80 por omisión, o 7070 en http://192.168.1.20:7070/), transmite una petición y el servidor devuelve una respuesta. Ambos mensajes comparten formato:

  1. Línea inicial: petición o estado;
  2. Cabeceras sucesivas en formato Nombre: valor;
  3. Una línea en blanco;
  4. Cuerpo de datos opcional.

Cada línea concluye estrictamente en CRLF (\r\n). Siguiendo el principio de delimitación de §5, el servidor lee sucesivamente hasta localizar la secuencia \r\n\r\n (línea vacía) que delimita el fin de las cabeceras.

Petición · request

GET /saludo HTTP/1.1\r\nHost: 192.168.1.20:7070\r\nUser-Agent: Mozilla/5.0 …\r\nAccept: text/html\r\n\r\n

Línea de petición = Método + Ruta + Versión. Métodos habituales: GET (recuperar recurso) y POST (envío de datos en el cuerpo). GET prescinde normalmente de cuerpo.

Respuesta · response

HTTP/1.1 200 OK\r\nContent-Type: text/plain; charset=utf-8\r\nContent-Length: 4\r\nConnection: close\r\n\r\nHola

Línea de estado = Versión + Código numérico + Frase explicativa. Códigos usuales: 200 OK, 301 Movido, 400 Formato incorrecto, 404 No encontrado, 500 Error interno del servidor.

CabeceraFunción
HostNombre de host y puerto solicitado (obligatorio en HTTP/1.1)
Content-TypeNaturaleza del cuerpo: text/plain, text/html, application/json…
Content-LengthLongitud exacta del cuerpo en bytes
Connection: closeInforma de que el servidor cerrará la conexión tras este envío

¿Cómo determinar el final del cuerpo?

Las cabeceras terminan con una línea vacía, pero el cuerpo puede contener cualquier dato binario arbitrario. HTTP ofrece tres mecanismos:

  • Content-Length: especifica el número exacto de bytes; el receptor suspende la lectura al alcanzarlos.
  • Cierre de conexión: el servidor cierra el socket tras el cuerpo; read devuelve 0 señalando el final (requiere Connection: close).
  • Codificación fragmentada (Transfer-Encoding: chunked): divide el cuerpo en bloques precedidos de su tamaño, concluyendo con un bloque de 0 bytes.

Generación de una respuesta HTTP mínima en C tras recibir la petición en cfd:

static const char resp[] =    "HTTP/1.1 200 OK\r\n"    "Content-Type: text/plain; charset=utf-8\r\n"    "Content-Length: 4\r\n"                  // "Hola" = 4 bytes    "Connection: close\r\n"    "\r\n"                                    // Línea vacía: concluyen cabeceras    "Hola";write_all(cfd, resp, sizeof resp - 1);     // Se omite el '\0' finalclose(cfd);

Content-Length contabiliza bytes físicos: caracteres multibyte UTF-8 como "ñ" o acentos ocupan 2 bytes cada uno.

Preguntas de repaso 12 preguntas

Cuestiones de repaso sobre los contenidos del tema. Seleccione una opción para visualizar la explicación razonada.

01¿Qué nivel de la arquitectura de red proporciona la interfaz de sockets a las aplicaciones?

B. Los sockets se sitúan entre el nivel de aplicación y el nivel de transporte; no obstante, la familia de direcciones y el tipo de conexión deben indicarse al crearlo (§1).

02En una Raspberry Pi little-endian, ¿qué valor se obtiene al leer con formato máquina el resultado de htons(5005) (5005 = 0x138D)?

C. htons intercambia ambos bytes (no invierte los dígitos hexadecimales), situando 0x13 en la dirección más baja para coincidir con el formato red (§3).

03¿Cuál de las siguientes inicializaciones de sockaddr_in es correcta para un servidor que escucha en el puerto 5005 en cualquier dirección local?

A. sin_family indica la familia de direcciones (AF_INET) y el puerto debe convertirse a formato red con htons (§3).

04¿Qué llamada al sistema es exclusiva de servidores TCP y ordena al kernel comenzar a encolar solicitudes de conexión entrantes?

D. listen habilita el socket en modo pasivo y fija la capacidad de la cola mediante backlog; accept extrae las conexiones ya completadas (§4).

05Respecto al enlace en tres vías (three-way handshake) y accept, ¿cuál de las siguientes afirmaciones es correcta?

B. El socket de escucha original permanece operativo y disponible, mientras que la comunicación de datos transcurre por el nuevo descriptor devuelto por accept (§4).

06En una conexión TCP establecida, ¿qué indica que read(fd, buf, 100) devuelva 0?

C. Un valor > 0 indica bytes leídos, 0 representa fin de conexión y -1 indica error. En modo bloqueante, si no hay datos disponibles read espera en lugar de retornar (§5, §7).

07Un cliente TCP ejecuta write(fd, "ABC", 3) y a continuación write(fd, "DEFG", 4). Si el servidor realiza una lectura con read(fd, buf, 100), ¿qué resultado puede obtener?

D. TCP es un flujo continuo de bytes sin delimitadores de mensaje intrínsecos; la aplicación debe leer en bucle y emplear delimitadores o prefijos de longitud (§5).

08Un emisor UDP transmite un datagrama de 1000 bytes y el receptor invoca recvfrom(fd, buf, 500, 0, …). ¿Cuál es el resultado?

A. Cada datagrama constituye una unidad atómica e indivisible; si el búfer resulta insuficiente, el contenido sobrante se descarta de forma irrecuperable (§6).

09¿Cuál de las siguientes entidades no requiere habitualmente invocar bind?

C. Al invocar connect, el kernel asigna automáticamente un puerto dinámico al cliente; los servidores y receptores UDP precisan un puerto prefijado (§4, §5, §6).

10Al monitorizar múltiples descriptores con select, ¿por qué es necesario reinicializar el conjunto de descriptores en cada iteración del bucle?

B. select sobrescribe la máscara; el patrón de diseño estándar mantiene una máscara maestra y transfiere una copia en cada llamada (§7).

11Un servidor escribe en un socket cuyo cliente ya ha cerrado la conexión y el proceso del servidor finaliza de forma abrupta. ¿Cuál es la causa y la solución?

A. SO_REUSEADDR solventa el aviso de dirección ya en uso tras reiniciar; la finalización abrupta al escribir se debe a SIGPIPE (§7).

12En una respuesta HTTP/1.1, ¿qué elemento delimita la separación entre las cabeceras y el cuerpo del mensaje?

D. El cuerpo se inicia tras la línea vacía (CRLF doble); su finalización se determina mediante Content-Length, chunked o cierre del canal (§8).
