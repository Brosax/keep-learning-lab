Comunicaciones: sockets

套接字：让板子上的程序和网络另一端的程序说话

10 个要点 阅读约 25 分钟

一块跑 Linux 的 Raspberry Pi 接上网线或 Wi-Fi 之后，程序要怎样把数据交给网络、又怎样从网络上收数据？几乎所有现代操作系统给出的答案都一样：socket (EN) / conector (ES)——套接字。它像一个文件描述符：可以 read、write、close；但在它背后，内核替你完成了分包、编址、重传和排序。这一章先看数据在网络里怎样一层层包装，再把 TCP 服务器、TCP 客户端和 UDP 的系统调用一个一个拆开，最后看一条 HTTP 报文长什么样。

§1分层与地址 T4.1 · T4.2

程序只写了四个字节 "hola"，网线上跑的却是一个几十字节的包。多出来的是什么？Cada capa añade su propia cabecera.

网络软件按层组织。OSI 参考模型分 7 层（Físico、Enlace、Red、Transporte、Sesión、Presentación、Aplicación）；实际在用的 TCP/IP 只分 4 层，把 OSI 的上三层合成"应用层"，把下两层合成"链路层"。每层只和相邻的层打交道，并在数据前面加上自己的 cabecera (ES) / header (EN)——首部，这个过程叫 encapsulado (ES) / encapsulation (EN)——封装。

通信要知道的五件事

两个程序之间的一条通信，由五项信息确定：

协议源 IP源端口目的 IP目的端口
tcp192.168.0.11200192.168.0.21500

dirección IP (ES) / IP address (EN)——IP 地址标识一台机器（准确地说是机器上的一个网络接口）：IPv4 是 32 位，写成 10.12.110.57 这样的点分十进制；IPv6 是 128 位，写成 2001:db8:63b3:1::3490。puerto (ES) / port (EN)——端口是 16 位的数（0–65535），标识机器里的一个程序或服务。例如 HTTP 服务器按惯例监听 80 端口。

两种拿到端口的方式

  • 固定端口：程序自己选一个号，用 bind 绑上。服务器必须这样做，否则客户端不知道去哪里找它。注意别和系统已占用的端口冲突。
  • 由系统分配：bind 时端口写 0，或者干脆不调用 bind，内核会从 puertos dinámicos (ES) / ephemeral ports (EN)——临时端口里挑一个空闲的。客户端通常这样做。

端口号的分区

  • 1024 以下是给知名服务保留的（ftp、ssh、http……），在 Linux 上绑定它们需要超级用户权限。
  • 临时端口的范围由操作系统决定，各系统不同；Linux 上可以查看 /proc/sys/net/ipv4/ip_local_port_range。
  • 自己写的服务，挑一个 1024 以上、没有被别的程序占用的端口就行。本章的例子用 5005（TCP）、6006（UDP）和 7070（HTTP）。
客户端与服务器

servidor (ES) / server (EN)——服务器：先启动，在一个已知的端口上等待；cliente (ES) / client (EN)——客户端：主动发起通信。TCP 里这两个角色的调用顺序完全不同（§4、§5）；UDP 里两边的调用几乎一样，只是把先开口的一方叫客户端（§6）。

§2套接字是什么 T4.3

一个 int，为什么就能代表一条网络连接？socket() devuelve un descriptor, como un fichero.

在 Linux 里，套接字和文件一样，用一个descriptor (ES) / file descriptor (EN)——文件描述符来引用：一个小的非负整数，是进程打开文件表里的下标。正因为如此，read、write、close 这些文件调用也能直接用在套接字上。创建它的调用只有一个：

#include <sys/types.h>#include <sys/socket.h> int socket(int domain, int type, int protocol);   // 成功：描述符 ≥ 0；失败：-1，并设置 errno
参数常用取值含义
domainAF_INET · AF_INET6 · AF_UNIX（= AF_LOCAL）地址族：用 IPv4、IPv6，还是同一台机器上的本地通信。它决定了后面用哪种地址结构。
typeSOCK_STREAM · SOCK_DGRAM语义：面向连接的字节流（circuito virtual），还是无连接的数据报（datagrama）。
protocol0写 0 让系统选默认协议：STREAM → TCP，DGRAM → UDP。也可以显式指定，例如 IPPROTO_SCTP。

SOCK_STREAM · TCP

orientado a conexión (ES) / connection-oriented (EN)——面向连接：先建立连接，再传数据。丢包重传、排序、去重都由系统负责，程序看到的是一条可靠、按顺序的字节流。代价是控制权都在协议手里。

SOCK_DGRAM · UDP

no orientado a conexión (ES) / connectionless (EN)——无连接：不需要事先协商，直接发。没有重传、没有排序；需要可靠性的话，要在应用层自己做。每次发送是一个独立的 datagrama。

int s = socket(AF_INET, SOCK_STREAM, 0);   // IPv4 + TCPif (s == -1) {    perror("socket");                     // 打印出错原因    exit(EXIT_FAILURE);}

PF_INET（Protocol Family）和 AF_INET（Address Family）在 Linux 上数值相同，很多代码把 PF_ 用在 socket()、把 AF_ 用在地址结构里；写哪个都能工作。

别忽视 AF_UNIX

AF_UNIX 套接字只在同一台机器的进程之间通信，地址是文件系统里的一个路径（struct sockaddr_un 的 sun_path）。它常常被忽略，但越来越多的系统服务用它代替传统的进程间通信机制：API 和网络套接字完全一样，换个地址族就行。

§3地址与字节序 T4.4

端口写的是 5005，对方却在 36115 端口上等你。为什么？¡¡¡Atención!!! formato red y formato máquina.

所有带地址的调用（bind、connect、accept、sendto、recvfrom）都接受一个通用的地址指针 struct sockaddr *，再根据它的第一个字段（地址族）去解释后面的字节。IPv4 用的具体结构是 sockaddr_in，传参时强制转换成 sockaddr *：

struct sockaddr {                 // 通用：只用来传指针    sa_family_t sa_family;         // AF_xxx    char        sa_data[14];}; struct sockaddr_in {              // IPv4，<netinet/in.h>    sa_family_t    sin_family;     // AF_INET    in_port_t      sin_port;       // 端口，网络字节序    struct in_addr sin_addr;       // { uint32_t s_addr; } IP，网络字节序    unsigned char  sin_zero[8];    // 填 0，让大小和 sockaddr 一样};

IPv6 用 sockaddr_in6（sin6_family = AF_INET6，地址是 16 字节的 in6_addr，另有 flowinfo、scope_id）；要同时容纳两种地址时用足够大的 struct sockaddr_storage。

formato red · formato máquina

多字节整数在内存里有两种摆法：big endian——大端，高字节放在低地址；little endian——小端，低字节放在低地址。网络协议规定，首部里的端口和地址一律按大端传输，这叫网络字节序（formato red）；而 Intel 和 Raspberry Pi 的 ARM 平时都按小端工作（formato máquina）。看看端口 5005 在内存里是什么样子：

函数（<arpa/inet.h>）方向用于
uint16_t htons(uint16_t)主机 → 网络，16 位端口：sin_port = htons(5005)
uint32_t htonl(uint32_t)主机 → 网络，32 位IPv4 地址常量：sin_addr.s_addr = htonl(INADDR_ANY)
uint16_t ntohs(uint16_t)网络 → 主机，16 位打印收到的端口：ntohs(cli.sin_port)
uint32_t ntohl(uint32_t)网络 → 主机，32 位把收到的地址当整数比较、计算

文本地址 ↔ 二进制地址

人写的是 "192.168.1.20"，sin_addr 里要的是 4 个按网络字节序排好的字节。转换用 inet_pton（presentation → network）和反方向的 inet_ntop，两者都支持 IPv4 和 IPv6，都通过指针传结果：

struct sockaddr_in dst;memset(&dst, 0, sizeof dst);                  // sin_zero 也清零dst.sin_family = AF_INET;dst.sin_port   = htons(5005);if (inet_pton(AF_INET, "192.168.1.20", &dst.sin_addr) != 1)    /* 1 = 成功；0 = 字符串不是合法地址；-1 = 地址族不支持 */; char txt[INET_ADDRSTRLEN];                     // 16 字节，够放 "255.255.255.255"inet_ntop(AF_INET, &dst.sin_addr, txt, sizeof txt);printf("%s:%u\n", txt, ntohs(dst.sin_port));   // 192.168.1.20:5005
  • 老式的 inet_addr("192.168.1.20") 直接返回网络字节序的 32 位值，inet_ntoa() 做反向转换。它们只支持 IPv4，而且 inet_addr 的出错值和 "255.255.255.255" 分不开，新代码用 pton/ntop。
  • INADDR_ANY（值为 0）表示"本机的任何一个地址"：服务器 bind 它，就能收到发往这台机器任何网络接口、目的端口匹配的请求。
  • getaddrinfo("www.example.com", "http", &hints, &res) 从主机名和服务名查出可以直接交给 socket/connect 的地址链表（IPv4、IPv6 都可能有），用完要 freeaddrinfo；反方向是 getnameinfo。
注意 · 资料的写法

有些资料里有一句"inet_addr("192.168.0.1") 之后 s_addr 里是 0xC0A80001"：这是按网络字节序（从左往右）读出的值。在小端的 Raspberry Pi 上直接 printf("%x", s_addr)，看到的是 0x0100A8C0；ntohl(s_addr) 才是 0xC0A80001。

§4TCP 服务器 T4.5 · T4.6

服务器在 5005 端口上接了一个客户，第二个客户来了，还能连上吗？socket → bind → listen → accept → read / write → close.

面向连接的服务器要经过四个准备步骤，每一步都有自己的意义：socket 打开通道（abrir canal），bind 公布地址（publicar dirección），listen 表示愿意接受连接，accept 等待并取出一个连接请求。下面把服务器和客户端放在同一条时间线上，看每个调用什么时候返回、内核在中间做了什么：

各步的参数

调用作用与要点
bind(fd, addr, len)给套接字一个本地地址和端口。创建套接字时它只有地址族，没有具体地址。服务器必须 bind，否则没有固定端口，客户找不到；面向连接的客户端不需要。
listen(fd, backlog)只用于 TCP。打开连接请求队列；backlog 是排队等 accept 的连接数上限，一般 5–10 就够，只等一个客户时可以写 1。
accept(fd, addr, &len)取出队列里的第一个连接，返回新描述符；没有连接时阻塞。addr 带回客户端的地址；len 是输入输出参数：调用前设成结构的大小，返回后是实际长度。不关心对方地址时两者都可以传 NULL。失败返回 -1。
read / write在 accept 返回的描述符上收发，见 §5。
close(fd)关闭连接并释放系统资源，见 §7。

把这几步写成一个最简单的迭代服务器：一次服务一个客户，服务完再去 accept 下一个。这个例子把收到的文本转成大写送回去：

int main(void) {    int lfd = socket(AF_INET, SOCK_STREAM, 0);    if (lfd < 0) { perror("socket"); return 1; }    int on = 1;    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);   // 见 §7     struct sockaddr_in me;    memset(&me, 0, sizeof me);    me.sin_family      = AF_INET;    me.sin_addr.s_addr = htonl(INADDR_ANY);   // 本机任何地址    me.sin_port        = htons(5005);    if (bind(lfd, (struct sockaddr *)&me, sizeof me) < 0) { perror("bind"); return 1; }    if (listen(lfd, 5) < 0) { perror("listen"); return 1; }     for (;;) {        struct sockaddr_in peer;        socklen_t plen = sizeof peer;            // 输入：结构的大小        int cfd = accept(lfd, (struct sockaddr *)&peer, &plen);   // 阻塞        if (cfd < 0) { perror("accept"); continue; }         char buf[128];        ssize_t n;        while ((n = read(cfd, buf, sizeof buf)) > 0) {   // 0 = 客户关闭，-1 = 出错            for (ssize_t i = 0; i < n; i++) buf[i] = toupper((unsigned char)buf[i]);            write_all(cfd, buf, n);                // §5 的辅助函数        }        close(cfd);                                // 只关这个客户；lfd 继续监听    }}

头文件：<sys/socket.h>、<netinet/in.h>、<arpa/inet.h>、<unistd.h>、<string.h>、<ctype.h>、<stdio.h>。这个服务器在服务一个客户时，第二个客户的握手会完成并在队列里等着，但要等第一个客户断开才轮到它——怎样同时服务多个客户见 §7。

注意 · 新套接字的端口

有些资料把 accept 返回的新套接字描述为使用一个动态分配的、和监听端口不同的端口，好让原端口空出来接受新连接。严格地说，新套接字的本地端口仍是 5005：内核按四元组（本地 IP、本地端口、远端 IP、远端端口）区分连接，所以同一个端口上可以同时有一个监听套接字和许多已连接的套接字。两种说法的结论相同：accept 返回一个新的套接字，监听套接字保持可用。

§5TCP 客户端与字节流 T4.7

客户端写了两次，服务器一定读两次吗？TCP es un flujo de bytes: no conserva los límites de los mensajes.

客户端只需要两步：socket，然后 connect 到服务器的地址。connect 会阻塞到连接建立成功（返回 0）或者失败（返回 -1，例如对方端口上没有程序在监听）。不需要 bind：内核在 connect 时自动分配临时端口，并在整个连接期间保留它。

int fd = socket(AF_INET, SOCK_STREAM, 0);struct sockaddr_in srv;memset(&srv, 0, sizeof srv);srv.sin_family = AF_INET;srv.sin_port   = htons(5005);inet_pton(AF_INET, "192.168.1.20", &srv.sin_addr);if (connect(fd, (struct sockaddr *)&srv, sizeof srv) < 0) {   // 阻塞到握手完成    perror("connect");                       // 例如 Connection refused    return 1;}write_all(fd, "hola\n", 5);char buf[64];ssize_t n = read(fd, buf, sizeof buf);close(fd);

read 和 recv 的三种返回值

> 0

读到 n 个字节

n 可能小于你要的长度：只是"目前已经到达的那些"。

= 0

对方关闭了连接

流结束（EOF）。之后不会再有数据，应该 close 自己这一端。

= -1

出错

看 errno，用 perror() 打印原因。

recv(fd, buf, len, flags) 和 send(fd, buf, len, flags) 是只能用在套接字上的版本，flags 通常写 0，此时和 read/write 一样。有用的 flags：MSG_PEEK（看一眼数据但不从队列里取走，下次还能读到）、MSG_OOB（带外的"紧急"数据）、MSG_NOSIGNAL（见 §7）。send/write 返回实际交给内核的字节数，也可能少于要求的长度。

TCP 交给程序的是一条flujo de bytes (ES) / byte stream (EN)——字节流：它保证字节不丢、不重、按顺序到达，但不保留每次 write 的边界：

写的一方也一样：write 可能只写出一部分（尤其是数据量大、对方读得慢时），所以通常包一个循环：

/* 把 len 个字节全部写出去；成功返回 0，出错返回 -1 */int write_all(int fd, const void *p, size_t len) {    const char *c = p;    while (len > 0) {        ssize_t n = write(fd, c, len);        if (n < 0) {            if (errno == EINTR) continue;   // 被信号打断：重试            return -1;        }        c += n; len -= n;                   // 只写出了一部分：接着写剩下的    }    return 0;}

TCP 保证"字节"可靠有序，不保证"消息"。读和写都可能只完成一部分；消息从哪里开始、到哪里结束，是应用层协议的事。

§6UDP：一次一个数据报 T4.8

没有连接，接收方怎么知道是谁发来的、又该回给谁？sendto() y recvfrom() llevan la dirección en cada llamada.

UDP 没有 listen、accept、connect 这一套：两边都是 socket(AF_INET, SOCK_DGRAM, 0)，要接收的一方用 bind 绑定一个已知端口，然后直接收发。因为没有连接把双方"绑"在一起，每次发送都要写明目的地址，每次接收都会带回发送者的地址：

ssize_t sendto(int fd, const void *buf, size_t len, int flags,               const struct sockaddr *to, socklen_t tolen);      // 发给 tossize_t recvfrom(int fd, void *buf, size_t len, int flags,                 struct sockaddr *from, socklen_t *fromlen);      // from 带回发送者

fromlen 和 accept 的长度参数一样是输入输出参数。接收方把 from 原样交给 sendto，就能回复对方。两个调用都返回字节数，出错返回 -1；UDP 没有连接，所以返回 0 不代表"关闭"，只是一个空数据报。

一个接收方：在 6006 端口上收数据报，打印内容和发送者：

int fd = socket(AF_INET, SOCK_DGRAM, 0);struct sockaddr_in me;memset(&me, 0, sizeof me);me.sin_family = AF_INET;me.sin_addr.s_addr = htonl(INADDR_ANY);me.sin_port = htons(6006);bind(fd, (struct sockaddr *)&me, sizeof me);         // 要接收，就要有已知端口 for (;;) {    char buf[1500];                                   // ≥ 最大的数据报    struct sockaddr_in from;    socklen_t flen = sizeof from;    ssize_t n = recvfrom(fd, buf, sizeof buf, 0, (struct sockaddr *)&from, &flen);    if (n < 0) { perror("recvfrom"); continue; }    char ip[INET_ADDRSTRLEN];    inet_ntop(AF_INET, &from.sin_addr, ip, sizeof ip);    printf("%zd bytes de %s:%u: %.*s\n", n, ip, ntohs(from.sin_port), (int)n, buf);}

发送方不需要 bind（只发不收时）；它调用 sendto(fd, msg, len, 0, (struct sockaddr *)&dst, sizeof dst)，内核在第一次发送时自动分配一个临时端口，接收方在 from 里看到的就是它。UDP 套接字也可以调用 connect：这不产生任何协商、立刻返回，只是记下默认的目的地址，之后可以用 send/recv，sendto 的地址参数传 NULL。

可靠性丢了重传、按序、不重复可能丢、乱序、重复
边界字节流，没有消息边界每个数据报是一个整体；读不完的部分丢掉
收发调用read/write、recv/send 都可以（连接里已有对方地址）必须 sendto/recvfrom（或先 connect 记下对方）
谁来控制协议控制，程序几乎插不上手程序自己控制：知道每个包什么时候到、丢了哪些
适合数据必须完整到达：文件、网页、命令控制和实时应用：迟到的数据不如不要

开发应用时 TCP 通常是首选，但它不适合实时：一个包丢了，后面的数据都要等它重传完才能交给程序，延迟不可预测，而程序对此几乎无从控制。UDP 把控制权交还给应用：程序知道每个包何时到达、哪些丢了，可以自己决定是等待、重发还是直接丢弃旧数据。它对更低层的控制仍然有限；需要的话还可以用 raw socket——原始套接字，直接收发 IP 层的包。

§7阻塞、多路复用与关闭 T4.9

服务器停在 accept 里等客户，可它同时还要照看别的事情。怎么办？¿Necesitamos multitarea? select como alternativa.

套接字调用默认是bloqueante (ES) / blocking (EN)——阻塞的：条件不满足，调用就不返回，整个线程停在那里。

调用在等什么
accept队列里出现一个已建立的连接
connect（TCP）三次握手完成或失败
read / recv / recvfrom至少有 1 个字节（或一个数据报）到达，或者对方关闭
write / send（TCP）内核的发送缓冲区有空间放下数据；对方读得慢时会等

只要程序除了通信还有别的事要做（看管传感器、用户界面……），或者要同时服务好几个客户，就不能让唯一的线程卡在一个调用里。有三种思路：

multitarea

每个客户一个线程

主线程只负责 accept；每接到一个连接，就创建一个线程（或 fork 一个进程）专门在那个描述符上读写。每个线程里的代码仍是简单的阻塞写法。最灵活、控制力最强，代价是要处理共享数据的同步（见 Tema 2）。

multiplexación

select / poll

一个线程同时等多个描述符：告诉内核"这些里面任何一个能读了就叫醒我"，再只对就绪的那个调用 accept 或 read，这次调用就不会阻塞。可以在一定程度上避免多线程。

no bloqueante

非阻塞模式

用 fcntl(fd, F_SETFL, O_NONBLOCK) 把描述符设成非阻塞：调用条件不满足时立刻返回 -1，errno 为 EAGAIN/EWOULDBLOCK。通常和 select/poll 搭配使用。

有些资料里把非阻塞标志写作 O_NODELAY；Linux 头文件里对应的名字是 O_NONBLOCK。

每个客户一个线程

static void *atiende(void *arg) {    int cfd = (int)(intptr_t)arg;    /* …在 cfd 上用阻塞的 read/write 服务这个客户… */    close(cfd);    return NULL;} for (;;) {                                       // 主线程：只管接客    int cfd = accept(lfd, NULL, NULL);    if (cfd < 0) continue;    pthread_t th;    pthread_create(&th, NULL, atiende, (void *)(intptr_t)cfd);    pthread_detach(th);                          // 线程结束后自动回收}

select

int select(int nfds, fd_set *readfds, fd_set *writefds,           fd_set *exceptfds, struct timeval *timeout);
  • readfds、writefds、exceptfds 是三组要监视的描述符（可读、可写、异常），不关心的传 NULL。用 FD_ZERO（清空）、FD_SET（加入）、FD_CLR（移除）、FD_ISSET（测试）操作。
  • nfds 是最大的描述符 + 1。
  • timeout（tv_sec 秒 + tv_usec 微秒）到了也会返回，返回值 0；传 NULL 表示一直等。
  • 返回时，内核改写了这些集合：只留下已经就绪的描述符。所以每一轮循环都要从一份"总表"重新复制一次。监听套接字"可读"表示有连接可以 accept；已连接的套接字"可读"表示有数据，或者对方关闭（read 返回 0）。
fd_set all, rd;FD_ZERO(&all);FD_SET(lfd, &all);int maxfd = lfd;for (;;) {    rd = all;                                     // select 会改写集合：每轮复制    struct timeval tv = { 1, 500000 };         // 1.5 s    int r = select(maxfd + 1, &rd, NULL, NULL, &tv);    if (r < 0) { perror("select"); break; }    if (r == 0) { puts("sin actividad"); continue; }   // 超时    for (int fd = 0; fd <= maxfd; fd++) {        if (!FD_ISSET(fd, &rd)) continue;        if (fd == lfd) {                          // 新连接：这次 accept 不会阻塞            int c = accept(lfd, NULL, NULL);            if (c >= 0) { FD_SET(c, &all); if (c > maxfd) maxfd = c; }        } else {                                  // 某个客户有数据或已关闭            char buf[256];            ssize_t n = read(fd, buf, sizeof buf);            if (n <= 0) { close(fd); FD_CLR(fd, &all); }            else write_all(fd, buf, n);            // 这里只是原样送回        }    }}
选哪一种

select 能在一定程度上替代多任务，但线程（或 fork）加定时器的写法灵活得多、控制力也强得多。经验法则：程序还有别的周期性任务、或者每个客户的处理比较复杂时，用线程；只是在几个描述符之间转发少量数据时，select 就够了。poll 做的事和 select 一样，只是用一个 struct pollfd 数组代替三个位集合，没有描述符数目上限（select 受 FD_SETSIZE，通常是 1024，限制）。

关闭：close 和 shutdown

close(fd)

两个方向一起关闭，并释放描述符和系统资源。用完的套接字一定要 close。

shutdown(fd, how)

只关闭通信的某个方向：SHUT_RD（0，不再接收）、SHUT_WR（1，不再发送，对方的 read 会返回 0）、SHUT_RDWR（2，两个方向）。它不释放描述符，之后仍要 close。

有些资料有一页建议"用 shutdown 代替 close"，另几处又强调只有 close 才释放资源。两者并不冲突的写法是：先 shutdown(fd, SHUT_RDWR) 明确结束通信，再 close(fd) 释放描述符。

bind: Address already in use

程序结束后，内核还会让刚关闭的 TCP 连接在 TIME_WAIT 状态里停留一段时间（大约一两分钟），这期间再启动服务器，bind 同一个端口会失败。两种办法：等一会儿，或者在 bind 之前设置 SO_REUSEADDR：

int on = 1;setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);

程序运行期间不 close，端口就一直被占着，别的程序用不了。

SIGPIPE

向一个对方已经关闭的 TCP 连接写数据，内核会给进程发送 SIGPIPE 信号；它的默认动作是终止进程——服务器会莫名其妙地退出。办法是发送时加上 MSG_NOSIGNAL，这时 send 只返回 -1、errno = EPIPE，由程序自己处理：

send(fd, buf, len, MSG_NOSIGNAL);sendto(fd, buf, len, MSG_NOSIGNAL, (struct sockaddr *)&to, sizeof to);

另一种办法是在程序开头忽略这个信号：signal(SIGPIPE, SIG_IGN)，之后 write 也会以 EPIPE 失败而不是终止进程（信号见 Tema 3）。

还有几个有用的小工具：getpeername(fd, …) 取得已连接套接字对端的地址（只用于 TCP）；gethostname(buf, size) 取得本机的名字；getifaddrs/freeifaddrs 列出本机所有网络接口（名字如 eth0、wlan0，以及各自的 IP 地址）。

§8HTTP 报文 T4.10

浏览器也只是一个 TCP 客户端。它在连接上写了什么？HTTP: texto sobre TCP, líneas terminadas en CRLF.

HTTP（HyperText Transfer Protocol）是跑在 TCP 之上的文本协议：浏览器 connect 到服务器（默认 80 端口；地址栏写 http://192.168.1.20:7070/ 时用 7070），写一条请求，服务器读完后写回一条响应。两种报文的结构相同：

  1. 第一行：请求行，或状态行；
  2. 若干行头部，每行 Nombre: valor；
  3. 一个空行；
  4. 正文（可以没有）。

每一行以 CRLF（\r\n，回车 + 换行）结束。这正是 §5 说的"用分隔符定义边界"：服务器要循环 read，直到读到连续的 \r\n\r\n（空行），才知道请求头结束了。

请求 · petición

GET /saludo HTTP/1.1\r\nHost: 192.168.1.20:7070\r\nUser-Agent: Mozilla/5.0 …\r\nAccept: text/html\r\n\r\n

请求行 = 方法 + 路径 + 版本。最常用的方法是 GET（取资源）和 POST（提交数据，数据放在正文里）。GET 请求通常没有正文。

响应 · respuesta

HTTP/1.1 200 OK\r\nContent-Type: text/plain; charset=utf-8\r\nContent-Length: 4\r\nConnection: close\r\n\r\nHola

状态行 = 版本 + 状态码 + 一句说明。常见状态码：200 OK、301 移走了、400 请求格式错、404 Not Found、500 服务器内部错误。

头部意思
Host请求要找的主机名和端口（HTTP/1.1 必须有）
Content-Type正文是什么：text/plain、text/html、application/json……
Content-Length正文有多少字节
Connection: close这次响应之后，服务器会关闭连接

接收方怎么知道正文结束了？

头部靠空行结束，正文却可以是任何字节，不能靠分隔符。HTTP 有三种办法：

  • Content-Length：头部先说正文有几个字节，接收方读够就停。
  • 关闭连接：服务器写完正文就关闭，接收方 read 返回 0 时就知道结束了（Connection: close 明确告诉对方会这样做）。
  • 分块（Transfer-Encoding: chunked）：每块前面写上自己的长度，最后一个长度为 0 的块表示结束。

在服务器一侧，上面那条响应就是一串要写进已连接描述符的字节。下面的片段假设 cfd 是 accept 得到的描述符，并且请求头已经读完：

static const char resp[] =    "HTTP/1.1 200 OK\r\n"    "Content-Type: text/plain; charset=utf-8\r\n"    "Content-Length: 4\r\n"                  // "Hola" = 4 字节    "Connection: close\r\n"    "\r\n"                                    // 空行：头部结束    "Hola";write_all(cfd, resp, sizeof resp - 1);     // 不发字符串末尾的 '\0'close(cfd);

Content-Length 数的是字节，不是字符：正文里有 "ñ"、"á" 这类字符时，它们在 UTF-8 里各占 2 个字节。

自测 12 题

根据本章内容编写的练习题。每题只能点一次，答完会显示解析。

01套接字接口把网络的哪一层提供给应用程序？

B。套接字位于应用层和传输层之间；不过地址族和连接类型仍要由程序指定（§1）。

02在小端的 Raspberry Pi 上，htons(5005)（5005 = 0x138D）按主机序读出来是多少？

C。htons 把两个字节对调（不是把十六进制数字倒过来），这样内存里先是 0x13，和网络字节序一致（§3）。

03下面哪一项填写 sockaddr_in 是正确的（服务器监听本机所有地址的 5005 端口）？

A。sin_family 是地址族而不是套接字类型；端口要用 16 位的 htons 转成网络字节序（§3）。

04哪一个调用只用于 TCP 服务器，作用是让内核开始为这个套接字排队保存连接请求？

D。listen 把套接字变成监听套接字，backlog 是队列长度；accept 才从队列里取连接（§4）。

05关于 TCP 的三次握手和 accept，哪一句是对的？

B。监听套接字始终保持可用，以后和这个客户的数据都走 accept 返回的新描述符（§4）。

06TCP 连接上 read(fd, buf, 100) 返回 0，说明什么？

C。> 0 是读到的字节数，0 是对方关闭，-1 是出错。阻塞模式下没有数据时 read 不会返回，而是等待（§5、§7）。

07客户端先 write(fd, "ABC", 3)，再 write(fd, "DEFG", 4)。服务器调用一次 read(fd, buf, 100)，可能得到什么？

D。TCP 是有序的字节流，没有消息边界；读的一方要循环读，用分隔符或长度前缀切出消息（§5）。

08UDP 发送方发出一个 1000 字节的数据报，接收方调用 recvfrom(fd, buf, 500, 0, …)。结果是？

A。数据报是一个整体，必须一次读完；len 要大于等于对方可能发送的最大数据报（§6）。

09下面哪一方通常不需要调用 bind？

C。connect 时内核会自动分配一个临时端口；服务器和要接收的 UDP 程序则需要一个已知的端口（§4、§5、§6）。

10用 select 等待多个套接字时，为什么每一轮都要把描述符集合重新设置一次？

B。所以常见写法是保存一份"总表"，每轮复制一份交给 select（§7）。

11服务器向一个客户写数据时，客户已经断开，服务器进程随即被终止。原因和对策是？

A。SO_REUSEADDR 解决的是重启后 bind 报 "Address already in use"（§7）。

12一条 HTTP 响应里，什么把头部和正文分开？

D。正文本身的结束靠 Content-Length、关闭连接或分块编码来判断（§8）。
