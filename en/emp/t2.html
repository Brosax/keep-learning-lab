Procesos y threads

Multitasking: processes, threads, and keeping them from clashing

10 Key Points Approx. 25 min read

Things in the physical world happen concurrently: data arrives on the network port, the user presses a button, time ticks away. A program with only a single thread of execution struggles to handle all of them at once. Linux provides two approaches: spawn several independent processes (EN) / procesos (ES), or launch several threads (EN) / hilos (ES) within a single process. This chapter first examines how to create, wait for, and terminate them; next, how the scheduler allocates CPU time; and finally, how to handle the three classic problems that arise when multiple threads share data: race conditions, synchronization, and deadlock.

§1Why Multitasking is Needed T2.1

Can a single while(1) loop wait for network packets, poll keystrokes, and still perform calculations on time?El mundo físico es concurrente.

A common idiom on bare-metal microcontrollers is a single large loop: checking each event in turn, processing whatever is ready. Its limitation is clear: if any single task takes even a little longer (waiting on a network packet, writing to a file), everything else is stalled; worse, every wait has to be restructured into a state machine ("poll and move on"), making code difficult to read.

A board running Linux is a general-purpose computer. The operating system provides multitasking (EN) / multitarea (ES): each task is written as sequential code that simply blocks when it needs to wait, while the OS decides which task gets the CPU at any given moment. Multitasking comes in two granularities:

grano grueso · coarse-grained

Multiple Processes

Each task executes inside its own "virtual machine": the memory it observes starts at virtual address 0 and belongs strictly to itself, with the operating system translating these virtual addresses into physical RAM addresses. The key advantage is isolation: if a process crashes or performs an illegal operation, no other process is dragged down with it.

grano fino · fine-grained

Multiple Threads in a Process

Multiple tasks run inside the same "virtual machine", sharing address space and system resources. Creation, context switching, and communication are much cheaper, at the cost of zero memory isolation: if one thread corrupts memory, every thread in that process is affected.

In production systems, the two approaches are commonly combined: several processes, each hosting multiple threads.

There is also a widespread misconception: spawning two threads means they are "truly running at the exact same physical instant". Not necessarily. With only one core, the operating system divides time into tiny slices and alternates between them: this is concurrency (EN) / concurrencia (ES). Only with multiple physical cores can two threads truly execute simultaneously on distinct cores: this is parallelism (EN) / paralelismo (ES).

A Consequence

The code that creates a thread often finishes before the new thread even begins executing. If main returns immediately after creating a thread, the entire process terminates and the new thread may never execute a single line. §3 explains how to use pthread_join to wait for it.

Multitasking delegates juggling multiple duties to the OS: coarse-grained via processes (strong isolation, higher overhead), fine-grained via threads (shared memory, lower overhead). On a single core you have concurrency; true parallelism requires multiple cores. Execution ordering is always dictated by the scheduler.

§2Processes: Spawning, Duplicating, and Waiting T2.2 · T2.3 · T2.4

Every time you run a program, a new process is created. Inside code, how do you spawn another?Multitarea de grano grueso.

A proceso (process) is an executing program instance: it possesses its own address space (text, global variables, heap, stack), open file descriptors, a unique process ID (PID) / identificador de proceso (PID), and at least one thread.

On the Command Line T2.2

Launching Another Program from Code T2.3

The exec family of functions (execl, execv, execle, execve, execlp, execvp) replaces the current process's image with another program: the PID remains unchanged, but the previous program text and memory are completely replaced. Because exec is "destructive", on success it does not return—there is no longer any code to return to. It returns −1 only on failure.

#include <unistd.h> execl("/bin/ls", "ls", "-l", (char *)0);   // Argument list ends with a null pointerperror("execl");                               // Reaching here indicates exec has failed

Letters in function names follow conventions: l = arguments passed as a list, v = arguments passed in an array (vector), e = custom environment variables passed, p = search for executable in PATH.

To launch another program while continuing caller execution, use posix_spawn / posix_spawnp (<spawn.h>). It is "non-destructive": the caller keeps running, and the new program's PID is returned via the first argument. Internally, this is equivalent to calling fork() and then exec() inside the child process.

fork: Duplicating Yourself T2.4

pid_t fork(void); splits the calling process into two. The caller is the parent process (EN) / proceso padre (ES), and the new instance is the child process (EN) / proceso hijo (ES). The child receives an exact duplicate of the parent's user space: identical code, identical variable copies and values, and identical open file descriptors. Both resume execution from the point where fork() returns. The only difference is the return value:

In code, a single if branches parent and child execution:

#include <stdio.h>#include <stdlib.h>#include <unistd.h>#include <sys/wait.h> int main(void) {    int x = 5;    pid_t pid = fork();    if (pid == -1) {                      // Failure: no child process        perror("fork");        return 1;    }    if (pid == 0) {                       // Child process        x++;        printf("hijo  %d: x = %d\n", (int)getpid(), x);        exit(3);                          // Exit status 3    }    int st;                               // Parent process: pid is child's PID    pid_t h = wait(&st);    if (WIFEXITED(st))        printf("padre %d: hijo %d salió con %d, x = %d\n",               (int)getpid(), (int)h, WEXITSTATUS(st), x);   // x is still 5    return 0;}
void exit(int status)

Terminating Itself

Terminates the calling process, delivering status to the system for the parent to retrieve via wait. Returning return n from main has the identical effect.

pid_t wait(int *st)

Waiting for Any Child

Blocks until any child process terminates; returns its PID. st receives an encoded status integer rather than the raw exit code: check WIFEXITED(st) for normal exit first, then use WEXITSTATUS(st) to extract the exit code.

waitpid(pid, &st, opts)

Waiting for a Specific Child

Waits specifically for the process with PID pid (or any child if pid = -1). Passing WNOHANG in opts prevents blocking: returns 0 immediately if no child has exited.

Zombies and Orphans

Between the moment a child exits and the parent calls wait, it remains a zombie process (EN) / proceso zombi (ES): holding only a single entry in the system process table. Neglecting to wait causes zombies to accumulate. Conversely, if the parent exits first, the child becomes an orphan and is adopted by the system's init process (PID 1), which reaps it automatically. Long-running daemons must either wait for every child or periodically clean up using waitpid(-1, &st, WNOHANG).

Open files in the parent are inherited by the child: both refer to the same open file description (sharing the read/write offset). Be cautious when both processes write to the same file.

When calling fork() repeatedly inside a loop, every existing process duplicates itself, causing the process count to grow as powers of 2. The practice drill below generates questions based on this rule:

fork duplicates the entire process, distinguishing parent and child by its return value: parent gets the child's PID, child gets 0, and failure returns −1. Memory spaces remain independent after duplicating. Children terminate with exit, and parents reap them with wait/waitpid to avoid zombies. exec replaces the active program and never returns on success; posix_spawn starts a new binary while preserving the caller.

§3Threads: Multiple Lines of Execution Within a Process T2.5 · T2.6

When you don't want to duplicate the entire process, but simply need an additional thread of execution, what do you do?Threads: líneas de ejecución concurrente dentro de un proceso.

A thread (hilo) is the smallest execution unit that an operating system can schedule: an instruction stream executing concurrently within a process. Every process starts with at least one thread, the main thread (EN) / hilo principal (ES), which is the thread executing main.

Threads in the Same ProcessContents
SharedCode (text), global variables, static variables inside functions, heap memory (allocated via malloc), open file descriptors, PID, and signal disposition
Private to Each ThreadProgram counter (PC) and CPU registers, stack (meaning local variables are private to each thread), thread ID pthread_t, scheduling priority, errno, and thread-specific data (TSD)

When two threads execute the same function, each thread maintains its own copy of the function's local variables (on its own stack); however, if a local variable is declared static, only one shared copy exists across both threads.

Compared to processes, the primary advantage of threads is being lightweight:

  • Creating a thread is significantly faster than creating a process (commonly estimated at an order of magnitude faster), and termination is similarly cheaper: the kernel only needs to reclaim the thread context and stack, without tearing down an entire process control block.
  • Context switches between threads within the same process are much faster: the CPU only switches the PC, registers, and stack pointer, without switching the memory address space. It remains a context switch, but a vastly cheaper one.
  • Inter-thread communication takes place directly through reading and writing shared memory, avoiding round-trips through the kernel.

The cost also stems from sharing: there is zero fault isolation. If one thread corrupts memory or crashes, the entire process terminates; and shared mutable data must be protected manually (§5).

Threads can be implemented at kernel level (the kernel is aware of each thread, schedules them directly, and can utilize multiple CPU cores) or in user space (a user-level library handles thread switching within a single process, while the kernel sees only one process: no OS modifications needed, but incapable of multi-core parallelism, and a blocking system call by one thread halts the entire process). Modern Linux uses kernel-level threads (NPTL): each pthread corresponds to a distinct kernel scheduling entity.

Creation, Termination, and Joining T2.6

Why use threads? When you need to perform another task simultaneously without abandoning the current work. A regular function call forces the caller to pause until the function completes; pthread_create launches the function on a new execution path while the caller proceeds immediately:

#include <pthread.h> int  pthread_create(pthread_t *tid, const pthread_attr_t *attr,                     void *(*funcion)(void *), void *arg);void pthread_exit(void *valor);int  pthread_join(pthread_t tid, void **valor);pthread_t pthread_self(void);int  pthread_equal(pthread_t t1, pthread_t t2);
  • tid: Output argument storing the new thread's thread ID (EN) / identificador (ES).
  • attr: Creation attributes (priority, scheduling policy, stack size, etc.); pass NULL to use all defaults (§4).
  • funcion: The entry-point function for the new thread, which must conform to the signature void *f(void *): taking one void * argument and returning a void *.
  • arg: The argument passed to funcion. To pass multiple values, pack them into a struct and pass the struct's address.
  • Return value: Returns 0 on success, or an error number on failure (not −1, and does not set errno); print using strerror(err).

A thread terminates under three conditions: returning from its entry function funcion; calling pthread_exit(valor); or being canceled by another thread in the same process (pthread_cancel). In the first two cases, the void * acts as the thread's return value. Another thread calling pthread_join(tid, &r) blocks until tid terminates, storing that return pointer into r.

Example: Two threads each compute the sum of half an array; the main thread waits for both and computes the total. Parameters and results are organized in separate structs:

#include <pthread.h>#include <stdio.h>#include <string.h> typedef struct { const int *v; int n; long suma; } tarea_t; void *sumar(void *arg) {    tarea_t *t = arg;                      // void * → concrete type    t->suma = 0;    for (int i = 0; i < t->n; i++)        t->suma += t->v[i];    return t;                              // Equivalent to pthread_exit(t)} int main(void) {    static int datos[1000];    for (int i = 0; i < 1000; i++) datos[i] = i;     tarea_t a = { datos, 500, 0 }, b = { datos + 500, 500, 0 };    pthread_t ha, hb;    int err = pthread_create(&ha, NULL, sumar, &a);    if (err) { fprintf(stderr, "create: %s\n", strerror(err)); return 1; }    err = pthread_create(&hb, NULL, sumar, &b);    if (err) { fprintf(stderr, "create: %s\n", strerror(err)); return 1; } void *r;    pthread_join(ha, &r);                   // Blocks until ha terminates; r == &a    pthread_join(hb, NULL);                 // Pass NULL when return value is not needed    printf("total = %ld\n", ((tarea_t *)r)->suma + b.suma);   // 499500    return 0;}

When compiling, link against the POSIX threads library: gcc -o suma suma.c -lpthread (or use -pthread to set both compiler and linker flags). When cross-compiling for Raspberry Pi, replace gcc with the toolchain compiler; flags remain unchanged.

Three Common Mistakes

Main Exits Early: When main returns (or any thread calls exit), the entire process terminates and all sibling threads vanish immediately. Either call pthread_join to wait for them, or have main call pthread_exit(NULL): this terminates only the main thread while keeping the process alive until all remaining threads finish. Using sleep to wait is sheer guesswork.

Passing a Mutating Address: In for (i = 0; i < 4; i++) pthread_create(&h[i], NULL, f, &i);, all four threads receive the same address &i, and the value they read depends on arbitrary scheduling. Each thread must receive its own distinct storage (an array element or dedicated struct).

Returning a Stack-Allocated Address: If a thread function returns a pointer to its own local stack variable, that stack frame is destroyed upon return, leaving join with a dangling pointer to invalid memory. Store results in caller-provided structures or dynamic heap memory allocated via malloc.

pthread_self() returns the calling thread's own thread ID; compare two thread IDs with pthread_equal(t1, t2) (returns non-zero if equal, 0 if different) rather than ==, as pthread_t is not guaranteed to be an integer.

When each thread requires its own private copy of a global variable, use thread-specific data (TSD): call pthread_key_create(&key, destructor) to create a process-wide key, then use pthread_setspecific(key, ptr) to attach private data and pthread_getspecific(key) to retrieve it; the destructor reclaims the memory upon thread exit. A common idiom to initialize the key exactly once across all threads is pthread_once.

Threads share global data and the heap, while maintaining their own private stacks and registers. pthread_create starts a void *f(void *) function with struct parameters passed by address; threads terminate via return or pthread_exit, and pthread_join blocks synchronously to retrieve return values. Always link with -lpthread; returning from main terminates all sibling threads.

§4Scheduling: Who Gets the CPU First T2.7

Ten threads are ready to run, but the CPU has only a few cores. Who decides, and by what rules?Scheduling: SCHED_FIFO, SCHED_RR, SCHED_OTHER.

The kernel's scheduler (EN) / planificador (ES) is responsible for allocating CPU execution time. From its perspective, every thread exists in one of three states at any given moment:

en ejecución · running

Running

Actively occupying a CPU core and executing instructions. On a single core, only one thread can be in this state at any instant.

listo · ready

Ready

Everything is prepared and waiting only for CPU allocation; queued in the ready queue.

bloqueado · blocked

Blocked

Waiting for an external event: timer expiration, incoming data on read, pthread_join, pthread_mutex_lock... Transitions to ready once the event occurs; consumes zero CPU while blocked.

A running thread yields the CPU for one of three reasons: it blocks voluntarily; it is preempted by a higher-priority ready thread; or its quantum / time slice (EN) / rodaja de tiempo (ES) expires. POSIX defines three primary scheduling policies:

PolicyRules
SCHED_FIFOMaintains one queue per priority level; always executes the thread queued the longest in the highest-priority non-empty queue. It runs continuously until it blocks, voluntarily yields (sched_yield), or is preempted by a higher priority; peer threads of identical priority must wait.
SCHED_RRPrioritized like FIFO, but adds a time limit: threads of identical priority run for at most one time slice before being moved to the tail of their priority queue, alternating execution in round-robin fashion.
SCHED_OTHERDefault policy; specific behavior is OS-dependent. On Linux, this is completely fair time-sharing: all threads hold static priority 0, with CPU time distributed dynamically based on nice values and consumed runtime.

FIFO and RR are real-time policies: on Linux, real-time priorities span 1–99 (higher numbers indicate higher urgency, queryable via sched_get_priority_min/max), and any ready real-time thread preempts all SCHED_OTHER threads. Because real-time threads can easily starve standard processes, configuring them requires superuser privileges.

Below we observe how three threads of equal priority share CPU time under SCHED_RR. The rule is simple: whichever thread is scheduled runs for up to one time slice; if incomplete, it moves to the tail of the queue; if its remaining workload is less than a slice, it yields immediately upon completion.

Setting Policy and Priority Programmatically

Policies and priorities are passed to pthread_create using creation attributes pthread_attr_t:

#include <pthread.h>#include <sched.h> pthread_attr_t attr;struct sched_param sp = { .sched_priority = 20 }; pthread_attr_init(&attr);                                  // Initialize to default valuespthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED); // Do not inherit creator's policypthread_attr_setschedpolicy(&attr, SCHED_RR);pthread_attr_setschedparam(&attr, &sp);                    // Note pointer argumentint err = pthread_create(&tid, &attr, trabajo, NULL);    // Returns EPERM without privilegespthread_attr_destroy(&attr);
  • Linux by default configures threads to inherit the creator's scheduling settings, ignoring policies and priorities specified in attributes; call PTHREAD_EXPLICIT_SCHED to disable inheritance.
  • Scheduling can also be modified dynamically during execution: pthread_setschedparam(tid, SCHED_FIFO, &sp), and queried via pthread_getschedparam(tid, &pol, &sp).
  • sched_yield(): The caller voluntarily relinquishes the CPU, prompting the scheduler to run the next ready thread of the same priority; if no such thread exists, it returns immediately and continues execution. Lower-priority threads are not granted CPU time by this call. Combined with SCHED_FIFO, this enables cooperative multitasking.

Threads transition between running, ready, and blocked. SCHED_FIFO runs highest-priority tasks to completion or block; SCHED_RR adds time slices for round-robin among equal priority; SCHED_OTHER is the default fair time-share scheduler. Real-time policies require elevated privileges and explicit attribute inheritance disabling; sched_yield yields only to equal-priority peers.

§5Race Conditions and Mutexes T2.8

If two threads each execute count = count + 1 once, is count guaranteed to increase by 2?Condición de carrera y sección crítica.

In C, the line count = count + 1; compiles down to three assembly instructions: load from memory into register (LDR), increment register (ADD), and store back to memory (STR). The scheduler may switch threads between any two instructions (and on multi-core systems, both threads may execute simultaneously). Observe what happens when two threads collide:

race condition (EN) / condición de carrera (ES): A situation where program output depends on the precise timing of thread execution. The code segment that accesses shared data and must complete without interruption is called a critical section (EN) / sección crítica (ES). The requirement that at most one thread enters the critical section simultaneously is mutual exclusion (EN) / exclusión mutua (ES). POSIX threads provide a mutex for this purpose.

pthread_mutex: A Lock

A mutex is a system-managed synchronization variable indicating "this resource is currently held by a specific thread". Its usage pattern is always three steps: lock → critical section → unlock.

#include <pthread.h> long contador = 0;                                   // Global: shared across all threadspthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;        // Static initialization with default attributes void *sumar_mucho(void *arg) {    for (int i = 0; i < 1000000; i++) {        pthread_mutex_lock(&m);                     // Enter critical section        contador++;        pthread_mutex_unlock(&m);                   // Exit critical section    }    return NULL;}// Both threads run sumar_mucho; joining yields contador == 2000000.// Remove lock/unlock lines: result is typically less than 2000000 and varies every run.
FunctionPurpose
PTHREAD_MUTEX_INITIALIZERStatic initialization with default attributes. Simple and preferred whenever applicable.
pthread_mutex_init(&m, &attr)Dynamic initialization, allowing non-default attributes; passing NULL in attr uses defaults.
pthread_mutex_lock(&m)Acquires the lock; blocks (thread sleeps) if already held by another thread until available. Returns 0 on success.
pthread_mutex_trylock(&m)Attempts to acquire the lock; returns 0 if acquired; returns non-zero (EBUSY) immediately without blocking if held.
pthread_mutex_unlock(&m)Releases the lock, unblocking one waiting thread. Returns 0 on success.
pthread_mutex_destroy(&m)Destroys the mutex when no longer needed, freeing internal resources.

The mutex type is configured via pthread_mutexattr_settype(&attr, tipo), differing in how misuse is handled:

TypeRelocking by Same ThreadUnlocking Unowned / Unlocked Mutex

By default, mutexes operate strictly between threads of the same process (PTHREAD_PROCESS_PRIVATE). Setting PTHREAD_PROCESS_SHARED (via pthread_mutexattr_setpshared) allows inter-process synchronization, provided the mutex itself resides in shared memory accessible by all participating processes (via mmap or shmat).

Locks are Purely Advisory

Mutexes are advisory, resembling traffic lights: a red light requests you to stop, but there is no physical barrier. If a thread modifies shared memory without calling lock, nothing prevents it. The protocol must be strictly observed by programmers: every single access to that shared data must acquire the identical lock.

Race conditions stem from non-atomic read-modify-write sequences interrupted by concurrency. Guard shared data inside critical sections enclosed by a single pthread_mutex: lock blocks on contention, trylock returns immediately, and unlock awakens waiting threads. Keep critical sections brief; locking is purely advisory.

§6Synchronization: Waiting Until a Condition Holds T2.9

When the buffer is empty, how should a consumer wait? Spin in a continuous loop of lock, check, and unlock?Variables condicionales, semáforos y productor–consumidor.

Mutexes solve the problem of "preventing simultaneous access". Another fundamental challenge is "waiting for a specific event before proceeding"—for example, a consumer waiting for items to appear in a buffer. Polling repeatedly under a mutex (busy-waiting) wastes CPU cycles. A condition variable (EN) / variable condicional (ES) enables a thread to sleep until notified by another thread that the condition may now hold.

FunctionPurpose
PTHREAD_COND_INITIALIZERStatic initialization; dynamic via pthread_cond_init(&c, NULL); destroyed via pthread_cond_destroy.
pthread_cond_wait(&c, &m)Must be invoked with m already held. It atomically releases m and puts the thread to sleep on c; upon waking, it reacquires m before returning. The caller holds m both entering and exiting this function.
pthread_cond_signal(&c)Wakes at least one thread sleeping on c; does nothing if no thread is waiting (does not buffer notifications).
pthread_cond_broadcast(&c)Wakes all threads sleeping on c, prompting each to re-evaluate its condition.
pthread_cond_timedwait(&c, &m, &t)Identical to wait, but returns ETIMEDOUT if the specified absolute time t (struct timespec) arrives before being signaled.
Why while is Mandatory

Waking up does not guarantee that the condition is met: another consumer thread may have snatched the item first; multiple threads woken by broadcast contend for the same item; and the POSIX standard explicitly permits spurious wakeups (EN) / despertares espurios (ES) where a thread wakes without any signal. Therefore, the canonical pattern is always while (!condition) pthread_cond_wait(...): re-evaluate upon waking, and resume sleeping if the condition is false.

The Producer–Consumer Pattern

A classic concurrency problem: one or more producers (EN) / productores (ES) place data into a ring buffer of capacity N, while one or more consumers (EN) / consumidores (ES) retrieve items. If full, producers must wait; if empty, consumers must wait. This is implemented using one mutex and two condition variables:

#define N 8int buf[N], ini = 0, fin = 0, n = 0;pthread_mutex_t m        = PTHREAD_MUTEX_INITIALIZER;pthread_cond_t  no_vacio = PTHREAD_COND_INITIALIZER;   // "Data available"pthread_cond_t  no_lleno = PTHREAD_COND_INITIALIZER;   // "Space available" void poner(int x) {                              // Producer call    pthread_mutex_lock(&m);    while (n == N)        pthread_cond_wait(&no_lleno, &m);    buf[fin] = x;  fin = (fin + 1) % N;  n++;    pthread_cond_signal(&no_vacio);    pthread_mutex_unlock(&m);} int tomar(void) {                                // Consumer call    pthread_mutex_lock(&m);    while (n == 0)        pthread_cond_wait(&no_vacio, &m);    int x = buf[ini];  ini = (ini + 1) % N;  n--;    pthread_cond_signal(&no_lleno);    pthread_mutex_unlock(&m);    return x;}

The sequence is: update state (n++) inside the lock, then signal. Because waiting threads always check state in a while loop, the relative order of state mutation and signaling (so long as both are protected) does not compromise correctness. When multiple threads wait on varying conditions or multiple items are inserted, broadcast is safer.

Waiting with a timeout requires an absolute timestamp:

struct timespec t;clock_gettime(CLOCK_REALTIME, &t);t.tv_sec += 2;                                     // Wait at most 2 secondspthread_mutex_lock(&m);while (n == 0) {    if (pthread_cond_timedwait(&no_vacio, &m, &t) == ETIMEDOUT)        break;                                     // Timed out: n may still be 0}pthread_mutex_unlock(&m);

Semaphores: sem_t

A semaphore (EN) / semáforo (ES) is a non-negative counter supporting two atomic operations: sem_wait (P operation), which decrements the counter by 1 and blocks if the counter is already 0 until someone increments it; and sem_post (V operation), which increments it by 1, waking a waiting thread. Initialized to 1, it functions as a lock; initialized to N, it counts available resource slots. Unlike condition variables, semaphores remember every post, even if no thread is waiting at that instant.

Function (<semaphore.h>)Purpose
sem_init(&s, pshared, valor)Initializes semaphore with value valor. pshared = 0: thread-local; non-zero: shared across processes (must reside in shared memory).
sem_wait(&s)Decrements and returns if s > 0; blocks if s = 0. sem_trywait is non-blocking; sem_timedwait supports absolute timeout.
sem_post(&s)Increments by 1, awakening a waiting thread if present.
sem_destroy(&s)Destroys the semaphore.

Writing producer–consumer with semaphores: one semaphore counts empty slots, one counts items, and a mutex protects buffer index manipulation:

#include <semaphore.h>sem_t huecos, datos;sem_init(&huecos, 0, N);                         // Initially N empty slotssem_init(&datos,  0, 0);                         // Initially 0 items void poner(int x) {    sem_wait(&huecos);                            // Wait for an empty slot    pthread_mutex_lock(&m);    buf[fin] = x;  fin = (fin + 1) % N;    pthread_mutex_unlock(&m);    sem_post(&datos);                             // One more item available} int tomar(void) {    sem_wait(&datos);                             // Wait for an item    pthread_mutex_lock(&m);    int x = buf[ini];  ini = (ini + 1) % N;    pthread_mutex_unlock(&m);    sem_post(&huecos);                            // One more empty slot available    return x;}

Notice that sem_wait is placed outside the mutex lock: if a thread acquired the lock before blocking on sem_wait, the other side could never acquire the lock to call sem_post, deadlocking both sides (covered in §7).

Condition variables: acquire lock, check condition in while loop, sleep via cond_wait (atomically releases lock and sleeps, re-locking upon wakeup); signaling thread mutates state then signals or broadcasts. Semaphores: counters where sem_wait decrements and sem_post increments, ideal for tracking discrete resource quotas. Producer-consumer combines a mutex guarding buffer indices with two condition triggers (slots available, items available).

§7Deadlock and Common Pitfalls T2.10

Two threads are each waiting for the other to let go. Who releases first?Bloqueo mutuo (deadlock).

When a thread needs to acquire multiple locks simultaneously, deadlock risks emerge. Suppose Thread 1 locks A then B, while Thread 2 locks B then A:

Another prevention strategy is "back off on contention": acquire the first lock, then attempt the second via pthread_mutex_trylock; if acquisition fails, release the first lock and retry from the beginning:

for (;;) {    pthread_mutex_lock(&B);    if (pthread_mutex_trylock(&A) == 0)        break;                          // Both locks acquired successfully    pthread_mutex_unlock(&B);          // Failed to acquire A: release B to allow peer to progress}/* Access both resources */pthread_mutex_unlock(&A);pthread_mutex_unlock(&B);

While this prevents deadlock, threads may repeatedly yield to one another without making progress (livelock), making consistent global lock ordering the superior approach.

Consumer wakes up but finds buffer emptyEnclosed pthread_cond_wait with if instead of while (§6).

Deadlock occurs when threads hold resources while waiting on others in a cyclic dependency. Prevention: enforce a universal lock ordering across all threads, or release held locks on trylock failure. Keep lock holding times minimal, and never initiate blocking operations while holding a mutex.

Self-Assessment 12 Questions

Review questions based on chapter concepts. Single attempt per question; explanations display immediately upon selection.

01In the parent process, int x = 5; is declared, followed by fork(). The child process executes x = 9; and exits. The parent calls wait and prints x. What is printed?

B. fork clones the entire user address space; thereafter, both memory spaces are completely independent (§2). Threads share memory, not processes.

02Inside the child process, what is the return value of fork()?

C. The parent receives the child's PID (> 0), while the child receives 0; −1 indicates failure and is returned only to the parent (§2).

03After execl("/bin/date", "date", (char *)0);, there is an immediate line printf("listo\n");. Under what condition is "listo" printed?

D. On success, exec replaces the active process image completely and never returns; reaching the next line indicates exec failed. To retain the caller, use posix_spawn or fork + exec (§2).

04Two threads within the same process execute the same function. Which variable is not shared between the two threads?

A. Automatic local variables reside on each thread's private stack; static local variables, globals, and heap memory are shared (§3).

05In main, immediately after calling pthread_create to spawn a thread, it executes return 0;. What happens?

B. Returning from main is equivalent to exit, terminating the process and all sibling threads immediately. Use pthread_join or call pthread_exit from main (§3).

06A thread function finishes by calling pthread_exit(p);. How does another thread retrieve pointer p?

C. The second argument of pthread_join is void **, used to store the pointer passed to pthread_exit or returned from the entry function; pthread_join itself returns an integer status code (§3).

07What is the key difference between SCHED_FIFO and SCHED_RR?

D. Both select threads based on fixed static priority; RR simply adds a time slice limit for equal-priority peers. The default policy is SCHED_OTHER (§4).

08Two threads each perform c++ 1000 times on an unsynchronized global counter c (initial value 0). After joining both threads, what is the value of c?

A. Incrementing is a 3-step read-modify-write; overlapping execution causes lost updates, so the total will be at most 2000 and cannot spontaneously exceed 2000 (§5).

09A mutex is currently held by another thread. If a thread calls pthread_mutex_trylock(&m), what happens?

B. trylock is a non-blocking lock request: returns 0 if acquired, and immediately returns non-zero (EBUSY) without blocking if contested (§5).

10What occurs when calling pthread_cond_wait(&c, &m)?

C. The caller holds m upon entering and exiting cond_wait; while asleep, m is released so peer threads can enter to update state (§6). Condition verification is the caller's duty via while.

11Why must pthread_cond_wait be enclosed in while (n == 0) rather than if (n == 0)?

D. Re-evaluating upon waking ensures that if the condition is not met, the thread immediately resumes sleeping (§6).

12T1 locks mutex A then B; T2 locks mutex B then A. The program occasionally deadlocks. What is the most direct fix?

A. Universal lock hierarchy prevents cyclic wait dependencies. RECURSIVE only allows recursive relocking by the same thread; yield and priorities merely shift occurrence probabilities (§7).
